# Создание справочников знаний

Создавай структурированные справочники из внешних источников и храни их в директории справочников,
чтобы другие kodla-навыки могли переиспользовать их в дальнейшем.

## Когда использовать

- AI нужна документация, которую он не знает или знает только частично
- Нужны выверенные ответы на основе конкретной документации, спецификаций или внутренних файлов
- Нужен переиспользуемый контекст для `/kodla-plan`, `/kodla-implement-plan`, `/kodla-research`
- Нужен постоянный артефакт знаний вместо одноразового контекста разговора

## Шаг 0: Загрузка конфига

**В ПЕРВУЮ ОЧЕРЕДЬ:** Прочитай `.kodla/config.yaml` если существует, и извлеки:
- **Пути:** `paths.references` — директория хранения справочников

Значения по умолчанию:
- Директория справочников: `.kodla/references/`

Если `config.yaml` не существует — использовать значения по умолчанию. Никогда не использовать `.ai-factory/` как fallback.

## Шаг 0.1: Подготовка

Убедись что директория справочников существует:

```bash
mkdir -p <директория справочников>
```

Проверь существующие справочники чтобы избежать дублирования:

```bash
ls <директория справочников>
```

Если `--name <имя>` передан — использовать его как имя справочника.
Если `--update` передан — найти существующий справочник и обновить его вместо создания нового.

## Определение режима

Проверь аргументы (`$ARGUMENTS`):

```
Содержит "--update"           → Режим обновления: обновить существующий справочник
Содержит URL (http/https)     → Режим URL: загрузить и обработать веб-источники
Содержит пути к файлам        → Режим файлов: обработать локальные документы
"list"                        → Показать существующие справочники
"show <имя>"                  → Показать содержимое справочника
"delete <имя>"                → Удалить справочник (с подтверждением)
Пусто                         → Интерактивный режим
```

## Шаг 1: Сбор источников

### Для URL

Для каждого URL:

1. Загрузи страницу через `WebFetch` и извлеки:
   - главную тему и назначение
   - ключевые концепции, термины и определения
   - примеры кода и паттерны
   - методы API, параметры, возвращаемые типы и сигнатуры
   - параметры конфигурации со значениями по умолчанию
   - лучшие практики и рекомендации
   - обработку ошибок и граничные случаи
   - информацию о версиях и совместимости
   - ссылки на важные подстраницы
2. Если есть ссылки на критические подстраницы — загрузи и их (до 8 дополнительных страниц на каждый исходный URL)
3. Если остались очевидные пробелы — выполни 1-2 целевых запроса через `WebSearch` для их заполнения
4. Если URL недоступен или требует авторизации — сообщи об этом, не угадывай содержимое

### Для локальных файлов

1. Прочитай каждый файл через `Read`
2. Если файл ссылается на другие локальные файлы — прочитай и их (до 5 уровней вложенности)
3. Определи формат (markdown, HTML, JSON, YAML, plain text) и извлеки информацию соответственно

### Интерактивный режим

Спроси пользователя через `AskUserQuestion`:
1. Какую тему или технологию должен охватывать справочник?
2. Есть ли URL или локальные файлы, или нужно выполнить поиск?
3. Какие аспекты наиболее важны для их задачи?

## Шаг 2: Синтез справочника

Преобразуй собранный материал в структурированный справочный документ.

**Формат справочного файла:**

```markdown
# <Тема> Справочник

> Источник: <список URL или путей к файлам>
> Создан: YYYY-MM-DD
> Обновлён: YYYY-MM-DD

## Обзор

<1-3 параграфа резюме>

## Основные концепции

<Концепция 1>: <чёткое объяснение>
<Концепция 2>: <чёткое объяснение>

## API / Интерфейс

<Только если применимо. Сохраняй точные сигнатуры и типы из исходной документации.>

## Паттерны использования

<Практические примеры кода, организованные по сценариям использования.>

## Конфигурация

<Параметры, значения по умолчанию, допустимые значения. Предпочтительно в формате таблицы.>

## Лучшие практики

<Нумерованный список с обоснованиями>

## Частые ошибки

<Что идёт не так и как этого избежать>

## Заметки о версиях

<Только если актуально. Критические изменения, инструкции по миграции, устаревания.>
```

**Правила качества:**
- **Без галлюцинаций** — включай только то что фактически найдено в источниках
- **Код дословно** — примеры из документации должны оставаться точными
- **Практично, а не академично** — оптимизировано для удобного поиска
- **Плотно** — максимум полезной информации на строку
- **Полные сигнатуры** — API нужны все параметры, типы и возвращаемые значения
- **Атрибуция источников** — всегда указывать исходные URL или пути

## Шаг 3: Название и сохранение

**Соглашение об именах:**
- Выводи из темы: `react-hooks.md`, `fastapi-endpoints.md`, `docker-compose.md`
- Используй строчные буквы, дефисы, расширение `.md`
- Если передан `--name` — использовать его (добавить `.md` если отсутствует)
- Избегай обобщённых имён типа `reference.md`

**Сохрани в:** `<директория справочников>/<имя>.md`

## Шаг 4: Регистрация в INDEX.md

Проверь наличие `<директория справочников>/INDEX.md`. Создай или обнови его:

```markdown
# Индекс справочников

Доступные справочники знаний для AI-агентов.

| Справочник | Тема | Источники | Обновлён |
|------------|------|-----------|---------|
| [react-hooks](react-hooks.md) | React Hooks API и паттерны | react.dev | 2026-03-20 |
| [docker-compose](docker-compose.md) | Конфигурация Docker Compose | docs.docker.com | 2026-03-20 |
```

## Шаг 5: Отчёт

Покажи пользователю:
- имя и путь справочника
- размер (количество строк — используй `wc -l`)
- включённые разделы
- использованные URL или пути к файлам
- как использовать его в дальнейших kodla-задачах

## Режим обновления (`--update`)

Когда передан `--update`:

1. Найди существующий справочник по `--name` или по совпадению источников
2. Повторно загрузи источники из заголовка файла (`> Источник: ...`)
3. Сравни новый материал с существующим содержимым, обнови только изменившиеся разделы
4. Сохраняй значение `Создан:`, обновляй `Обновлён:`
5. Сообщи что изменилось

## Список / Просмотр / Удаление

- **`/kodla-reference list`** — прочитай и отобрази `<директория справочников>/INDEX.md` или перечисли файлы в директории
- **`/kodla-reference show <имя>`** — прочитай и отобрази содержимое справочника (`.md` необязателен)
- **`/kodla-reference delete <имя>`** — запроси подтверждение через `AskUserQuestion`, удали файл и обнови `INDEX.md`

## Интеграция с планами tasar

При запуске в интерактивном режиме или при поиске контекста — проверь наличие tasar-планов в проекте:

```bash
test -d tasar || test -d .tasar
```

Если папка найдена:
- Прочитай `tasar/specs/` (или `.tasar/specs/`) для понимания требований проекта
- Прочитай активные `tasar/changes/*/tasks.md` (или `.tasar/changes/*/tasks.md`, исключая `archive/`) для понимания текущих задач
- В отчёте (Шаг 5) укажи если создаваемый справочник релевантен текущим планам

## Интеграция с другими навыками

Справочники из директории справочников доступны всем kodla-навыкам:
- `/kodla-plan` и `/kodla-implement-plan` могут читать их для получения доменного контекста
- `/kodla-research` может использовать их как источники при исследовании

Чтобы указать навыку конкретный справочник — упомяни его в `RULES.md` проекта или `.kodla/rules/base.md`:

```markdown
## Справочники
- Детали по <теме> см. в `<директория справочников>/<имя>.md`
```

## Ограничения

- **Максимальный размер справочника:** стремись к не более 1000 строк. Если больше — разбей на несколько файлов в поддиректории внутри директории справочников, создай `INDEX.md` внутри этой поддиректории
- **Без дублирования:** проверяй существующие справочники перед созданием нового
- **Без устаревших данных:** всегда указывай источники чтобы справочник можно было обновить
- **Без мнений:** справочники должны отражать источники, а не личные предпочтения
- **Доступность источников:** если URL требует авторизации или недоступен — сообщи об этом вместо того чтобы угадывать содержимое
- **Без git-действий:** не выполнять никаких git-операций (коммиты, ветки, статус)
- **Без handoff:** режим передачи контекста между агентами не поддерживается
