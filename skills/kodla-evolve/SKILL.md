# Evolve — Самоулучшение навыков

Анализирует контекст проекта, патчи и кодовую базу для улучшения существующих навыков. Делает kodla умнее с каждым запуском.

## Основная идея

```
патчи (прошлые ошибки) + контекст проекта + паттерны кодовой базы
    ↓
анализ повторяющихся проблем, ловушек стека, конвенций проекта
    ↓
обогащение навыков проектно-специфичными правилами, защитами и паттернами
```

## Политика потребления патчей

Используется двухуровневая модель обучения:

1. **Сырые патчи** (`paths.patches`, по умолчанию: `.kodla/patches/*.md`) — исходный материал.
2. **Правила skill-context** (`.kodla/skill-context/*`) — компактный, переиспользуемый результат.

Политика по навыкам:
- `/kodla-evolve` — основной анализатор сырых патчей. Обрабатывает патчи **инкрементально** с помощью курсора.
- `/kodla-implement-plan`, `/kodla-plan` и другие навыки — предпочитают skill-context; сырые патчи используют только как резервный контекст.
- Полный повторный анализ — только при необходимости (сбросить курсор и перезапустить evolve).

## Критично: никогда не редактировать встроенные навыки напрямую

**НИКОГДА не изменяй файлы внутри директорий встроенных навыков** (`skills/kodla-*/`).
Все файлы в этих директориях управляются kodla и будут перезаписаны при обновлении — прямые правки будут потеряны.

**ВСЕГДА записывай проектно-специфичные правила в skill-context:**
```
.kodla/skill-context/<имя-навыка>/SKILL.md
```

Это ЕДИНСТВЕННО правильная цель для улучшений встроенных навыков. Без исключений.

## Рабочий процесс

### Шаг 0: Разрешение цели и загрузка контекста

#### Шаг 0.1: Разрешение цели

**Нормализация имени навыка из `$ARGUMENTS`:**

| Ввод пользователя  | Разрешённое имя  |
|--------------------|-----------------|
| `plan`             | `kodla-plan`    |
| `kodla-plan`       | `kodla-plan`    |
| `/kodla-plan`      | `kodla-plan`    |
| `my-custom-skill`  | `my-custom-skill` |

Правило: сначала убрать ведущий `/`. Затем: если аргумент не начинается с `kodla-` И навык с именем `kodla-<аргумент>` существует — использовать `kodla-<аргумент>`. Иначе использовать как есть.

**После разрешения имени:** убедиться что навык действительно существует
(проверить `{{skills_dir}}/<имя>/SKILL.md` или `skills/<имя>/SKILL.md`).
Если навык не найден → сообщить об ошибке и остановиться:
"Навык '<имя>' не найден. Запусти `/kodla-evolve` без аргументов чтобы улучшить все навыки, или укажи корректное имя."

**Определение целевых навыков из `$ARGUMENTS`:**
- Если `$ARGUMENTS` содержит конкретное имя → улучшать только этот навык
- Если `$ARGUMENTS` равно "all" или пусто → улучшать все установленные навыки

#### Шаг 0.2: Загрузка контекста

**СНАЧАЛА:** Прочитать `.kodla/config.yaml` если существует для разрешения:
- **Пути:** `paths.description`, `paths.architecture`, `paths.rules_file`, `paths.rules`, `paths.patches`, `paths.evolutions`
- **Язык:** `language.ui` для сообщений и `language.artifacts` для генерируемых отчётов
- **Иерархия правил:** `rules.base` и любые именованные `rules.<area>`

Если config.yaml не существует, использовать значения по умолчанию:
- DESCRIPTION.md: `.kodla/DESCRIPTION.md`
- ARCHITECTURE.md: `.kodla/ARCHITECTURE.md`
- RULES.md: `.kodla/RULES.md`
- rules/: `.kodla/rules/`
- patches/: `.kodla/patches/`
- evolutions/: `.kodla/evolutions/`
- Язык: `ru` (русский)

**Примечание:** `.kodla/skill-context/` остаётся фиксированным внутренним путём kodla. Расположение патчей и логов эволюций конфигурируется через `paths.patches` и `paths.evolutions`.

**ЗАТЕМ:** Прочитать `.kodla/DESCRIPTION.md` (путь из конфига) для понимания:
- Технологического стека
- Архитектуры
- Конвенций

**Также прочитать `.kodla/ARCHITECTURE.md`** (путь из конфига) и настроенную иерархию правил при наличии. Этот контекст информирует анализ конвенций и выявление пробелов, но не меняет принадлежности артефактов.

**Прочитать skill-context файлы для целевых навыков:**

- При улучшении **конкретного навыка** (например, `/kodla-evolve plan`) → читать только:
  1. `.kodla/skill-context/kodla-plan/SKILL.md` (контекст целевого навыка)
  2. `.kodla/skill-context/kodla-evolve/SKILL.md` (собственный контекст evolve, если существует
     **и** целевой навык — не сам `kodla-evolve`)
- При улучшении **всех навыков** (`/kodla-evolve` или `/kodla-evolve all`) → читать все контекстные файлы:
  `Glob: .kodla/skill-context/*/SKILL.md` (уже включает собственный контекст evolve — НЕ читать отдельно)

Это ранее накопленные проектно-специфичные правила встроенных навыков.
Держать в памяти — они влияют на анализ пробелов в Шаге 5.

Правила skill-context — **переопределения уровня проекта**: когда они конфликтуют с базовым SKILL.md целевого навыка, skill-context побеждает (тот же принцип что и вложенные CLAUDE.md файлы).

**Как применять собственные правила skill-context evolve (`kodla-evolve`):**
- Воспринимать как **переопределения уровня проекта** для общих инструкций этого навыка
- Когда правило skill-context конфликтует с общим правилом этого SKILL.md — **побеждает skill-context** (более специфичный контекст имеет приоритет)
- При отсутствии конфликта применять оба: общие правила из SKILL.md + проектные из skill-context
- НЕ игнорировать правила skill-context даже если они кажутся противоречащими настройкам по умолчанию
- **КРИТИЧНО:** правила skill-context применяются ко ВСЕМ выходным данным этого навыка — включая отчёт эволюции, предложенные улучшения, правки skill-context файлов и анализ устаревших правил.

**Проверка:** после генерации любого выходного артефакта проверить его на соответствие всем правилам skill-context. При нарушении — исправить до показа пользователю.

### Шаг 1: Сбор данных

**1.1: Инкрементальное чтение патчей (по курсору)**

```
Glob: <директория патчей>/*.md
```

Файл курсора:

```
<директория эволюций>/patch-cursor.json
```

Рекомендуемая структура:

```json
{
  "last_processed_patch": "YYYY-MM-DD-HH.mm.md",
  "updated_at": "YYYY-MM-DD HH:mm"
}
```

Правила обработки:

1. Получить список патчей и отсортировать по имени файла по возрастанию (формат временной метки совместим с лексикографической сортировкой).
2. Если файл курсора не существует → первый запуск: читать все патчи.
3. Если файл курсора существует и указанный патч присутствует → читать только патчи с именем `>` `last_processed_patch`.
4. Если файл курсора существует, но указанный патч отсутствует (удалён/переименован) → выдать `WARN [evolve]` и выполнить полное пересканирование.
5. Исторические правки/удаления патчей старше курсора без сохранённого базового состояния (снэпшота) надёжно не обнаружить. НЕ выдавать это предупреждение по умолчанию.
6. Выдавать `WARN [evolve]` об исторических расхождениях только при наличии надёжного базового состояния и фактически обнаруженном расхождении.
7. Процедура полного пересканирования: удалить `<директория эволюций>/patch-cursor.json`, затем запустить `/kodla-evolve` заново.
8. **Не обновлять курсор в Шаге 1.1.** Курсор обновляется только после успешного применения изменений и записи лога в Шаге 7.3.

**Окно перекрытия (защита от пропуска):**

LLM могут пропустить точки предотвращения при однократном проходе. Для снижения риска "постоянного пропуска" патча при инкрементальном режиме:

9. При инкрементальном режиме (курсор существует и указанный патч присутствует), ТАКЖЕ читать 5 новейших патчей по имени файла (хвост-5 отсортированного списка), затем дедуплицировать по имени файла.
10. Отслеживать отдельно в рабочих заметках:
    - "Новые патчи" = патчи с именем `>` `last_processed_patch`
    - "Патчи перекрытия" = хвост-5 патчей
    - "Обработанные патчи" = объединение(Новые, Перекрытие)
11. Обновление курсора в Шаге 7.3 ДОЛЖНО основываться только на "Новых патчах" (курсор не двигать когда обработаны только патчи перекрытия).

Читать каждый патч. Для каждого извлекать:
- **Категории проблем** (null-проверка, async, валидация, типы, API, БД, и т.д.)
- **Паттерны корневых причин** (какие классы ошибок допущены)
- **Точки предотвращения** — каждое независимое применимое правило из раздела Предотвращение/Решение.
  Один патч часто содержит **несколько независимых точек предотвращения для разных навыков**.
  Извлекать КАЖДУЮ отдельно с указанием целевых навыков. НЕ рассматривать патч как единое целое.
- **Теги**

**Построить Реестр точек предотвращения** — плоский список ВСЕХ извлечённых точек по обработанному набору патчей. Это главный вход для анализа пробелов в Шаге 5.

```
| # | Патч | Точка предотвращения (конкретное действие) | Целевые навыки |
|---|------|--------------------------------------------|----------------|
| 1 | <файл-патча> | <конкретное действие для применения> | <навык-1> |
| 2 | <файл-патча> | <другое действие из того же патча> | <навык-1>, <навык-2> |
| 3 | <другой-патч> | <действие> | <навык-3> |
```

**КРИТИЧНО:** Патч с 5 точками предотвращения даёт 5 строк, а не 1.
Если точка предотвращения нацелена на 2 навыка, она появляется один раз, но с обоими навыками —
и КАЖДЫЙ навык проверяется независимо в Шаге 5.

При инкрементальном запуске реестр отражает обработанный набор патчей (новые + перекрытие). Для полного исторического пересчёта выполнить полное пересканирование.

**1.2: Агрегация паттернов**

Сгруппировать патчи по тегам и категориям. Выявить:
- **Повторяющиеся проблемы** — тот же тег встречается 3+ раза? Это системная проблема
- **Ловушки стека** — проблемы связанные со стеком (например, React ре-рендеры, Laravel N+1)
- **Отсутствующие защиты** — какие проверки/паттерны могли бы предотвратить эти баги

**1.3: Чтение конвенций кодовой базы**

Сканировать проект на паттерны:
- Конфиги линтеров (`.eslintrc`, `phpstan.neon`, `ruff.toml`, и т.д.)
- Существующие тестовые паттерны (структура тестовых файлов, используемые утверждения)
- Паттерны обработки ошибок (стиль try/catch, типы ошибок)
- Паттерны логирования (используемый логгер, формат, уровни)
- Конвенции импортов, структура файлов

**При улучшении конкретного навыка** фокусировать сканирование конвенций на областях, релевантных этому навыку
(например, для `/kodla-plan` — структура файлов и нейминг; для `/kodla-implement-plan` — обработка ошибок и тестирование).

### Шаг 2: Чтение целевых навыков

**Читать ТОЛЬКО базовые SKILL.md файлы целевых навыков — не все навыки.**

- При улучшении **конкретного навыка** (например, `/kodla-evolve plan`) → читать только один:
  `Read: {{skills_dir}}/kodla-plan/SKILL.md` (или `skills/kodla-plan/SKILL.md` если не установлен)
- При улучшении **всех навыков** (`/kodla-evolve` или `/kodla-evolve all`) → читать все:
  `Glob: {{skills_dir}}/*/SKILL.md` (или `Glob: skills/*/SKILL.md` если не установлены)

Держать загруженное содержимое SKILL.md в памяти — Шаг 3 нуждается в нём для сравнения (НЕ перечитывать).

### Шаг 3: Проверка устаревших правил в skill-context

**Когда:** Выполнять этот шаг для каждого **целевого** навыка `kodla-*` у которого есть skill-context файл.

**Для каждого правила в `.kodla/skill-context/<имя-навыка>/SKILL.md`:**

**Ограничение области:** Шаг 3 может ТОЛЬКО изменять или удалять skill-context файлы.
Он НИКОГДА не должен предлагать редактировать, удалять или откатывать базовые `skills/kodla-*/` файлы.
Даже если базовый файл содержит ошибки или неполные правила — это вне области ответственности evolve.

1. Использовать базовый `SKILL.md` уже загруженный в Шаге 2 (НЕ перечитывать файл).
2. Сравнить каждое правило skill-context с содержимым базового SKILL.md:

   **Случай A — Базовый файл полностью покрывает правило skill-context (эквивалент или супerset):**
   Базовый SKILL.md теперь содержит правило эквивалентное или БОЛЕЕ полное чем правило skill-context.
   Это включает:
   - Точный эквивалент — то же правило, то же содержание
   - База является superset — база содержит всё что есть в skill-context, плюс больше
   → НЕ удалять автоматически. НЕ спрашивать пользователя пока.
   → Собрать для отчёта в Шаге 4 — включить оба правила и пометить как
     "Полностью покрыто базой — рекомендуется удалить из skill-context".
   Примечание: если пользователь выберет сохранить правило skill-context, это допустимо —
   skill-context имеет приоритет над базой, поэтому сохранение гарантирует применение полной/корректной версии.

   **Случай B — В базовом SKILL.md найдено противоречащее правило:**
   В базовом навыке теперь есть правило напрямую противоречащее правилу skill-context.
   → НЕ удалять автоматически. НЕ спрашивать пользователя пока.
   → Собрать этот конфликт для отчёта в Шаге 4 — включить оба правила и пометить как "Конфликт — требуется решение пользователя".

   **Случай C — Частичное перекрытие (в любом направлении):**
   Базовый SKILL.md и правило skill-context перекрываются, но НИ ОДНО полностью не покрывает другое.
   → НЕ сужать автоматически. Проанализировать зависимы ли части друг от друга
     (порядок, предусловия, поток данных).
   → Собрать это перекрытие для отчёта в Шаге 4 — включить оба правила, анализ и пометить как "Частичное перекрытие — требуется решение пользователя".
   **Предупреждение о приоритете:** skill-context имеет приоритет над базой по той же теме.
   Если пользователь сохранит skill-context как есть, уникальные части базы вероятно будут ПОТЕРЯНЫ.
   Всегда объяснять это последствие в описании вариантов.

   **Случай D — Нет перекрытия:**
   Правило всё ещё уникально для проектного контекста.
   → Оставить как есть, действий не требуется.

### Шаг 4: Представление и разрешение устаревших правил

**Пропустить этот шаг** если в Шаге 3 не найдено правил случаев A/B/C.

Представить все выявленные устаревшие правила используя формат отчёта об устаревших правилах
(разделы Случай A/B/C со сравнением базы и skill-context).

**ВАЖНО: Все решения здесь затрагивают ТОЛЬКО skill-context файлы.**
Никогда не предлагать редактировать, удалять или откатывать базовые `skills/kodla-*/` файлы —
они вне области ответственности evolve.

#### Формат отчёта об устаревших правилах

Для каждого устаревшего правила представить:

##### /kodla-plan — Полностью покрыто: [Название правила]
- **Базовый SKILL.md говорит:** [текст базового правила]
- **Skill-context говорит:** [текст проектного правила]
- **Требуется решение:** Оставить в skill-context (имеет приоритет над базой — гарантирует применение полной версии) / Удалить из skill-context (довериться базе) / Переписать правило skill-context

##### /kodla-plan — Конфликт: [Название правила]
- **Базовый SKILL.md говорит:** [текст базового правила]
- **Skill-context говорит:** [текст проектного правила]
- **Требуется решение:** Оставить правило skill-context (имеет приоритет — базовая версия будет игнорироваться) / Удалить правило skill-context (довериться базе) / Переписать правило skill-context

##### /kodla-implement-plan — Частичное перекрытие: [Название правила]
- **Базовый SKILL.md говорит:** [текст базового правила]
- **Skill-context говорит:** [текст проектного правила]
- **Анализ:** [объяснить перекрытие и зависимы ли части или независимы]
- **Требуется решение:** Переписать skill-context включив обе уникальные части (рекомендуется когда части последовательны) / Оставить skill-context как есть (ВНИМАНИЕ: уникальные части базы будут потеряны — skill-context имеет приоритет) / Сузить skill-context до непокрытой части / Удалить из skill-context (довериться базе — уникальные части skill-context будут потеряны)

#### Сбор решений

Использовать `AskUserQuestion` для сбора решений по устаревшим правилам. Обрабатывать пакетами
до 3 решений на вызов `AskUserQuestion`:

- Представить первый пакет (до 3 устаревших правил) → `AskUserQuestion`
- Получить ответы → применить решения
- Если остались ещё устаревшие правила → представить следующий пакет → `AskUserQuestion`
- Повторять пока все устаревшие правила не разрешены

**НЕ переходить к Шагу 5 пока все решения по устаревшим правилам не собраны
и не применены.** Это определяет фактическое состояние skill-context для анализа пробелов.

### Шаг 5: Анализ пробелов

**Перед анализом пробелов:** повторно прочитать skill-context файлы для целевых навыков которые
были изменены в Шаге 4 (удаление/переписывание устаревших правил). НЕ использовать версию загруженную
в Шаге 0.2 — она устарела после изменений Шага 4.

Для каждого навыка рассматривать базовый SKILL.md И его **актуальный** skill-context файл
(после применения решений из Шага 4).
Пробел существует только если НИ ОДИН источник его не покрывает.

Для каждого навыка выявить что отсутствует на основе собранных данных:

**5.1: Пробелы из патчей (исчерпывающая проверка точек предотвращения)**

**КРИТИЧНО: Проверять каждую точку предотвращения × каждый целевой навык независимо.**

Итерировать по Реестру точек предотвращения построенному в Шаге 1.1. Для каждой строки:
1. Для КАЖДОГО целевого навыка указанного в строке:
   - Проверить покрывает ли базовый SKILL.md это **конкретное** действие предотвращения
   - Проверить есть ли в skill-context правило покрывающее это **конкретное** действие предотвращения
2. Точка предотвращения считается "покрытой" для навыка ТОЛЬКО когда есть правило адресующее
   **конкретное описанное действие** — а не просто когда имя файла патча встречается в поле Source.
3. Пометить непокрытые пары (точка_предотвращения, навык) как пробелы → они становятся входом для Шага 6.

**Частая ловушка — ссылка на Source ≠ полное покрытие:**
Нахождение `Source: <имя-файла-патча>` в правиле skill-context означает что ОДНО правило выведено
из этого патча. Это **НЕ** означает что ВСЕ точки предотвращения из патча покрыты.
Патч с 5 точками предотвращения может иметь только 1 покрытую. Всегда проверять **содержание**
существующего правила против каждой точки предотвращения индивидуально.

**Верификация:** После завершения сканирования реестра подсчитать: всего точек предотвращения,
покрытых, непокрытых. Если непокрытых > 0 — это пробелы для Шага 6.

Примечание: в инкрементальном режиме счётчики отражают обработанный набор патчей текущего запуска. Для полного исторического пересчёта выполнить полное пересканирование.

**5.2: Пробелы технологического стека**

Сравнить стек проекта с инструкциями навыков:
- Навыки ссылаются на общие паттерны, но проект использует конкретный фреймворк? → Добавить специфичные для фреймворка указания
- Проект использует TypeScript, а навыки показывают примеры на JS? → Обновить примеры
- Проект использует конкретный ORM (Prisma, Eloquent)? → Добавить специфичные для ORM паттерны

**5.3: Пробелы конвенций**

Сравнить конвенции проекта с инструкциями навыков:
- Проект имеет специфичный паттерн обработки ошибок? → Навыки должны его соблюдать
- Проект использует конкретный логгер? → Навыки должны ссылаться на него
- Проект имеет специфичную структуру файлов? → Навыки должны её придерживаться

### Шаг 6: Генерация улучшений

Для каждого найденного пробела создать конкретное улучшение:

**Правила качества улучшений:**
- **Одна точка предотвращения = одно правило.** Один патч может содержать несколько независимых элементов. Каждый становится отдельным правилом — НЕ объединять их в одно расплывчатое резюме.
- **Сохранять конкретные форматы и паттерны** из патчей. Если патч указывает точный формат, синтаксис или шаблон — правило ДОЛЖНО включать его дословно. НЕ перефразировать конкретику в расплывчатые описания.
- Каждое улучшение должно быть прослеживаемым к патчу, конвенции или факту стека
- Никаких общих советов — только проектно-специфичные улучшения
- Улучшения должны быть минимальными и сфокусированными — не переписывать навыки целиком
- Сохранять существующую структуру навыка — добавлять, не заменять

### Шаг 7: Представление и применение

**7.1: Представление улучшений пользователю**

Каждое улучшение ДОЛЖНО явно указывать путь целевого файла.
Использовать следующие метки целей:

- **`skill-context`** → `.kodla/skill-context/<имя-навыка>/SKILL.md`
- **`SKILL.md`** → прямое редактирование собственного `SKILL.md` навыка (только для кастомных/не-kodla навыков)
- **Вложенный файл** → если директория навыка содержит дополнительные файлы (например, `templates/`, `checklists/`),
  указать точный относительный путь внутри директории навыка

Формат:

```
## Отчёт об эволюции навыков

На основе:
- X проанализированных патчей
- Y найденных повторяющихся паттернов
- Z специфичных для стека наблюдений

### Предложенные улучшения

#### /kodla-implement-plan (N правил)
**Цель:** `.kodla/skill-context/kodla-implement-plan/SKILL.md`

1. **Добавить защиту от null**
   - **Источник:** patch-2026-02-10.md, patch-2026-02-12.md (5 патчей связаны с null-ссылками)
   - **Почему:** Повторяющиеся ошибки null-ссылок в опциональных связях БД
   - **Правило:** "Проверять опциональные/nullable поля перед обращением к вложенным свойствам"

2. **Добавить паттерн async/await**
   - **Источник:** patch-2026-02-11.md (3 патча с необработанными промисами)
   - **Почему:** Необработанные rejection промисов в API слое
   - **Правило:** "Всегда использовать try/catch с async/await"

#### /kodla-plan (N правил)
**Цель:** `.kodla/skill-context/kodla-plan/SKILL.md`

1. **Добавить предупреждение про Eloquent**
   - **Источник:** patch-2026-02-13.md (2 патча из-за неверных Eloquent запросов)
   - **Почему:** Молчаливая потеря данных из-за неверных методов Eloquent
   - **Правило:** "Указывать в плане использование eager loading для N+1 проблем"

#### /my-custom-skill (N правил)
**Цель:** `skills/my-custom-skill/SKILL.md` (прямое редактирование — кастомный навык)

1. **Добавить паттерн**
   - **Источник:** конвенция кодовой базы
   - **Почему:** Отсутствует защита в Шаге 2
   - **Правило:** "..."
```

**После представления полного отчёта использовать `AskUserQuestion` для сбора решений:**

По улучшениям — спросить:
- Да, применить все улучшения
- Дай выбрать
- Нет, только сохранить отчёт (изменения не применять)

**На основе выбора:**
- "Да, применить все улучшения" → перейти к 7.2 со всеми улучшениями
- "Дай выбрать" → представлять улучшения пакетами до 4 штук
  на вызов `AskUserQuestion` (тот же подход что в Шаге 4). Для каждого
  улучшения: Применить / Пропустить. Продолжать пока все улучшения не разрешены.
  Затем перейти к 7.2 только с одобренными улучшениями.
- "Нет, только сохранить отчёт" → изменения не применять, **СТОП**

**НЕ применять никаких изменений пока пользователь не ответил.**

**7.2: Применение одобренных улучшений**

Для каждого одобренного улучшения определить цель:

**Если навык является встроенным `kodla-*` навыком** (его SKILL.md находится внутри директории `skills/` пакета):

1. Создать директорию при необходимости:
   `mkdir -p .kodla/skill-context/<имя-навыка>`
2. Если `.kodla/skill-context/<имя-навыка>/SKILL.md` не существует — создать его с шаблоном заголовка
3. Если существует — сначала прочитать, затем для каждого улучшения решить:
   - **Обновить существующее правило** — когда правило по той же теме уже существует (например, правило null-проверки есть из 3 патчей, и пришло 5 новых → усилить существующее правило, обновить список Source, скорректировать серьёзность/формулировку на основе новых свидетельств)
   - **Добавить новое правило** — когда ни одно существующее правило не покрывает эту тему
   - **Объединить правила** — когда несколько узких правил можно объединить в одно более широкое
4. Обновить строки `> Last updated:` и `> Based on:` в заголовке
5. **НИКОГДА не редактировать файлы внутри директории `skills/kodla-*/`** — все файлы там управляются kodla и БУДУТ перезаписаны при обновлении. Все улучшения идут только в skill-context.
6. После применения всех изменений (включая удаление устаревших правил), если skill-context файл не содержит правил (остался только заголовок) — удалить файл и директорию:
   `rm .kodla/skill-context/<имя-навыка>/SKILL.md`
   `rmdir .kodla/skill-context/<имя-навыка>` (только если пустая)
7. Обновить счётчик `> Based on:` и `> Last updated:` в skill-context файлах которые были затронуты только удалением устаревших правил (Шаг 4) но НЕ получили новых улучшений (те уже обновлены в пункте 4).

**Если навык является кастомным/проектным** (не `kodla-*`):
1. Редактировать SKILL.md навыка напрямую (поведение без изменений)

**Шаблон файла skill-context:**

**ВАЖНО: Все skill-context файлы ДОЛЖНЫ быть написаны на английском**, независимо от языка пользователя или языка патчей/RULES.md. Правила skill-context потребляются AI-агентами — английский обеспечивает консистентную интерпретацию во всех навыках и сессиях.

```
# Project Rules for /<имя-навыка>

> Auto-generated by `/kodla-evolve`. Do not edit manually.
> Last updated: YYYY-MM-DD HH:mm
> Based on: N analyzed patches

## Rules

### [Rule Name]
**Source**: [patch filenames or "codebase convention"]
**Rule**: [Specific, actionable instruction in English]
```

**7.3: Сохранение лога эволюции**

Создать `<директория эволюций>/YYYY-MM-DD-HH.mm.md`:

```bash
mkdir -p <директория эволюций>
```

После сохранения лога обновить состояние курсора:

Определения:
- "Новые обработанные патчи" = патчи с именем `>` `last_processed_patch`.
  - Если курсора нет (первый запуск): "Новые патчи" = весь список патчей.
  - Патчи перекрытия НЕ считаются "Новыми патчами".
- "Применённые улучшения" = хотя бы одно одобренное улучшение записано на диск (обновлён skill-context и/или отредактирован SKILL.md кастомного навыка).

Правила обновления курсора:

1. Если новых патчей не обработано — курсор не менять.
2. Если новые патчи обработаны:
   - Если улучшения применены: продвинуть курсор до имени самого нового "Нового патча".
   - Если улучшения не применены (например, пользователь выбрал "Нет, только сохранить отчёт" или пропустил все):
     - По умолчанию НЕ двигать курсор.
     - Спросить пользователя — двигать ли курсор.
       - Рекомендуется: оставить курсор без изменений для возможности повторных запусков (LLM может пропустить точки предотвращения).
       - Если пользователь явно выбрал продвинуть — записать курсор как обычно.
3. Если выполнение прерывается до финализации изменений — курсор не двигать.

```markdown
# Эволюция: YYYY-MM-DD HH:mm

## Сводка данных

- Повторяющиеся паттерны: [список]

### [имя-навыка] → SKILL.md (кастомный навык)
- [описание изменения] ← вызвано: [стек / конвенция]
  **Файл:** `skills/[имя-навыка]/SKILL.md`

- [паттерн]: [частота] вхождений
- [паттерн]: [частота] вхождений
```

### Шаг 8: Рекомендации после завершения

```
## Эволюция завершена

Улучшено навыков: X
Применено улучшений: Y

### Рекомендации

1. **Запусти `/kodla-plan`** для новой задачи — правила skill-context уже активны
2. **Следующая эволюция** — запусти `/kodla-evolve` снова после 5-10 новых исправлений
3. **Рассмотри новый навык** — если паттерн X продолжает повторяться, создай специализированный навык:
   `/kodla-skill-generator <имя-навыка>`
```

После завершения эволюции предложить `/clear` или `/compact` — контекст тяжёлый после анализа патчей и обработки навыков.

## Принадлежность артефактов

- Основная принадлежность: `.kodla/skill-context/*`, `<директория эволюций>/*.md` и `<директория эволюций>/patch-cursor.json`.
- Конфиг используется частично: `config.yaml` разрешает пути к описанию, правилам, патчам и логам эволюций, но skill-context остаётся фиксированным внутренним путём kodla.
- Контекст только для чтения: дорожная карта, правила, исследования и артефакты планов — если пользователь явно не запросил иное.

## Правила

1. **Прослеживаемость** — каждое улучшение должно ссылаться на патч, конвенцию или факт стека
2. **Минимальность** — добавлять правила в skill-context, не переписывать базовые навыки
3. **Обратимость** — пользователь подтверждает перед применением изменений
4. **Накопительность** — каждая эволюция строится на предыдущих
5. **Без галлюцинаций** — предлагать только улучшения подкреплённые свидетельствами
6. **Сохранение структуры** — не менять рабочий процесс базового навыка, только обогащать через skill-context
7. **Только skill-context** — все улучшения встроенных `kodla-*` навыков идут в `.kodla/skill-context/`, никогда в `skills/kodla-*/`. **НИКОГДА не редактировать файлы внутри `skills/kodla-*/`** — они перезаписываются при обновлении. Без исключений.
8. **Только по-английски** — все skill-context файлы должны быть написаны на английском, независимо от языка пользователя
9. **Без общих советов** — "пиши чистый код" — не улучшение; только проектно-специфичные усиления
10. **Без новых навыков** — предложить `/kodla-skill-generator` вместо этого
11. **Без потери покрытия** — не удалять правила если они не устарели (Шаги 3-4).
    Объединение в Шаге 7 (комбинирование узких правил в одно более широкое) допустимо при условии
    что все точки предотвращения сохранены в объединённом правиле.
12. **Только установленные** — не улучшать навыки не установленные в проекте
13. **Граница принадлежности** — эта команда владеет `<директория эволюций>/*.md`, `<директория эволюций>/patch-cursor.json` и `.kodla/skill-context/*`; дорожная карта/правила/исследования/артефакты планов — только для чтения, если явно не запрошено иное

## Пример

```
/kodla-evolve implement-plan

→ Найдено 6/10 патчей с тегом #null-check
→ Улучшение для /kodla-implement-plan (2 правила):
  Цель: .kodla/skill-context/kodla-implement-plan/SKILL.md
  1. "ПРИОРИТЕТНАЯ ПРОВЕРКА: Искать опциональные/nullable поля обращение к которым
      происходит без null-защит. Это источник #1 багов в этом проекте."
  2. "При исправлении ошибок nullable-связей проверять ВСЕ использования этой
      связи в том же файле — тот же баг часто повторяется рядом."
```
