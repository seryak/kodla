# Improve — Улучшение плана реализации

Вторая итерация планирования: углублённый анализ существующего плана, поиск пропущенных задач, исправление порядка, улучшение описаний.

## Базовая идея

```
существующий план + глубокий анализ кодовой базы + (опционально) инструкции пользователя
    ↓
найти пробелы, пропущенные граничные случаи, неверные предположения
    ↓
улучшенный план с более чёткими задачами и правильным порядком
```

## Рабочий процесс

### Шаг 0. Найти план

**Разбор `$ARGUMENTS`:**

- `--list` → показать доступные планы и **СТОП**
- `@<path>` → использовать указанный файл (наивысший приоритет)
- Остаток текста → инструкции по улучшению от пользователя

**Определение tasar-режима:**

```bash
test -d "tasar" || test -d ".tasar"
```

Если одна из папок (`tasar/` или `.tasar/`) существует — **tasar-режим**, иначе — **kodla-режим**.

**Поиск плана (без явного `@<path>`):**

В **tasar-режиме**:
```bash
# Проверить обе возможные папки:
find tasar .tasar -name "tasks.md" -not -path "*/archive/*" 2>/dev/null
```
Взять последний изменённый файл. Если несколько — спросить через AskUserQuestion.

В **kodla-режиме**:
```bash
ls -1 .kodla/plans/*.md 2>/dev/null
```
Если один файл — использовать. Если несколько — спросить. Если ни одного — сообщить и СТОП.

**Если план не найден:**
```
Активный план не найден.

Создай план сначала:
- /kodla-plan <описание>       — для проекта без tasar
- /tasar-propose <описание>    — для проекта с tasar
```
→ СТОП.

### Шаг 0.1: Режим --list

Если `$ARGUMENTS` содержит `--list` — вывести список планов и СТОП.

В tasar-режиме:
```bash
find tasar .tasar -name "tasks.md" -not -path "*/archive/*" 2>/dev/null
```

В kodla-режиме:
```bash
ls -1 .kodla/plans/*.md 2>/dev/null
```

Для каждого плана — прочитать и посчитать задачи (`- [ ]` и `- [x]`). Вывести:

```
Доступные планы:

  tasar/changes/my-feature/tasks.md    — 4/6 задач выполнено
  tasar/changes/other-change/tasks.md  — 0/3 задач выполнено

Использование:
  /kodla-improve @tasar/changes/my-feature/tasks.md
  /kodla-improve добавить обработку ошибок
```

→ СТОП.

### Шаг 1. Загрузить контекст

**Конфиг и skill-context:**

Прочитай `.kodla/config.yaml` если существует.
Разреши пути, если они указаны:
- `paths.description` — по умолчанию `.kodla/DESCRIPTION.md`
- `paths.architecture` — по умолчанию `.kodla/ARCHITECTURE.md`
- `paths.research` — по умолчанию `.kodla/RESEARCH.md`
- `paths.patches` — по умолчанию `.kodla/patches/`
- `paths.fix_plan` — по умолчанию `.kodla/FIX_PLAN.md`
- `paths.rules` / `rules.base` — по умолчанию `.kodla/rules/`

Прочитай `.kodla/skill-context/kodla-improve/SKILL.md` если существует — это проектно-специфичные правила накопленные `/kodla-evolve`. Они имеют **приоритет** над общими инструкциями этого навыка.
Правила skill-context применяются к отчёту улучшения и к любым изменениям плана.

**Файл плана:**

Прочитай найденный файл плана полностью. Пойми:
- Область и цели фичи/задачи
- Текущие задачи (описания, порядок)
- Настройки (тесты да/нет)
- Какие задачи уже выполнены (`- [x]`)

**Контекст проекта:**

Прочитай `.kodla/DESCRIPTION.md` если существует.
Прочитай `.kodla/ARCHITECTURE.md`, `.kodla/rules/base.md`, именованные правила из конфига и `.kodla/RESEARCH.md` если существуют.

**Патчи как ограниченный fallback:**

Если `.kodla/skill-context/kodla-improve/SKILL.md` отсутствует, но директория патчей существует:
- Найди `*.md` в `paths.patches`
- Отсортируй по имени и прочитай только последние 10
- Используй только повторяющиеся Root Cause / Prevention паттерны, которые улучшают качество планирования

Если skill-context существует — не читай все патчи по умолчанию; можно прочитать небольшой целевой набор только когда план явно связан с известным повторяющимся багом.

Если план находится в `tasar/changes/<name>/tasks.md` или `.tasar/changes/<name>/tasks.md` — прочитай также:
- `<tasar-dir>/changes/<name>/proposal.md` (что и зачем)
- `<tasar-dir>/changes/<name>/design.md` (как)
- `<tasar-dir>/changes/<name>/specs/<name>.md` если существует (требования)

### Шаг 2. Глубокий анализ кодовой базы

Запусти 2-3 Explore-агента параллельно:

```
Агент 1 — трассировка файлов:
Agent(subagent_type: Explore, prompt:
  "Найди и прочитай файлы упомянутые в задачах плана: [список файлов из задач].
   Выдай: реальное состояние каждого файла, что уже реализовано, что отсутствует.
   Уровень детализации: medium.")

Агент 2 — интеграционные точки:
Agent(subagent_type: Explore, prompt:
  "Найди в проекте интеграционные точки которые могут затронуть [тема плана]:
   - связанные модули/классы/сервисы
   - конфиги, миграции, роуты которые нужно обновить
   - существующие паттерны которые план должен использовать
   Уровень детализации: medium.")
```

Третий агент — при необходимости для граничных случаев или паттернов обработки ошибок.

### Шаг 3. Найти улучшения

Сравни план с тем что нашёл анализ. Категории проблем:

**3.1 Пропущенные задачи**
- Файлы которые нужно изменить но их нет в плане
- Граничные случаи без покрытия
- Обязательные шаги (миграции, конфиги, валидация)

**3.2 Расплывчатые описания**
- Нет пути к файлу
- Нет конкретики (что именно изменить, какой метод)
- Можно уточнить на основе анализа кода
- Нет требований к логированию, если в настройках плана выбран подробный или стандартный режим
- Нет деталей обработки ошибок, валидации или граничных случаев

**3.3 Неверный порядок**
- Задача X зависит от Y но идёт раньше
- Независимые задачи которые могут выполняться параллельно

**3.4 Дублирующие задачи**
- Два пункта делают одно и то же
- Задача дублирует уже существующую в коде функциональность

**3.5 Задачи вне области видимости**
- Задача явно не связана с целью плана
- Задача слишком крупная и должна быть разделена
- Задача слишком мелкая и создаёт шум без самостоятельного результата

**3.6 Несоответствие контексту проекта**
- План нарушает `.kodla/ARCHITECTURE.md` или `.kodla/rules/*`
- План не учитывает активное резюме из `.kodla/RESEARCH.md`
- План не учитывает требования tasar proposal/design/specs
- План содержит документационный checkpoint, но не направляет его к `/kodla-docs`

**3.7 Инструкции пользователя**
Если в `$ARGUMENTS` есть текст (кроме `--list` и `@<path>`) — применить его как дополнительный критерий анализа.

### Шаг 4. Показать отчёт

```
## Отчёт по улучшению плана

**План:** <path>
**Задач проанализировано:** N

### Находки

#### Пропущенные задачи (N)
1. **[Описание новой задачи]**
   Причина: [почему нужна]
   Место: после задачи «...»

#### Улучшения задач (N)
1. **«<текущее описание>»**
   Проблема: [что не так]
   Исправление: [новое описание]

#### Исправления порядка (N)
1. «Задача A» должна выполняться после «Задача B»
   Причина: [зависимость]

#### Удалить (N)
1. **«<описание>»**
   Причина: [дублирует / вне области / уже реализовано]

#### Итог
- Пропущенных задач: N
- Задач для улучшения: N
- Исправлений порядка: N
- Удалить: N
```

Затем AskUserQuestion: Применить улучшения?
- **Применить все** — применить все предложенные изменения
- **Выбрать по одному** — пройтись по каждому улучшению отдельно
- **Оставить как есть** — выйти без изменений

**Если улучшений не найдено:**

```
## Анализ завершён

План выглядит хорошо! Существенных пробелов не обнаружено.

**План:** <path>
**Задач:** N

Можно приступать к реализации.
```

Затем AskUserQuestion: Что делаем дальше?
- **Запустить реализацию** — `/kodla-implement-plan @<path>`
- **Ничего не делать** — завершить работу
- **Другое** — уточнить у пользователя или предложить уместное действие на своё усмотрение

Обработка ответа:
- **«Запустить реализацию»** → вызвать `/kodla-implement-plan @<path>`
- **«Ничего не делать»** → СТОП
- **«Другое»** → уточнить у пользователя что нужно, либо — если намерение понятно из контекста — предложить наиболее уместное действие

### Шаг 5. Применить улучшения

Изменить файл плана через Edit/Write:

- Добавить пропущенные задачи в нужное место (с `- [ ]`)
- Обновить расплывчатые описания
- Переупорядочить задачи (исправить зависимости)
- Удалить дублирующие задачи
- **Никогда не трогать `- [x]` выполненные задачи**
- После изменений проверить план против skill-context, архитектуры и правил проекта.

После применения прочитай файл плана и подсчитай задачи (`- [ ]` и `- [x]`). Выведи:

```
## План улучшен

**Изменения:**
- Добавлено задач: N
- Улучшено описаний: N
- Исправлено порядка: N
- Удалено: N

**Итого:** X/Y задач выполнено
```

Затем AskUserQuestion: Что делаем дальше?
- **Запустить реализацию** — `/kodla-implement-plan @<path>`
- **Ничего не делать** — завершить работу
- **Другое** — уточнить у пользователя или предложить уместное действие на своё усмотрение

Обработка ответа:
- **«Запустить реализацию»** → вызвать `/kodla-implement-plan @<path>`
- **«Ничего не делать»** → СТОП
- **«Другое»** → уточнить у пользователя что нужно, либо — если намерение понятно из контекста — предложить наиболее уместное действие

## Важные правила

1. **Не переписывать с нуля** — только точечные улучшения существующего плана
2. **Не трогать выполненные задачи** — `- [x]` неприкосновенны
3. **Каждое изменение обосновано** — анализом кода или инструкцией пользователя
4. **Уважать настройки плана** — если тесты «нет», не добавлять тестовые задачи
5. **Без золочения** — только то что реально нужно для области видимости
6. **Подтверждение пользователя** — не применять изменения без AskUserQuestion
7. **Правила skill-context в приоритете** — переопределяют эти инструкции
8. **Русский язык** — все тексты, заголовки и вопросы на русском
9. **Папки tasar:** проверять оба варианта — `tasar/` и `.tasar/`
10. **Выбор следующего шага через AskUserQuestion** — в обоих финальных блоках («улучшений не найдено» и «план улучшен») предлагай пользователю выбор: запустить `/kodla-implement-plan @<path>`, ничего не делать, или другое — не переходи к реализации без явного выбора пользователя
11. **Маршрут реализации** — всегда рекомендуй только `/kodla-implement-plan @<path>`; не предлагай `/tasar-apply`, даже для планов в `tasar/` или `.tasar/`. Это ограничение не отменяет явно выраженную пользователем команду запустить `/tasar-apply`.
