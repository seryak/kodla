# Implement Plan — Выполнение плана реализации

Выполняет задачи из плана последовательно, отслеживает прогресс и позволяет продолжить работу в новой сессии.

## Рабочий процесс

### Шаг 0: Определение состояния

**Читать `.kodla/config.yaml`** если существует, для извлечения:
- `paths.plans` — директория планов (по умолчанию: `.kodla/plans/`)
- `paths.description` — описание проекта (по умолчанию: `.kodla/DESCRIPTION.md`)
- `paths.architecture` — архитектура проекта (по умолчанию: `.kodla/ARCHITECTURE.md`)
- `paths.roadmap` — дорожная карта (по умолчанию: `.kodla/ROADMAP.md`)
- `paths.research` — исследования (по умолчанию: `.kodla/RESEARCH.md`)
- `paths.fix_plan` — план фикса (по умолчанию: `.kodla/FIX_PLAN.md`)
- `paths.patches` — патчи опыта (по умолчанию: `.kodla/patches/`)
- `paths.rules` — директория правил (по умолчанию: `.kodla/rules/`)
- `rules.base` и любые `rules.<area>` — иерархия правил
- `language.ui` — язык взаимодействия (по умолчанию: `ru`)
- `language.artifacts` — язык обновляемых артефактов (по умолчанию: `ru`)

**Разобрать аргументы:**
- `--list` → показать список доступных планов и СТОП
- `@<путь>` → использовать указанный файл плана (высший приоритет)
- `<число>` → начать с указанной задачи
- `status` → только показать прогресс, не выполнять

---

### Шаг 0.list: Режим `--list`

Если `$ARGUMENTS` содержит `--list` — показать список доступных планов и СТОП.

```
1. Найти tasar/changes/*/tasks.md (не в archive/) если tasar/ существует
2. Найти .tasar/changes/*/tasks.md (не в archive/) если .tasar/ существует
3. Найти *.md в paths.plans
4. Для каждого плана — вывести путь и количество задач (выполнено/всего)
5. СТОП — не выполнять задачи
```

Пример вывода:
```
Доступные планы:

tasar/changes/add-user-auth/tasks.md       3/8 задач выполнено
.kodla/plans/refactor-api.md               0/5 задач выполнено

Используй /kodla:implement-plan @<путь> для выбора конкретного плана.
```

---

### Шаг 0.0: Возобновление после перерыва

Если пользователь возобновляет работу после перерыва или потери контекста — прочитать файл плана и сверить чекбоксы с состоянием TaskList:

- Если код задачи уже реализован, но задача не отмечена выполненной → `TaskUpdate(completed)` и обновить чекбокс
- Если задача отмечена выполненной, но код не найден → вернуть в `pending` и обсудить с пользователем

---

### Шаг 0.1: Загрузка контекста проекта

**Читать `.kodla/DESCRIPTION.md`** (или `paths.description` из конфига) если существует:
- Tech-стек (язык, фреймворк, база данных, ORM)
- Архитектура проекта и соглашения
- Нефункциональные требования

**Читать `.kodla/ARCHITECTURE.md`** (или `paths.architecture`) если существует:
- Архитектурный паттерн
- Структура папок и границы модулей
- Правила зависимостей и коммуникации между слоями

**Читать `.kodla/rules/base.md`** если существует — соглашения по именованию, структуре, обработке ошибок.

**Читать иерархию правил**:
1. `rules.base` / `.kodla/rules/base.md`
2. Именованные правила из конфига (`rules.api`, `rules.frontend` и т.д.)
3. Остальные релевантные файлы из `paths.rules`

Более специфичные правила имеют приоритет над общими.

**Читать `.kodla/ROADMAP.md`** и `.kodla/RESEARCH.md` если они существуют и релевантны плану.

**Читать `.kodla/skill-context/kodla-implement-plan/SKILL.md`** если существует — **ОБЯЗАТЕЛЬНО**.

Этот файл содержит проектно-специфичные правила для данного навыка. Правила из skill-context имеют **приоритет** над общими инструкциями этого SKILL.md. Не игнорировать их даже если они противоречат инструкциям ниже.

**Использовать контекст при реализации:**
- Следовать указанному tech-стеку
- Использовать правильные паттерны импортов и соглашений
- Применять обработку ошибок как указано в правилах
- Следовать границам модулей и структуре из `.kodla/ARCHITECTURE.md`
- Учитывать известные решения и ограничения из `.kodla/RESEARCH.md`
- Не нарушать явные roadmap-ограничения, если план к ним привязан

**Патчи как ограниченный fallback:**

Если `.kodla/skill-context/kodla-implement-plan/SKILL.md` отсутствует и директория `paths.patches` существует:
- Найди `*.md` в директории патчей
- Отсортируй имена по возрастанию и прочитай последние 10
- Используй только Root Cause / Prevention паттерны, релевантные текущим задачам

Если skill-context существует — не читай все патчи по умолчанию.

---

### Шаг 0.2: Обнаружение плана

**Если `$ARGUMENTS` содержит `@<путь>`:**
```
1. Извлечь путь после "@"
2. Если файл не существует → сообщить: "Файл плана не найден: <путь>" → СТОП
3. Использовать этот файл как активный план
```

**Если нет явного `@<путь>`, проверить источники по приоритету:**

```
1. Проверить tasar/ или .tasar/:
   - Найти tasar/changes/*/tasks.md (исключить archive/)
   - Найти .tasar/changes/*/tasks.md (исключить archive/)
   - Один активный план → использовать его
   - Несколько планов → показать список и спросить пользователя

2. Иначе — проверить paths.plans (по умолчанию .kodla/plans/):
   - Найти *.md файлы
   - Один файл → использовать
   - Несколько → показать список и спросить пользователя

3. Если plan-файл не найден, но существует `paths.fix_plan` (`.kodla/FIX_PLAN.md`) →
   передать выполнение `/kodla-fix` без аргументов и остановить этот workflow.

4. Не найдено → сообщить:
   "Активный план не найден.
    Создай план через /kodla:plan или /tasar:propose"
   → СТОП
```

**Примечание по tasar:** Активные изменения находятся в `tasar/changes/<name>/`, архивированные — в `tasar/changes/archive/`. При поиске исключать папку `archive/`.

**Прочитать файл плана** для понимания:
- Структуры чеклиста (`- [ ]` / `- [x]`)
- Контекста и зависимостей задач

---

### Шаг 1: Загрузка текущего состояния

```
TaskList → получить все задачи со статусами
```

Найти:
- Задачи `in_progress` — возобновить их первыми
- Следующую `pending` задачу (в порядке списка)

Если указан `status` в аргументах — показать только прогресс и СТОП (не выполнять).

---

### Шаг 2: Отображение прогресса

```
## Прогресс реализации

✅ Выполнено: 3/8 задач
🔄 В работе: Задача #4 — Реализовать сервис поиска
⏳ Ожидает: 4 задачи

Текущая задача: #4 — Реализовать сервис поиска
```

---

### Шаг 3: Выполнение задачи

Для каждой задачи:

**3.1: Получить детали задачи**

```
TaskGet(taskId) → описание, файлы, контекст
```

**3.2: Отметить начало работы**

```
TaskUpdate(taskId, status: "in_progress")
```

**3.3: Реализовать задачу**

- Прочитать соответствующие файлы
- Внести необходимые изменения
- Следовать существующим паттернам кода
- Добавлять логирование согласно настройке плана:
  - `подробное` → вход/выход функций, важные изменения состояния, внешние вызовы и ошибки
  - `стандартное` → ключевые события и ошибки
  - `минимальное` → только WARN/ERROR
- Логирование должно быть настраиваемым, если проект поддерживает `LOG_LEVEL` или аналог
- **НЕТ тестам** (если не включены явно в план)
- **НЕТ отчётам и итоговым документам**

**3.4: Проверить реализацию**

- Убедиться что код компилируется/работает
- Исправить очевидные проблемы

**3.5: Отметить завершение**

```
TaskUpdate(taskId, status: "completed")
```

**3.6: Обновить чекбокс в файле плана — НЕМЕДЛЕННО**

```markdown
# До
- [ ] Задача 1: Создать модель пользователя

# После
- [x] Задача 1: Создать модель пользователя
```

**Это ОБЯЗАТЕЛЬНО** — чекбоксы должны отражать реальный прогресс:
- Использовать инструмент `Edit` для замены `- [ ]` на `- [x]`
- Делать это СРАЗУ после завершения каждой задачи
- Файл плана является источником истины о прогрессе

**3.7: Обновить описание проекта если нужно**

Если в ходе реализации:
- Добавлена новая зависимость/библиотека
- Изменился tech-стек (добавлен Redis, другой ORM и т.д.)
- Добавлена новая интеграция

→ Обновить `.kodla/DESCRIPTION.md` (или `paths.description` из конфига) с фактическими изменениями стека.

**3.8: Обновить AGENTS.md и ARCHITECTURE.md если изменилась структура**

Если в ходе задачи:
- Созданы новые директории или значимые модули
- Добавлены новые entry point файлы
- Изменились границы слоёв или правила зависимостей

→ Обновить `AGENTS.md` (если существует) в секциях структуры проекта и ключевых entry points.
→ Обновить `.kodla/ARCHITECTURE.md` (или `paths.architecture`) только если фактическая архитектура изменилась.
Не переписывай эти файлы при каждой задаче — только когда текущая карта стала неверной.

**3.9: Перейти к следующей задаче**

---

### Шаг 4: Сохранение сессии

Прогресс сохраняется автоматически через TaskUpdate.

После каждой задачи показывать:
```
Прогресс сохранён.
Выполнено: 4/8 задач
Следующая задача: #5 — Добавить пагинацию

Чтобы продолжить позже: /kodla:implement-plan
```

**Для паузы:**
```
Текущий прогресс сохранён.

Выполнено: 4/8 задач
Следующая задача: #5 — Добавить пагинацию

Для продолжения запусти: /kodla:implement-plan
```

---

### Шаг 5: Завершение

Когда все задачи выполнены — выполнить context maintenance и вывести итоговый блок.

**Документационный checkpoint:**
- Если в плане `Документация: обязательная проверка` или `Docs: yes` —
  спросить как документировать результат и предложить `/kodla-docs`.
- Если документация отключена или не задана — вывести `WARN [docs]`, что checkpoint пропущен.

**Roadmap checkpoint:**
- Если `.kodla/ROADMAP.md` существует и план содержит `Roadmap Linkage` с конкретным milestone —
  проверить, соответствует ли выполненная работа milestone.
- Если соответствие очевидно — предложить отметить milestone выполненным.
- Если соответствие неоднозначно — вывести `WARN [roadmap]` и предложить отдельную проверку roadmap.

После этого вывести итоговый блок и предложить выбор следующего шага:

```
## Реализация завершена

Выполнено все 8 задач.

Файл плана: tasar/changes/add-user-auth/tasks.md
Изменённые файлы:
- src/Services/AuthService.php (создан)
- src/Controllers/AuthController.php (создан)
- src/Models/User.php (изменён)
```

После вывода блока — использовать `AskUserQuestion`:

```
AskUserQuestion: Все задачи выполнены. Что делаем дальше?

Варианты:
1. Проверить реализацию — запустить /kodla-check-tasks @<путь к файлу плана>
2. Ничего не делать — завершить работу
3. Другое — уточнить у пользователя или предложить уместное действие на своё усмотрение
```

**Если "Проверить реализацию"** → вызвать `/kodla-check-tasks @<путь к файлу плана>`.
**Если "Ничего не делать"** → завершить работу.
**Если "Другое"** → уточнить у пользователя что нужно, либо — если намерение понятно из контекста (например список изменённых файлов без тестового покрытия) — предложить наиболее уместное действие, включая при необходимости `/kodla-unittest` с явной целью (список изменённых файлов из блока "Изменённые файлы" выше).

## Команды

### Запуск / возобновление

```
/kodla:implement-plan
```

Продолжает с первой незавершённой задачи.

### Список доступных планов

```
/kodla:implement-plan --list
```

Перечисляет планы из tasar/changes/ и .kodla/plans/ и завершается.

### Явное указание файла плана

```
/kodla:implement-plan @tasar/changes/my-feature/tasks.md
/kodla:implement-plan @.kodla/plans/refactor-api.md
```

Использует указанный файл вместо автоопределения.

### Начать с конкретной задачи

```
/kodla:implement-plan 5
```

Начинает с задачи №5 (полезно для повтора или пропуска).

### Только статус

```
/kodla:implement-plan status
```

Показывает прогресс без выполнения.

## Правила выполнения

### ДЕЛАТЬ:

- ✅ Выполнять по одной задаче за раз
- ✅ Отмечать `in_progress` перед началом работы
- ✅ Отмечать `completed` после завершения
- ✅ Следовать существующим соглашениям кода
- ✅ Обновлять чекбокс в файле плана сразу после завершения
- ✅ Остановиться и спросить если задача непонятна

### НЕ ДЕЛАТЬ:

- ❌ Писать тесты (если не указано явно в плане)
- ❌ Создавать отчёты и итоговые документы
- ❌ Добавлять задачи не из плана
- ❌ Пропускать задачи без разрешения пользователя
- ❌ Отмечать незавершённые задачи как выполненные
- ❌ Нарушать архитектурные соглашения из `.kodla/DESCRIPTION.md`

---

## Границы владения артефактами

- **Основное владение:** статус задач и чекбоксы в файле плана
- **Разрешено обновлять:** `.kodla/DESCRIPTION.md` при изменении стека, `AGENTS.md` и `.kodla/ARCHITECTURE.md` при фактическом изменении структуры, `.kodla/ROADMAP.md` только для очевидного закрытия milestone после подтверждения
- **Только чтение:** `.kodla/rules/`, `.kodla/skill-context/`, `.kodla/RESEARCH.md` (применять, не изменять)
