# Kodla Rules — Правила проекта

Добавляет короткие, действенные правила и соглашения для текущего проекта. Правила сохраняются в настроенный артефакт RULES.md (по умолчанию: `.kodla/RULES.md`) и автоматически загружаются при выполнении задач.

## Иерархия правил

Kodla поддерживает трёхуровневую иерархию правил:

1. **RULES.md** — Аксиомы (универсальные правила проекта)
   - Управляется этим навыком (`/kodla-rules`)
   - Короткий плоский список жёстких требований
   - Загружается всеми навыками

2. **rules/base.md** — Базовые соглашения проекта
   - Создаётся `/kodla-init` при инициализации проекта
   - Конвенции именования, границы модулей, паттерны обработки ошибок
   - Автоматически определяется из анализа кодовой базы

3. **rules.<area>** — Область-специфичные соглашения
   - Создаётся этим навыком (Режим C)
   - Регистрируется в `.kodla/config.yaml` как именованные ключи, например `rules.api`
   - Паттерны и ограничения для конкретных областей

**Приоритет:** Более специфичные правила побеждают. `rules.<area>` > `rules/base.md` > `RULES.md`

## Рабочий процесс

### Шаг 0: Загрузить конфиг

**СНАЧАЛА:** Прочитать `.kodla/config.yaml` если существует для определения:
- **Пути:** `paths.rules_file` и `paths.rules`
- **Язык:** `language.ui` для подсказок

Если config.yaml не существует — использовать значения по умолчанию:
- RULES.md: `.kodla/RULES.md`
- rules/: `.kodla/rules/`

### Шаг 0.1: Загрузить контекст навыка

**Прочитать `.kodla/skill-context/kodla-rules/SKILL.md`** — ОБЯЗАТЕЛЬНО если файл существует.

Этот файл содержит проектно-специфичные правила, накопленные из патчей, соглашений кодовой базы и анализа технического стека. Эти правила адаптированы под текущий проект.

**Как применять правила skill-context:**
- Рассматривать как **проектные переопределения** общих инструкций этого навыка
- Когда правило skill-context конфликтует с общим правилом из этого SKILL.md — **правило skill-context побеждает** (более специфичный контекст имеет приоритет)
- При отсутствии конфликта — применять оба: общие правила из SKILL.md + проектные из skill-context
- Не игнорировать правила skill-context даже если они кажутся противоречащими значениям по умолчанию — они существуют потому что опыт проекта доказал их необходимость
- **КРИТИЧНО:** правила skill-context применяются ко ВСЕМ выводам этого навыка — включая формат RULES.md и формулировки правил. Если правило skill-context говорит "правила ДОЛЖНЫ следовать формату X" — нужно соблюдать. Генерация правил, нарушающих skill-context, является ошибкой.

**Принудительное применение:** После генерации любого артефакта — проверить его на соответствие всем правилам skill-context. При нарушении — исправить вывод перед показом пользователю.

### Шаг 1: Определить режим

```text
Проверить $ARGUMENTS:
- Начинается с "area:" или "area "? -> Режим C: Правила области
- Есть текст? -> Режим A: Прямое добавление
- Нет аргументов? -> Режим B: Интерактивный
```

### Режим A: Прямое добавление

Пользователь передал текст правила как аргумент:

```text
/kodla-rules Всегда использовать DTO классы вместо массивов
```

Перейти к Шагу 2 с предоставленным текстом как правилом.

### Режим B: Интерактивный

Нет аргументов:

```text
/kodla-rules
```

Спросить через AskUserQuestion:

```text
Какое правило или соглашение добавить?

Примеры:
- Всегда использовать DTO классы вместо массивов для передачи данных
- Маршруты должны использовать kebab-case
- Все запросы к БД проходят через классы-репозитории
- Никогда не использовать сырой SQL, только query builder
- Логировать каждый вызов внешнего API с запросом и ответом
```

### Режим C: Правила области

Пользователь хочет создать или обновить правила для конкретной области:

```text
/kodla-rules area:api
/kodla-rules area frontend
```

**Рабочий процесс:**

1. **Определить название области** из аргумента (например, `api`, `frontend`, `backend`, `database`)

2. **Определить путь файла области** внутри настроенной директории правил.
   По умолчанию: `.kodla/rules/<area>.md`

3. **Проверить существование файла области:**
   ```text
   Glob: <resolved rules dir>/<area>.md
   ```

4. **Если файл НЕ существует** → создать с заголовком:

   ```markdown
   # Правила <Area>

   > Область-специфичные соглашения для <area>. Загружаются после rules/base.md.

   ## Правила

   - [первое правило]
   ```

5. **Если файл существует** → спросить пользователя какое правило добавить:

   ```text
   AskUserQuestion: Какое правило добавить в <area>.md?

   Текущие правила в <area>.md:
   - [существующее правило 1]
   - [существующее правило 2]

   Варианты:
   1. Добавить новое правило — укажите ниже
   2. Посмотреть весь файл
   3. Отмена
   ```

6. **Добавить правило** через `Edit` в конец секции `## Правила`.

7. **Зарегистрировать область в `.kodla/config.yaml`:**
   - Убедиться что `rules.<area>` указывает на путь файла правил области
   - Если `config.yaml` не существует — создать минимальный конфиг со значениями по умолчанию плюс новая запись `rules.<area>`
   - Сохранить существующие `rules.base` и другие именованные `rules.<other-area>`

8. **Подтвердить:**
   ```text
   Правило добавлено в <resolved area rules file> и зарегистрировано как `rules.<area>` в config.yaml:

   - [правило]

   Всего правил <area>: [количество]
   ```

9. **ОСТАНОВИТЬСЯ после завершения Режима C.**
   - Не продолжать к Шагу 2 / Шагу 3 / Шагу 4 ниже.
   - Эти шаги применяются только к правилам-аксиомам верхнего уровня в артефакте `paths.rules_file`.
   - Правила области принадлежат только `<resolved rules dir>/<area>.md` плюс соответствующая регистрация `rules.<area>` в `config.yaml`.

**Распространённые области:**
- `api` — соглашения REST/GraphQL API
- `frontend` — UI компоненты, управление состоянием
- `backend` — Сервисы, бизнес-логика
- `database` — Запросы, миграции, схемы
- `testing` — Паттерны тестов, покрытие
- `security` — Авторизация, валидация, санитизация

### Шаг 2: Прочитать или создать RULES.md

**Проверить существование настроенного пути RULES.md:**

```text
Glob: <resolved RULES.md path>
```

**Если файл НЕ существует** → создать с заголовком и первым правилом:

```markdown
# Правила проекта

> Короткие, действенные правила и соглашения для этого проекта.

## Правила

- [новое правило]
```

**Если файл существует** → прочитать, затем добавить новое правило в конец списка правил.

### Шаг 3: Записать правило

Использовать `Edit` чтобы добавить новое правило как элемент `- ` в конце секции `## Правила`.

**Правила форматирования:**
- Каждое правило — одна строка `- `
- Короткие и действенные (одно предложение)
- Без категорий, заголовков или подсписков — только плоский список
- Без дублей — если правило уже существует (по смыслу), сообщить пользователю и пропустить
- Если пользователь передаёт несколько правил сразу (разделены переносами строк или точкой с запятой) — добавить каждое отдельной строкой

### Шаг 4: Подтвердить

```text
Правило добавлено в <resolved RULES.md path>:

- [правило]

Всего правил: [количество]
```

## Правила

1. **Одно правило на строку** — плоский список, без вложенности
2. **Без категорий** — без заголовков внутри секции правил
3. **Без дублей** — проверить существующие правила с тем же смыслом перед добавлением
4. **Действенные формулировки** — чёткие директивы ("Всегда...", "Никогда...", "Использовать...", "Маршруты должны...")
5. **Расположение RULES.md** — использовать настроенный путь `paths.rules_file` (по умолчанию: `.kodla/RULES.md`)
6. **Регистрация области** — каждый файл правил области должен быть отражён в `config.yaml` как `rules.<area>`
7. **Граница владения** — этот навык владеет настроенным артефактом RULES.md и может обновлять подмножество `rules.*` в `.kodla/config.yaml`; другие артефакты контекста остаются read-only если пользователь явно не запросил иное
