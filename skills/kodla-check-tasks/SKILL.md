# Check Tasks — Проверка реализации плана

Проверяет что реализация соответствует плану: каждая задача выполнена, код рабочий, нет незавершённых маркеров.

**Навык только читает** — не вносит изменения в код и не изменяет `.kodla/*` файлы.

---

## Шаг 0: Загрузка контекста

### 0.0 Читать конфиг

**Прочитать `.kodla/config.yaml`** если существует, для извлечения:
- `paths.plans` — директория планов (по умолчанию: `.kodla/plans/`)
- `paths.description` — описание проекта (по умолчанию: `.kodla/DESCRIPTION.md`)
- `paths.rules` — директория правил (по умолчанию: `.kodla/rules/`)

Если конфиг не существует — использовать значения по умолчанию.

### 0.1 Читать контекст проекта

- **Прочитать `.kodla/DESCRIPTION.md`** если существует — tech-стек, архитектура, соглашения
- **Прочитать `.kodla/rules/base.md`** если существует — правила проекта

### 0.2 Обнаружение плана

**Если `$ARGUMENTS` содержит `@<путь>`:**
```
1. Извлечь путь после "@"
2. Если файл не существует → сообщить: "Файл плана не найден: <путь>" → СТОП
3. Использовать этот файл как активный план
```

**Если нет явного `@<путь>`, проверить источники по приоритету:**

```
1. tasar/changes/*/tasks.md (исключить archive/)
2. .tasar/changes/*/tasks.md (исключить archive/)
3. .kodla/plans/*.md (из paths.plans)
```

- Один найден → использовать его
- Несколько найдено → спросить пользователя какой проверять
- Ни одного → сообщить:
  ```
  Активный план не найден.
  Создай план через /kodla:plan или /tasar:propose
  ```
  → СТОП

**Примечание:** Активные изменения tasar находятся в `tasar/changes/<name>/`, архивированные — в `tasar/changes/archive/`. При поиске исключать папку `archive/`.

**Прочитать файл плана** для понимания:
- Списка задач (чекбоксы `- [ ]` и `- [x]`)
- Контекста задач

---

## Шаг 1: Аудит задач

Для **каждой задачи** из плана проверить фактическую реализацию.

### 1.1 Получить описание задачи

```
TaskGet(taskId) → полное описание, требования, контекст
```

### 1.2 Найти реализацию

Для каждого требования из описания задачи:
- Использовать `Glob` и `Grep` для поиска кода
- Прочитать найденные файлы и убедиться что реализация соответствует описанию
- Проверить именно содержимое, а не просто наличие файла

### 1.3 Присвоить статус

```
✅ Задача #1: Создать модель User — ВЫПОЛНЕНО
   - Модель создана в src/Models/User.php
   - Все поля присутствуют

⚠️ Задача #3: Добавить валидацию — ЧАСТИЧНО
   - Валидация добавлена в контроллер
   - НЕ НАЙДЕНО: правила валидации для поля email

❌ Задача #5: Написать документацию — НЕ НАЙДЕНО
   - Изменений в docs/ не обнаружено

⏭️ Задача #2: Добавить тесты — ПРОПУЩЕНО
   - Задача была явно пропущена
```

Статусы:
- `✅ ВЫПОЛНЕНО` — все требования задачи реализованы
- `⚠️ ЧАСТИЧНО` — часть требований реализована, часть отсутствует
- `❌ НЕ НАЙДЕНО` — реализация не обнаружена
- `⏭️ ПРОПУЩЕНО` — задача была намеренно пропущена

## Шаг 2: Проверка качества кода

### 2.1 Проверка зависимостей

```bash
# Если есть composer.json
composer validate
```

Если `composer.json` отсутствует — отметить "не применимо".

### 2.2 Запуск тестов

```bash
# Если есть phpunit.xml или phpunit.xml.dist
./vendor/bin/phpunit
```

Если phpunit не настроен — отметить "тесты не настроены" и продолжить.

### 2.3 Проверка стиля кода

```bash
# Если есть .php-cs-fixer.php или .php-cs-fixer.dist.php
./vendor/bin/php-cs-fixer fix --dry-run --diff
```

Если php-cs-fixer не настроен — отметить "линтер не настроен".

Если инструмент не установлен (`vendor/bin/` не существует) — пропустить и отметить.

## Шаг 3: Проверка согласованности

### 3.1 Незавершённые маркеры

Поиск в изменённых файлах (файлы упомянутые в задачах или `src/`):

```
Grep: TODO|FIXME|HACK|TEMP|PLACEHOLDER
```

Найденные маркеры — не обязательно ошибка, но нужно показать.

### 3.2 Debug-вывод

```
Grep: var_dump\(|dd\(|print_r\(|dump\(
```

Debug-вывод в коде — признак незавершённости.

### 3.3 Переменные окружения

```
Grep: env\(|getenv\(|\$_ENV\[|\$_SERVER\[
```

Проверить что новые переменные задокументированы в `.env.example`, `README.md` или аналогичных файлах.

- **Всё зелёно** — реализация проверена, можно продолжать

## Команды

### Стандартный запуск

```
/kodla:check-tasks
```

Проверяет активный план (tasar/changes/ → .tasar/changes/ → .kodla/plans/).

### Явное указание файла плана

```
/kodla:check-tasks @tasar/changes/my-feature/tasks.md
/kodla:check-tasks @.kodla/plans/refactor-api.md
```

---

## Правила

- Только читать — не вносить изменения в файлы
- Не отмечать задачи как выполненные или невыполненные
- Не предлагать commit или другие git-операции
- Проверять фактическое содержимое кода, а не просто наличие файлов
- Если качество-инструмент не настроен — отметить и продолжить, не считать это провалом
