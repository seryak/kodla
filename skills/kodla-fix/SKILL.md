# Fix — Рабочий процесс исправления багов

Исправляет конкретный баг или проблему в кодовой базе. Поддерживает два режима: немедленный фикс или план-первый.

## Рабочий процесс

### Шаг 0: Загрузка конфига и разрешение путей

**СНАЧАЛА:** Прочитай `.kodla/config.yaml` если существует, чтобы разрешить:

- **Пути:** `paths.description`, `paths.architecture`, `paths.rules_file`, `paths.rules`, `paths.fix_plan`, `paths.patches`
- **Язык:** `language.ui` для подсказок
- **Правила:** `rules.base` и любые именованные `rules.<area>` записи

Если config.yaml не существует, используй умолчания:

- DESCRIPTION.md: `.kodla/DESCRIPTION.md`
- ARCHITECTURE.md: `.kodla/ARCHITECTURE.md`
- rules/base.md: `.kodla/rules/base.md`
- rules/: `.kodla/rules/`
- FIX_PLAN.md: `.kodla/FIX_PLAN.md`
- patches/: `.kodla/patches/`

### Шаг 0.1: Проверка существующего плана фикса

**ДО чего-либо ещё после разрешения конфига**, проверь разрешённый путь к плану фикса (по умолчанию: `.kodla/FIX_PLAN.md`).

**Если файл СУЩЕСТВУЕТ:**

- Прочитай файл плана фикса
- Сообщи пользователю: "Найден существующий план фикса. Выполняю фикс по плану."
- Пропусти **Шаг 1** (выбор режима), но всё равно выполни **Шаг 0.2** для загрузки контекста
- Затем перейди к **Шагу 2: Исследование кодовой базы**, используя план как руководство
- Следуй каждому шагу плана последовательно
- После полного применения и верификации фикса **удали** файл плана:
  ```bash
  rm <путь к плану фикса>
  ```
- Продолжи к Шагу 4 (Верификация), Шагу 5 (Тесты), Шагу 6 (Патч)

**Если файл НЕ СУЩЕСТВУЕТ И `$ARGUMENTS` пусты:**

- Сообщи пользователю: "Файл плана не найден и описание проблемы не предоставлено. Укажи описание бага (`/kodla-fix <описание>`) или создай план сначала."
- **СТОП.**

**Если файл НЕ СУЩЕСТВУЕТ И `$ARGUMENTS` предоставлены:**

- Продолжи к Шагу 0.2 ниже.

### Шаг 0.2: Загрузка контекста проекта и прошлого опыта

**ЗАТЕМ:** Прочитай `.kodla/DESCRIPTION.md` (используй путь из конфига) если существует, чтобы понять:

- Технологический стек (язык, фреймворк, база данных)
- Архитектуру проекта
- Соглашения по коду

**Также прочитай `.kodla/ARCHITECTURE.md`** (используй путь из конфига), разрешённый путь к `rules/base.md` и правила из конфига.

**Прочитай `.kodla/skill-context/kodla-fix/SKILL.md`** — ОБЯЗАТЕЛЬНО если файл существует.

Этот файл содержит специфичные для проекта правила, накопленные `/kodla-evolve` из патчей, конвенций кодовой базы и анализа технологического стека. Эти правила подобраны для текущего проекта.

**Как применять правила skill-context:**

- Относись к ним как к **переопределениям уровня проекта** для общих инструкций этого навыка
- Когда правило skill-context конфликтует с общим правилом в этом SKILL.md, **правило skill-context побеждает** (более специфичный контекст в приоритете — тот же принцип, что и вложенные CLAUDE.md файлы)
- Когда конфликта нет — применяй оба: общие правила SKILL.md + правила проекта из skill-context
- НЕ игнорируй правила skill-context даже если они кажутся противоречащими умолчаниям навыка
- **КРИТИЧНО:** правила skill-context применяются ко ВСЕМ выходным данным навыка — включая шаблон FIX_PLAN.md и файлы патчей. Если правило skill-context говорит "шаги ДОЛЖНЫ включать X" или "план ДОЛЖЕН иметь раздел Y" — НЕОБХОДИМО дополнить шаблон соответственно

**Принуждение:** После создания любого выходного артефакта проверь его на соответствие всем правилам skill-context. Если правило нарушено — исправь выходные данные до показа пользователю.

**Фоллбэк с патчами (ограниченный, только если skill-context отсутствует):**

- Если `.kodla/skill-context/kodla-fix/SKILL.md` не существует и разрешённая директория патчей существует:
  - Используй `Glob` для поиска `*.md` файлов в директории патчей
  - Отсортируй имена файлов патчей по возрастанию (лексически), выбери последние **10** (или меньше если их меньше)
  - Прочитай только эти файлы
  - Приоритизируй повторяющиеся паттерны **Корневой причины** и **Предотвращения**
- Если skill-context существует — не читай все патчи по умолчанию.
  - Опционально проверь небольшое целевое подмножество недавних патчей когда теги/файлы явно соответствуют текущему багу.

### Шаг 1: Понимание проблемы и выбор режима

Из `$ARGUMENTS` определи:

- Сообщение об ошибке или неожиданное поведение
- Где происходит (файл, функция, эндпоинт)
- Шаги воспроизведения (если указаны)

Если неясно, спроси:

```
Чтобы исправить это эффективно, мне нужен дополнительный контекст:

1. Какое ожидаемое поведение?
2. Что происходит на самом деле?
3. Можешь поделиться сообщением об ошибке/стектрейсом?
4. Когда это началось?
```

**После понимания проблемы, спроси пользователя выбрать режим через `AskUserQuestion`:**

Вопрос: "Как хочешь продолжить с фиксом?"

Варианты:

1. **Исправить сейчас** — исследовать и применить фикс немедленно
2. **Сначала план** — создать план фикса для проверки, затем исправить позже

**На основе выбора:**

- "Сначала план" → Перейди к **Шагу 1.1: Создание плана фикса**
- "Исправить сейчас" → Пропусти Шаг 1.1, перейди к **Шагу 2: Исследование кодовой базы**

### Шаг 1.1: Создание плана фикса

Исследуй кодовую базу достаточно для понимания проблемы и создания плана.

**Используй тот же параллельный подход исследования что и в Шаге 2** — запускай Explore-агенты для одновременного исследования проблемной области, связанного кода и прошлых паттернов.

После возврата агентов синтезируй выводы для:

1. Определения корневой причины (или наиболее вероятных кандидатов)
2. Составления карты затронутых файлов и функций
3. Оценки области воздействия

Затем создай файл плана фикса (по умолчанию: `.kodla/FIX_PLAN.md`).

Структура:

```markdown
# План фикса: [Краткий заголовок]

**Проблема:** [Что сломано — из описания пользователя]
**Создан:** YYYY-MM-DD HH:mm

## Анализ

Что было найдено при исследовании:

- Корневая причина (или предполагаемая)
- Затронутые файлы и функции
- Область воздействия

## Шаги фикса

1. [ ] Шаг первый — что изменить и почему
2. [ ] Шаг второй — ...
3. [ ] Шаг третий — ...

## Файлы для изменения

- `path/to/file.php` — какие изменения нужны
- `path/to/another.php` — какие изменения нужны

## Риски и соображения

- Возможные побочные эффекты
- Что проверить после фикса
- Граничные случаи

## Тест-покрытие

- Какие тесты нужно добавить
- Какие граничные случаи покрыть
```

**После создания плана выведи:**

```
## План фикса создан ✅

План сохранён в <путь к плану фикса>.

Проверь план и когда будешь готов выполнить, запусти:

/kodla-fix
```

**СТОП. НЕ применяй фикс.**

### Шаг 2: Исследование кодовой базы

**Используй `Agent` с `subagent_type: Explore` для параллельного исследования проблемы.** Это сохраняет чистоту основного контекста и позволяет одновременно исследовать несколько аспектов.

Запускай 2-3 Explore-агента одновременно:

```
Агент 1 — Найди проблемную область:
Agent(subagent_type: Explore, prompt:
  "Найди код связанный с [место ошибки / затронутая функциональность].
   Прочитай соответствующие функции, проследи поток данных.
   Детализация: medium.")

Агент 2 — Связанный код и побочные эффекты:
Agent(subagent_type: Explore, prompt:
  "Найди всех вызывающих/потребителей [затронутая функция/модуль].
   Определи что ещё может сломаться или быть затронуто.
   Детализация: medium.")

Агент 3 — Похожие прошлые паттерны (если есть патчи):
Agent(subagent_type: Explore, prompt:
  "Найди похожие паттерны ошибок или связанные фиксы в кодовой базе.
   Проверь git log, недавний контекст проекта и патчи опыта по [затронутым файлам].
   Детализация: quick.")
```

**После возврата агентов синтезируй выводы:**

- Корневая причина (не просто симптомы)
- Связанный код который может быть затронут
- Существующая обработка ошибок

**Фоллбэк:** Если Agent недоступен, исследуй напрямую:

- Найди релевантные файлы через Glob/Grep
- Прочитай код вокруг проблемы
- Проследи поток данных
- Проверь похожие паттерны в другом месте

### Шаг 3: Применение фикса

**Примени фикс с логированием:**

```typescript
// ✅ ОБЯЗАТЕЛЬНО: добавь логирование вокруг фикса
console.log("[FIX] Обработка входных данных", { userId, input });

try {
  // Сам фикс
  const result = fixedLogic(input);
  console.log("[FIX] Успех", { userId, result });
  return result;
} catch (error) {
  console.error("[FIX] Ошибка в fixedLogic", {
    userId,
    input,
    error: error.message,
    stack: error.stack,
  });
  throw error;
}
```

**Логирование ОБЯЗАТЕЛЬНО потому что:**

- Пользователю нужно убедиться что фикс работает
- Если не работает — логи помогают отлаживать дальше
- Цикл обратной связи: пользователь предоставляет логи → итерируем

### Шаг 4: Верификация фикса

- Проверь что код компилируется/запускается
- Убедись что логика корректна
- Убедись что регрессии не введены

### Шаг 5: Предложение тест-покрытия

**ВСЕГДА предлагай покрыть этот случай тестом:**

```
## Фикс применён ✅

Проблема была: [краткое объяснение]
Исправлено: [что изменено]

### Логирование добавлено
Фикс включает логирование с префиксом `[FIX]`.
Проверь и поделись логами если проблемы продолжаются.

### Рекомендуется: Добавить тест

Этот баг должен быть покрыт тестом для предотвращения регрессии:

\`\`\`
describe('functionName', () => {
  it('должна обрабатывать [граничный случай вызвавший баг]', () => {
    // Arrange
    const input = /* проблемный ввод */;

    // Act
    const result = functionName(input);

    // Assert
    expect(result).toBe(/* ожидаемое */);
  });
});
\`\`\`

AskUserQuestion: Создать этот тест?

Варианты:
1. Да, создать тест
2. Нет, пропустить
```

**Обработка ответа пользователя:**

- **Если "Да, создать тест":**
  1. Создай файл теста в соответствующей директории (следуй конвенциям проекта)
  2. Включи предложенный тест и дополнительные граничные случаи связанные с фиксом
  3. Запусти тест для проверки что проходит
  4. Затем перейди к **Шагу 6: Создание патча самообучения**

- **Если "Нет, пропустить":**
  - Перейди сразу к **Шагу 6: Создание патча самообучения**

## Требования к логированию

**Все фиксы ДОЛЖНЫ включать логирование:**

1. **Префикс лога**: Используй `[FIX]` или `[FIX:<issue-id>]` для лёгкой фильтрации
2. **Лог входных данных**: Какие данные обрабатывались
3. **Лог успеха**: Подтверждение что фикс сработал
4. **Лог ошибок**: Полный контекст если что-то не так
5. **Настраиваемость**: Используй LOG_LEVEL если доступно

```typescript
// Паттерн для фиксов
const LOG_FIX = process.env.LOG_LEVEL === "debug" || process.env.DEBUG_FIX;

function fixedFunction(input) {
  if (LOG_FIX) console.log("[FIX] Входные данные:", input);

  // ... логика фикса ...

  if (LOG_FIX) console.log("[FIX] Результат:", result);
  return result;
}
```

## Примеры

### Пример 1: Ошибка null-ссылки

**Пользователь:** `/kodla-fix TypeError: Cannot read property 'name' of undefined в UserProfile`

**Действия:**

1. Найти компонент/функцию UserProfile
2. Найти где обращается к `.name`
3. Добавить null-проверку с логированием
4. Предложить тест для случая с null пользователем

### Пример 2: API возвращает неправильные данные

**Пользователь:** `/kodla-fix /api/orders возвращает пустой массив для аутентифицированных пользователей`

**Действия:**

1. Найти эндпоинт API заказов
2. Проследить логику запроса
3. Найти баг (например, неправильный фильтр)
4. Исправить с логированием
5. Предложить интеграционный тест

### Пример 3: Валидация формы не работает

**Пользователь:** `/kodla-fix валидация email принимает невалидные адреса`

**Действия:**

1. Найти логику валидации email
2. Проверить regex или использование библиотеки валидации
3. Исправить валидацию
4. Добавить логирование для неудачных валидаций
5. Предложить unit-тест с граничными случаями

## Важные правила

1. **Проверяй план фикса первым** — всегда проверяй разрешённый путь плана перед всем остальным
2. **Режим "план" = только план** — когда пользователь выбирает "Сначала план", создай план и СТОП. НЕ исправляй.
3. **Режим выполнения = следуй плану** — когда разрешённый план фикса существует, следуй ему пошагово, затем удали его
4. **БЕЗ отчётов** — не создавай итоговые документы (патчи — артефакты обучения, не отчёты)
5. **ВСЕГДА логируй** — каждый фикс должен иметь логирование для обратной связи
6. **ВСЕГДА предлагай тесты** — помогай предотвращать регрессии
7. **Корневая причина** — исправляй реальную проблему, не симптомы
8. **Минимальные изменения** — не рефакторь несвязанный код
9. **Один фикс за раз** — не расширяй область
10. **Убирай за собой** — удали файл плана фикса после успешного выполнения
11. **Граница ответственности** — `/kodla-fix` владеет `paths.fix_plan` и `paths.patches`; артефакты `.kodla/DESCRIPTION.md`, правила и архитектурные контексты — только для чтения если пользователь явно не просит иного
12. **Область логирования** — сохраняй требования логирования `[FIX]` для фиксов; выходные данные навыка должны использовать `WARN`/`ERROR` и не менять глобальную политику логирования других навыков

## После фикса

**Используй этот шаблон вывода в Шаге 5** (до AskUserQuestion о тестах):

```
## Фикс применён ✅

**Проблема:** [что было сломано]
**Причина:** [почему было сломано]
**Фикс:** [что изменено]

**Изменённые файлы:**
- path/to/file.php (строка X)

**Логирование добавлено:** Да, префикс `[FIX]`
```

### Шаг 6: Создание патча самообучения

**ВСЕГДА создавай патч после каждого фикса.** Это строит базу знаний для будущих фиксов.

**Создай патч:**

1. Создай директорию если не существует:

   ```bash
   mkdir -p <разрешённая директория патчей>
   ```

2. Создай файл патча с текущей временной меткой как именем файла.
   **Формат:** `YYYY-MM-DD-HH.mm.md` (например, `2026-04-27-14.30.md`)

3. Используй этот шаблон:

```markdown
# [Краткий заголовок описывающий фикс]

**Дата:** YYYY-MM-DD HH:mm
**Файлы:** список изменённых файлов
**Серьёзность:** low | medium | high | critical

## Проблема

Что было сломано. Как проявлялось (сообщение об ошибке, неправильное поведение).
Конкретно — включи реальную ошибку или симптом.

## Корневая причина

ПОЧЕМУ проблема возникла. Это самая ценная часть.
Не "что было не так" а "почему было не так":

- Логическая ошибка? Почему логика была неверной?
- Отсутствующая проверка? Почему она отсутствовала?
- Неправильное допущение? Что было допущено?
- Состояние гонки? Какая последовательность вызвала это?

## Решение

Как был реализован фикс. Ключевые изменения кода и обоснование.
Включи подход, а не просто "изменена строка X".

## Предотвращение

Как предотвратить этот класс проблем в будущем:

- Какой паттерн/практику нужно соблюдать?
- Что нужно проверять при код-ревью?
- Какой тест поймает это?

## Теги

Теги через пробел для категоризации, например:
`#null-check` `#async` `#validation` `#api` `#database`
```

**Это НЕ опционально.** Каждый фикс генерирует патч. Патч — это твоё обучение.

---

**НЕ ДЕЛАЙ:**

- ❌ Применяй фикс когда пользователь выбрал "Сначала план" — только создай план и стоп
