# Unit-тесты

Написать тесты для конкретного метода, функции или файла-класса — в стиле, согласованном с проектом, так, чтобы тесты ловили реальные регрессии, а не просто покрывали строки.

Я создам или дополню:
- тесты в стандартной для языка/фреймворка тестовой директории (структура зеркалит production-код)
- fakes/билдеры/фикстуры — если их не хватает для покрытия цели без over-mocking

После генерации я запускаю тесты и чиню падения (кроме случаев, когда падение вызвано багом в production-коде — тогда я останавливаюсь и сообщаю).

---

**Входные данные**: запрос должен содержать явную цель — одно из:
- конкретный метод класса (`ClassName::methodName` или описание "метод X в классе Y")
- функция (свободная, не метод класса)
- путь к файлу-классу (`path/to/File.ext`) — тогда цель — все публичные методы файла

Этот навык **не занимается** авто-определением области покрытия (по tasar, git diff, "что я только что реализовал") — если нужно понять, что покрыть, после `/tasar:apply` или реализации плана, попроси пользователя явно указать метод/функцию/файл, или уточни через `AskUserQuestion`.

## Шаг 1: Загрузка конфига и контекста

**Конфиг проекта:**

Прочитай `.kodla/config.yaml` если существует. Извлеки:
- `paths.description` — описание проекта (по умолчанию: `.kodla/DESCRIPTION.md`)
- `paths.architecture` — архитектура проекта (по умолчанию: `.kodla/ARCHITECTURE.md`)
- `paths.rules` / `rules.base` — правила проекта (по умолчанию: `.kodla/rules/`)
- `language.ui` — язык взаимодействия (по умолчанию: `ru`)
- `language.artifacts` — язык тестов и комментариев (по умолчанию: `ru`)

**Skill-context (правила `/kodla-evolve`):**

Прочитай `.kodla/skill-context/kodla-unittest/SKILL.md` если существует.

Этот файл содержит проектно-специфичные правила, накопленные `/kodla-evolve` на основе опыта работы с этим проектом. Правила из skill-context **приоритетнее** общих правил этого навыка — как вложенные CLAUDE.md переопределяют родительские. Перед написанием тестов проверь финальный результат на соответствие всем правилам skill-context.

**Контекст проекта:**

Прочитай файлы если существуют: `.kodla/DESCRIPTION.md`, `.kodla/ARCHITECTURE.md`, `.kodla/rules/base.md` и именованные правила из конфига.

Используй контекст проекта для корректного выбора namespace/module, конвенций именования и структуры директорий тестов.

## Шаг 2: Определи язык и цель

Разбери запрос пользователя (`$ARGUMENTS` или сообщение) и определи `TARGET`:

- `TARGET.kind` — `method` | `function` | `file`
- `TARGET.path` — файл, где находится цель (найди через `Glob`/`Grep`, если пользователь дал только имя)
- `TARGET.language` — по расширению файла (`.php`, `.go`, `.ts`/`.tsx`, `.py`, ...)

Если цель неоднозначна (несколько файлов с таким именем класса/функции, или не найдено ни одного) — уточни через `AskUserQuestion`, не гадай.

Если `TARGET` не удаётся определить как метод/функцию/файл (пользователь описал область словами, "неймспейс", "фичу") — сообщи, что этот навык работает с явной целью, и попроси конкретный метод/функцию/путь.

---

## Шаг 3: Разведка тестового окружения

**Определи тест-фреймворк** по манифесту проекта:

| Язык | Манифест | Что искать |
|---|---|---|
| PHP | `composer.json` | `pestphp/pest` → Pest, иначе `phpunit/phpunit` → PHPUnit; `laravel/framework` → Laravel-стек |
| Go | `go.mod` | встроенный `testing`; `stretchr/testify` → testify |
| JS/TS | `package.json` | `vitest`, `jest`, `mocha` в devDependencies |
| Python | `pyproject.toml` / `requirements*.txt` | `pytest` или встроенный `unittest` |

Прочитай конфиг тестов (`phpunit.xml`/`phpunit.xml.dist`, `tests/Pest.php`, `vitest.config.*`, `jest.config.*`, `pytest.ini`/`pyproject.toml [tool.pytest]`) — фреймворк-специфичные настройки, базовые TestCase, трейты/фикстуры.

**Обязательно найди 2–3 ближайших существующих теста** того же типа (unit/feature, того же типа субъекта — сервис/контроллер/action) для копирования naming, стиля assertion'ов, подхода к mocking. Стиль существующих тестов **всегда важнее** референса навыка.

## Шаг 4: Загрузи референс языка

Референсы лежат в `references/<язык>/rules.md`:

| Язык | Референс |
|---|---|
| PHP | `references/php/rules.md` |

**Если референс для языка цели отсутствует** (например, цель на Go, а `references/golang/rules.md` ещё не существует):

1. Сообщи пользователю, что для этого языка ещё нет накопленного референса, и что ты напишешь тесты на основе общих знаний + стиля существующих тестов проекта.
2. После успешного прогона тестов — предложи сохранить обнаруженные конвенции (фреймворк, стиль naming, подход к mocking/fakes, типичные assertion'ы) в новый `references/<язык>/rules.md`, следуя структуре `references/php/rules.md` как образцу. Создавай файл только с подтверждения пользователя.
3. Не блокируй работу отсутствием референса — это optimization, не hard requirement.

## Шаг 5: Спланируй тесты

Используй **TodoWrite** для отслеживания. Для планируемых тестов определи:

- **Путь** теста — повторяет структуру production-кода / конвенцию проекта.
- **Тип** — unit (чистая логика, без IO) или feature/integration (БД, HTTP, очередь, файловая система). Будь честным: если цель делает IO — unit-тест со всеми моками — спектакль, делай feature/integration.
- **Тест-кейсы** — по одному на каждое наблюдаемое поведение цели:
  - `TARGET.kind == method` или `function` — все значимые ветки (`if`/`match`/`switch`/`throw`) этого метода/функции.
  - `TARGET.kind == file` — то же самое для каждого публичного метода файла.
- **Edge cases** — null/nil/zero-value, пустые коллекции, граничные значения, ошибочные ветки.

Перед первой генерацией в новом для тебя языке/проекте прочитай раздел «Антипаттерны» в `references/<язык>/rules.md` — каталог типовых ошибок LLM при генерации тестов.

Для >3 тестовых файлов — покажи пользователю план (список файлов и кейсов) до генерации.

---

## Шаг 6: Напиши тесты

Стиль — **повторяет** существующие тесты проекта (Шаг 3). Не вводи свой стиль поверх стиля проекта.

Конкретные паттерны (скелет файла, naming, assertion'ы, mocking, фреймворк-специфика) — в `references/<язык>/rules.md`.

---

## Шаг 7: Запусти, почини, проверь

Запусти только что написанные тесты (команда — по фреймворку из Шага 3, например `vendor/bin/pest <файл>`, `vendor/bin/phpunit <файл>`, `go test ./... -run <TestName>`, `npx vitest run <файл>`, `pytest <файл>`).

При падении теста разбери причину:
- **Ошибка в тесте** (неверный namespace/import, фикстура, setup) → почини тест.
- **Баг в production-коде** → стоп, сообщи пользователю. **Не** переписывай тест под баг, чтобы он прошёл.
- **Флаки** (timing, ordering, randomness) → почини дизайн теста (заморозь время, посей random, контролируй порядок). Никогда `sleep()`-and-pray.

После прохождения новых тестов запусти весь suite (или его релевантную часть) — проверь, что не сломал общие фикстуры/фабрики/состояние.

---

## Шаг 8: Покажи итог

Выведи:
- Список созданных/изменённых тестовых файлов (пути)
- Какие кейсы покрыты (метод/функция → перечень поведений)
- Результат запуска (`X passed, Y failed`)
- Нюансы, если есть (найденный баг в проде, флаки-предупреждение, пропущенный edge case с обоснованием)
- Если создан новый `references/<язык>/rules.md` (Шаг 4, п.2) — упомяни это отдельно

## Чек-лист перед завершением

- [ ] Тесты запускаются зелёным локально
- [ ] **Mutation-проверка**: мысленно убери одну значимую строку из цели — упадёт ли тест? Если нет — тест тавтологический, переписать
- [ ] Edge cases покрыты, не только happy path
- [ ] Naming совпадает со стилем проекта
- [ ] Расположение теста зеркалит production-код / соответствует конвенции проекта
- [ ] Нет забытых debug-выводов (`dd()`, `dump()`, `console.log`, `print()`, `fmt.Println` для отладки)
- [ ] Не замокана сама тестируемая цель (mock того, что тестируется, = тест проходит при любых багах)
- [ ] Нет focused-тестов (`->only()`, `.only`, `fit`, `-run` навсегда закреплённый в файле) — они молча отключают часть suite
- [ ] Правила skill-context соблюдены

## Важные правила

1. **Skill-context в приоритете** — правила из `.kodla/skill-context/kodla-unittest/SKILL.md` всегда перекрывают инструкции этого навыка
2. **Только явная цель** — навык не угадывает область покрытия; неоднозначность решается через `AskUserQuestion`, а не предположением
3. **Контекст проекта обязателен** — перед генерацией прочитать DESCRIPTION.md, rules/base.md; нарушение конвенций проекта = ошибка
4. **Стиль существующих тестов приоритетнее референса** — референс языка даёт паттерны, но конкретный проект может выбрать другой naming/структуру
5. **Тип теста честный** — если цель делает IO, это feature/integration-тест, не unit ради красивых цифр покрытия
6. **Не мокать тестируемую цель** — mock того, что тестируем, = тест всегда зелёный вне зависимости от багов
7. **Баги в проде — стоп** — найденный баг сообщаем явно, тест под багованное поведение не пишем
8. **Без focused-тестов в коммите**
9. **Русский язык** — все вопросы к пользователю и итоговые сообщения на русском (если `language.ui: ru`)
10. **Новый языковой референс — только с подтверждения** — не пиши `references/<язык>/rules.md` молча, предложи и дождись согласия

## Добавление нового языка

Структура `references/` рассчитана на рост:

```
references/
├── php/
│   └── rules.md    # заполнено
├── golang/
│   └── rules.md    # добавляется по мере надобности (Шаг 4, п.2)
└── <язык>/
    └── rules.md
```

При добавлении нового языка вручную или через накопленный опыт (Шаг 4):
- Имя папки — по возможности совпадает с использованием в других kodla-навыках (`kodla-makefile` использует `go`, `node`, `python`; для консистентности выбирай то же именование)
- Содержимое `rules.md` — следуй структуре `references/php/rules.md`: оглавление, скелет теста, naming, assertion'ы, data-driven тесты, mocking/fakes, фреймворк-специфика (если есть доминирующий фреймворк для этого языка/стека), антипаттерны, команды запуска
- После добавления — обнови таблицу в Шаге 4 этого файла (`SKILL.md`), указав новый язык и путь к референсу
- Если у языка несколько крупных фреймворков (как у PHP — vanilla/Laravel/Symfony) — можно вынести фреймворк-специфику в соседний файл (`references/<язык>/<framework>.md`) и сослаться на него из `rules.md`, по образцу `references/php/rules.md` → раздел Laravel

## Ограничения

- Не модифицирую production-код для тестируемости (extract dependency, разбиение метода) без явного согласия пользователя — предложу вариант, дождусь подтверждения.
- Не пишу тесты на код, который ещё не написан. TDD-режим (тесты до реализации) — отдельный сценарий, в этом скилле не покрыт.
- Не пишу тесты на код фреймворка/стандартной библиотеки — тестируется только своя логика поверх.
- Не удаляю существующие тесты автоматически.
- Не использую `->only()`/`.only`/`fit`/аналоги в коммитимом коде.
- Не игнорирую edge cases ради скорости — лучше 5 хороших тестов, чем 30 happy-path.
- Не угадываю область покрытия — без явной цели останавливаюсь и спрашиваю.
- Если ни один тест-фреймворк не установлен в проекте для языка цели — не устанавливаю автоматически. Сообщаю пользователю и предлагаю варианты.
