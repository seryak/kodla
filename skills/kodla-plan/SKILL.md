# Plan — Планирование реализации

Создаёт подробный план реализации фичи или задачи с разбивкой на шаги.

## Рабочий процесс

### Шаг 0. Обнаружение tasar

Проверь наличие папок tasar-фреймворка:

```bash
test -d "tasar" || test -d ".tasar"
```

**Если папка `tasar` или `.tasar` существует:**

Этот проект использует tasar. Не останавливайся — немедленно выполни полный workflow навыка `/tasar-propose` с теми же аргументами (`$ARGUMENTS`).

Выполняй `/tasar-propose` инлайн: прочитай его SKILL.md и следуй его workflow шаг за шагом — создание папки изменения через `tasar new <slug>`, заполнение proposal.md, design.md, tasks.md, specs/<slug>.md.

После завершения `/tasar-propose`, перед остановкой, предложи пользователю запустить вторую итерацию планирования:

```
Хочешь сначала углубить план? Запусти:
/kodla-improve @<tasar-dir>/changes/<slug>/tasks.md
```

где `<tasar-dir>` — `tasar` или `.tasar`, в зависимости от того какая папка использовалась.

После этого — **остановись**, не продолжай шаги ниже. Дальнейший workflow этого навыка предназначен только для проектов без tasar.

---

### Шаг 1. Загрузка конфига и skill-context

**Конфиг проекта:**

Прочитай `.kodla/config.yaml` если существует. Извлеки:
- `paths.plans` — директория для планов (по умолчанию: `.kodla/plans/`)
- `paths.description` — описание проекта (по умолчанию: `.kodla/DESCRIPTION.md`)
- `paths.architecture` — архитектура проекта (по умолчанию: `.kodla/ARCHITECTURE.md`)
- `paths.research` — сохранённые исследования (по умолчанию: `.kodla/RESEARCH.md`)
- `paths.roadmap` — дорожная карта (по умолчанию: `.kodla/ROADMAP.md`)
- `paths.rules` / `rules.base` — правила проекта (по умолчанию: `.kodla/rules/`)
- `language.ui` — язык взаимодействия (по умолчанию: `ru`)
- `language.artifacts` — язык артефактов (по умолчанию: `ru`)

**Skill-context (правила `/kodla-evolve`):**

Прочитай `.kodla/skill-context/kodla-plan/SKILL.md` если существует.

Этот файл содержит проектно-специфичные правила, накопленные `/kodla-evolve` на основе опыта работы с этим проектом. Правила из skill-context имеют **приоритет** над общими правилами этого навыка — как вложенные CLAUDE.md переопределяют родительские. Не игнорируй их даже если они противоречат инструкциям ниже.

После генерации плана проверь его на соответствие всем правилам skill-context.

**Контекст проекта:**

Прочитай файлы если существуют:
- `.kodla/DESCRIPTION.md` — стек, архитектура, соглашения и нефункциональные требования
- `.kodla/ARCHITECTURE.md` — структура проекта, границы модулей, правила зависимостей
- `.kodla/rules/base.md` и именованные правила из конфига — локальные соглашения
- `.kodla/RESEARCH.md` — сохранённое исследование; раздел `Активное резюме` считать дополнительным источником требований
- `.kodla/ROADMAP.md` — стратегические вехи; использовать для необязательной привязки плана к milestone

Если `$ARGUMENTS` пусты и в `.kodla/RESEARCH.md` есть непустая тема в `Активном резюме`,
можно использовать её как описание задачи без дополнительного вопроса о теме.

### Шаг 2. Разбор описания

Разбери `$ARGUMENTS`:

- Если аргументы не пусты — это описание фичи или задачи
- Если аргументы пусты:

```
AskUserQuestion: Что нужно реализовать?
Опиши фичу, задачу или проблему которую нужно решить.
```

Из описания извлеки:
- Основную суть (что добавляем/меняем/исправляем)
- Ключевые термины предметной области
- Тип изменения (фича, улучшение, исправление, рефакторинг)

Сгенерируй slug: строчные буквы, дефисы вместо пробелов, максимум 50 символов.

Пример: "добавить авторизацию пользователей" → `add-user-auth`

---

### Шаг 3. Быстрая разведка кодовой базы

Запусти 1-2 Explore-агента параллельно для понимания контекста:

```
Agent(subagent_type: Explore, prompt:
  "В [корень проекта] найди файлы и модули связанные с [ключевые термины из описания].
   Выдай: ключевые директории, релевантные файлы, существующие паттерны, точки интеграции.
   Уровень детализации: quick. Краткая структурированная сводка.")
```

Второй агент — при необходимости:

```
Agent(subagent_type: Explore, prompt:
  "Найди в проекте существующие примеры похожей функциональности — [паттерны из описания].
   Покажи как это сделано сейчас: структура файлов, классы, методы.
   Уровень детализации: quick.")
```

Пропусти этот шаг если описание проекта в `.kodla/DESCRIPTION.md` уже даёт достаточный контекст.

---

### Шаг 4. Вопросы предпочтений

```
AskUserQuestion: Несколько вопросов перед созданием плана:

1. Писать тесты для этой фичи?
   а. Да — включить задачи на тесты
   б. Нет — пропустить тесты

2. Уровень логирования для реализации?
   а. Подробный — DEBUG/diagnostic логи для разработки (рекомендуется)
   б. Стандартный — ключевые INFO-события
   в. Минимальный — только WARN/ERROR

3. Политика документации после реализации?
   а. Да — добавить обязательную проверку документации
   б. Нет — только предупреждение, без обязательной задачи

4. Привязать план к milestone из `.kodla/ROADMAP.md`?
   а. Да — выбрать milestone (только если roadmap существует)
   б. Нет — пропустить

5. Специфические требования или ограничения?
   (производительность, безопасность, обратная совместимость и т.д.)
```

Сохрани ответы — они войдут в план и секцию настроек.

Если roadmap существует и пользователь выбрал привязку — прочитай roadmap, покажи
кандидатные незавершённые milestone и сохрани выбранный milestone с кратким обоснованием.

---

### Шаг 5. Инициализация файла плана

Создай файл плана через бинарник:

```bash
kodla plan-init <slug>
```

Команда создаст `.kodla/plans/<slug>.md` с пустым шаблоном. Если файл уже существует — команда сообщит об этом и продолжит без ошибки.

---

### Шаг 6. Глубокое исследование кодовой базы

На основе данных из шага 3 запусти 2-3 Explore-агента для детального понимания:

```
Агент 1 — Архитектура и затронутые модули:
Agent(subagent_type: Explore, prompt:
  "Детально изучи файлы и модули связанные с [предметная область].
   Опиши директорную структуру, ключевые точки входа, взаимодействие модулей.
   Уровень детализации: medium.")

Агент 2 — Существующие паттерны и соглашения:
Agent(subagent_type: Explore, prompt:
  "Найди примеры уже реализованной похожей функциональности.
   Покажи паттерны для [тип изменений: эндпоинты, сервисы, модели и т.д.].
   Уровень детализации: medium.")

Агент 3 — Зависимости (при необходимости):
Agent(subagent_type: Explore, prompt:
  "Найди все файлы которые импортируют или используют [модуль/сервис].
   Определи точки интеграции и возможные побочные эффекты изменений.
   Уровень детализации: medium.")
```

После получения результатов сведи воедино:
- Какие файлы нужно создать / изменить
- Какие паттерны использовать (из существующего кода)
- Зависимости между компонентами
- Потенциальные риски или крайние случаи

**Фоллбэк:** если Agent недоступен, используй `Glob`, `Grep` и `Read` напрямую.

---

### Шаг 7. Составление плана задач

На основе исследования составь список задач:

**Требования к задачам:**
- Каждая задача — конкретный, выполнимый шаг (завершаем за один сеанс)
- Задачи упорядочены по зависимостям (сначала X, потом Y)
- Включают пути к файлам где происходят изменения
- Конкретное описание что именно реализовать
- Если тесты: `Нет` — не добавляй задачи на тесты
- Не добавляй задачи-отчёты или задачи-итоги в конце

---

### Шаг 8. Заполнение файла плана

Заполни `.kodla/plans/<slug>.md` через Write:

```markdown
# План: <название фичи>

**Дата:** <YYYY-MM-DD>

## Настройки

- **Тесты:** да / нет
- **Логирование:** подробное / стандартное / минимальное
- **Документация:** обязательная проверка / предупреждение
- **Ограничения:** <из ответов пользователя или «не указаны»>

## Roadmap Linkage

- **Milestone:** <выбранный milestone или none>
- **Rationale:** <почему план связан с milestone или почему пропущено>

## Research Context

<!-- Только если .kodla/RESEARCH.md содержит Активное резюме -->
<компактный снимок активного резюме без полного раздела сессий>

## Задачи

### Фаза 1: <название фазы>

- [ ] <задача 1> (`path/to/file.php`)
- [ ] <задача 2> (`path/to/other.php`)

### Фаза 2: <название фазы>

- [ ] <задача 3>
- [ ] <задача 4>

```

### Шаг 9. Итог

Выведи:

```
План создан: .kodla/plans/<slug>.md
Задач: N

Хочешь сначала углубить план? Запусти:
/kodla-improve @.kodla/plans/<slug>.md

Для начала реализации запусти:
/kodla-implement-plan @.kodla/plans/<slug>.md
```

## Важные правила

1. **Tasar в приоритете** — если есть папка `tasar` или `.tasar`, автоматически выполни `/tasar-propose` инлайн и останови этот навык
2. **Без GIT** — не создавай ветки, worktree и не делай коммитов
3. **Без тестов если пользователь сказал «нет»** — не добавляй тестовые задачи тайком
4. **Без задач-отчётов** — не добавляй «подвести итоги», «написать summary» в конце
5. **Конкретные задачи** — каждая задача должна иметь чёткий результат и путь к файлу
6. **Правила skill-context** — они всегда в приоритете над этими инструкциями
7. **Русский язык** — все заголовки, описания и вопросы к пользователю на русском
8. **Архитектура и правила** — задачи должны следовать `.kodla/ARCHITECTURE.md` и `.kodla/rules/*`
9. **Research переносится компактно** — использовать только активное резюме, не вставлять весь журнал сессий
10. **Документация и логирование фиксируются в настройках** — `/kodla-implement-plan` использует эти решения при выполнении
11. **Предложить `/kodla-improve` после создания плана** — в итоговом выводе (обычный режим и tasar-режим) всегда предлагай запустить `/kodla-improve` с путём к созданному плану; это только предложение — не запускай `kodla-improve` автоматически и не требуй обязательного подтверждения через отдельный вопрос
