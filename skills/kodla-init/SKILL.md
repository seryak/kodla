# Kodla Init — Настройка AI-контекста проекта

Настраивает AI-контекст для проекта:
1. Определяет технологический стек
2. Разрешает языковые настройки
3. Генерирует `.kodla/config.yaml`
4. Генерирует `.kodla/DESCRIPTION.md`
5. Генерирует `.kodla/rules/base.md`
6. Генерирует `AGENTS.md`
7. Проверяет доступность tasar и предлагает инициализировать
8. Проверяет Laravel-стек и предлагает настроить статический анализ

## Определение режима

```
Проверь $ARGUMENTS:
├── Есть описание? → Режим 2: Новый проект с описанием
└── Нет аргументов?
    └── Есть файлы проекта? (package.json, composer.json, pyproject.toml, go.mod и т.д.)
        ├── Да → Режим 1: Анализ существующего проекта
        └── Нет → Режим 3: Интерактивный новый проект
```

## Разрешение языковых настроек

Разреши языковые настройки **сразу после определения режима**, до генерации любых артефактов.

**Языковые переменные:**
- `language.ui` — язык для `AskUserQuestion`, пояснений, итогового сообщения
- `language.artifacts` — язык для всех генерируемых файлов: `DESCRIPTION.md`, `rules/base.md`, `AGENTS.md`
- `language.code_comments` — язык комментариев в коде проекта
- `git.commit_language` — язык сообщений коммитов (используется `/kodla-commit`)

**Порядок разрешения (для каждой отсутствующей переменной):**
1. `.kodla/config.yaml` → `language.ui` / `language.artifacts`
2. `AGENTS.md` (поиск подсказок по языку контента)
3. `CLAUDE.md` (поиск языковых инструкций) — актуально только пока `CLAUDE.md` не является симлинком на `AGENTS.md`; если это симлинк, он физически совпадает с `AGENTS.md` и отдельно проверять его не нужно
4. `.kodla/rules/base.md` (если уже существует и явно задаёт язык)
5. Спросить у пользователя

**Алгоритм:**
1. Прочитать `.kodla/config.yaml` если существует. Если оба ключа заполнены — использовать, не спрашивать.
2. Если один или оба ключа отсутствуют — проверить `AGENTS.md` и `CLAUDE.md`.
3. Если всё ещё не найдено — проверить `.kodla/rules/base.md`.
4. Если всё ещё не найдено — спросить через `AskUserQuestion`:

```
AskUserQuestion: На каком языке вести общение?
Варианты:
1. Русский (ru) — По умолчанию
2. English (en)
3. Другой — указать вручную
```

```
AskUserQuestion: На каком языке генерировать файлы (DESCRIPTION.md, AGENTS.md, rules)?
Варианты:
1. Такой же как язык общения (Рекомендуется)
2. English (en)
3. Другой — указать вручную
```

**Язык коммитов:**

Разреши `git.commit_language` в рамках этого же шага.

1. Если `.kodla/config.yaml` уже содержит `git.commit_language` — использовать, не спрашивать.
2. Иначе — спросить через `AskUserQuestion`:

```
AskUserQuestion: На каком языке писать сообщения коммитов?
Варианты:
1. English (en) — Рекомендуется для open-source
2. Русский (ru)
3. Другой — указать код языка вручную
```

Значение используется навыком `/kodla-commit`.

Языковые настройки фиксируются на весь запуск и не меняются.

Если в существующем `.kodla/config.yaml` уже задано `language.technical_terms`,
сохрани значение. Если ключ отсутствует — запиши `keep`.

Аналогично для `language.code_comments`: если ключ уже задан в существующем
`.kodla/config.yaml` — сохрани значение, не спрашивать. Если ключ отсутствует —
запиши `ru` (значение по умолчанию), без вопроса пользователю.

## Project skill-context

Прочитай `.kodla/skill-context/kodla-init/SKILL.md` если файл существует.

Этот файл содержит проектно-специфичные правила, накопленные `/kodla-evolve`.
Правила skill-context имеют приоритет над общими инструкциями этого навыка.
Они применяются ко всем выходным артефактам `kodla-init`: `.kodla/DESCRIPTION.md`,
`.kodla/rules/base.md`, `.kodla/config.yaml` и `AGENTS.md`.

После генерации каждого артефакта проверь его против правил skill-context.
Если правило нарушено — исправь артефакт до итогового сообщения.

## Сохранение конфига

После разрешения языковых настроек записать `.kodla/config.yaml`:

1. Создать директорию: `mkdir -p .kodla`

2. Записать файл `.kodla/config.update.json` через Write:
```json
{
  "mode": "create",
  "set": {
    "language.ui": "<разрешённый-ui>",
    "language.artifacts": "<разрешённый-artifacts>",
    "language.technical_terms": "keep",
    "language.code_comments": "<разрешённый-code-comments>",
    "git.commit_language": "<разрешённый-commit-language>"
  },
  "fillMissing": {
    "git.base_branch": "main",
    "git.branch_prefix": "feature/",
    "rules.base": ".kodla/rules/base.md"
  }
}
```

Если `.kodla/config.yaml` уже существует — использовать `"mode": "merge"`.

3. Запустить:
```bash
kodla config-update --target .kodla/config.yaml --payload .kodla/config.update.json
```

4. Удалить `.kodla/config.update.json` после успешного выполнения.

## Режим 1: Анализ существующего проекта

**Условие:** нет `$ARGUMENTS` + в директории есть файлы проекта.

**Шаг 1: Сканирование проекта**

Прочитать следующие файлы (если существуют):
- `package.json` → Node.js / JS-фреймворк
- `composer.json` → PHP (Laravel, Symfony и т.д.)
- `requirements.txt` / `pyproject.toml` → Python
- `go.mod` → Go
- `Cargo.toml` → Rust
- `docker-compose.yml` → Сервисы
- `prisma/schema.prisma` / `drizzle.config.*` / `alembic/` → схема БД и миграции
- Структура директорий (2-3 уровня)

**Шаг 2: Разрешить язык → Сохранить конфиг** (см. выше)

**Шаг 3: Сгенерировать `.kodla/DESCRIPTION.md`**

Создать на языке `language.artifacts`:

```markdown
# [Название / заголовок проекта]

## [Заголовок: Обзор]
[1-2 предложения описания на основе обнаруженных файлов]

## [Заголовок: Технологический стек]
- **[Метка: Язык]:** [обнаруженный]
- **[Метка: Фреймворк]:** [обнаруженный]
- **[Метка: База данных]:** [если обнаружена]

## [Заголовок: Архитектурные заметки]
[Ключевые наблюдения из структуры файлов]
```

**Шаг 4: Сгенерировать `.kodla/rules/base.md`**

Проанализировать кодовую базу и обнаружить соглашения:
- Именование: camelCase, snake_case, PascalCase (из имён файлов/классов/функций)
- Структура модулей: ключевые директории и их роль
- Обработка ошибок: паттерны try/catch, коды ошибок
- Логирование: используемая библиотека или паттерн

Создать `.kodla/rules/base.md` на языке `language.artifacts`:

```markdown
# [Заголовок: Базовые правила проекта]

> [Примечание: Автоматически обнаружены из кодовой базы. Редактируй по необходимости.]

## [Заголовок: Соглашения об именовании]
- Файлы: [паттерн]
- Переменные: [паттерн]
- Классы: [паттерн]

## [Заголовок: Структура модулей]
- [ключевая директория]: [назначение]

## [Заголовок: Обработка ошибок]
- [обнаруженный паттерн]

## [Заголовок: Логирование]
- [обнаруженный паттерн]
```

**Шаг 5: Сгенерировать `AGENTS.md`** (см. раздел [Генерация AGENTS.md](#генерация-agentsmd))

**Шаг 6: Проверка tasar** (см. раздел [Проверка tasar](#проверка-tasar))

**Шаг 7: Проверка Laravel** (см. раздел [Проверка Laravel](#проверка-laravel))

**Шаг 8: Итоговое сообщение** на языке `language.ui`. Упомянуть создание (или, при конфликте, решение пользователя) `CLAUDE.md` как симлинка на `AGENTS.md`, результат проверки tasar (инициализирован / пропущено), и результат проверки Laravel (kodla-larastan запущен / пропущено).

## Режим 2: Новый проект с описанием

**Условие:** `$ARGUMENTS` содержит описание проекта.

**Шаг 1: Разрешить язык → Сохранить конфиг** (см. выше)

**Шаг 2: Интерактивный выбор стека**

На основе описания задать уточняющие вопросы на языке `language.ui`. Показывать рекомендацию с пометкой "(Рекомендуется)".

Спросить о (пропускать неприменимые категории):
1. Язык программирования
2. Фреймворк
3. База данных (если применимо)
4. ORM / query builder (если применимо)
5. Внешние интеграции (если пользователь их упомянул)

**Шаг 3: Сгенерировать `.kodla/DESCRIPTION.md`**

После подтверждения выбора создать на языке `language.artifacts`:

```markdown
# [Название проекта из описания]

## [Заголовок: Обзор]
[Расширенное описание на основе ввода пользователя]

## [Заголовок: Основные функции]
- [Функция 1]
- [Функция 2]

## [Заголовок: Технологический стек]

- **[Метка: Фреймворк]:** [выбор пользователя]
- **[Метка: База данных]:** [выбор пользователя]
- **[Метка: ORM]:** [выбор пользователя, если применимо]
- **[Метка: Интеграции]:** [интеграции, если применимо]

## [Заголовок: Архитектурные заметки]
[Высокоуровневые решения на основе выбранного стека]

## [Заголовок: Нефункциональные требования]
```

**Шаг 4: Сгенерировать `.kodla/rules/base.md`**

Для нового проекта — минимальные правила на основе соглашений выбранного стека.

**Шаг 5: Сгенерировать `AGENTS.md`** (см. ниже)

**Шаг 6: Проверка tasar** (см. раздел [Проверка tasar](#проверка-tasar))

**Шаг 7: Проверка Laravel** (см. раздел [Проверка Laravel](#проверка-laravel))

## Режим 3: Интерактивный новый проект

**Условие:** нет `$ARGUMENTS` + пустая директория (нет узнаваемых файлов проекта).

**Шаг 1: Разрешить язык → Сохранить конфиг** (см. выше)

**Шаг 2: Спросить описание**

На языке `language.ui`:
```
Здесь нет существующего проекта. Давай создадим!

Что ты строишь?
(например: "CLI для обработки файлов", "REST API", "Laravel-приложение", "Next.js сайт")

> ___
```

**Шаги 3–8:** Аналогично Режиму 2.

## Генерация AGENTS.md

Сгенерировать `AGENTS.md` в **корне проекта** как структурную карту для AI-агентов.

Сканировать проект:
- Прочитать дерево директорий (2-3 уровня)
- Определить ключевые точки входа и конфигурационные файлы
- Использовать `.kodla/DESCRIPTION.md` для информации о стеке

Использовать язык `language.artifacts` для всех заголовков и текста внутри файла. Имя файла `AGENTS.md` не менять.

**Шаблон:**

```markdown
# AGENTS.md

> [Примечание: Обновляй этот файл при значительных изменениях структуры проекта.]

## [Заголовок: Обзор проекта]
[1-2 предложения из DESCRIPTION.md]

## [Заголовок: Технологический стек]
- **[Метка: Язык]:** [язык]
- **[Метка: Фреймворк]:** [фреймворк]
- **[Метка: База данных]:** [база данных, если есть]

## [Заголовок: Структура проекта]
\`\`\`
[дерево директорий с пояснениями для каждой]
\`\`\`

## [Заголовок: Ключевые точки входа]
| [Заголовок: Файл] | [Заголовок: Назначение] |
|-------------------|-------------------------|
| [главный файл]    | [описание]              |
| [конфиг-файл]     | [описание]              |

## [Заголовок: Документация]
| [Заголовок: Документ]     | [Заголовок: Путь]          | [Заголовок: Описание] |
|---------------------------|----------------------------|-----------------------|
| README                    | README.md                  | [описание]            |
| Описание AI-контекста     | .kodla/DESCRIPTION.md      | [описание]            |

## [Заголовок: Файлы AI-контекста]
| [Заголовок: Файл]     | [Заголовок: Назначение] |
|-----------------------|-------------------------|
| AGENTS.md             | [описание]              |
| CLAUDE.md             | Симлинк на AGENTS.md — для совместимости с Claude Code |
| .kodla/config.yaml    | [описание]              |
| .kodla/DESCRIPTION.md | [описание]              |
| .kodla/rules/base.md  | [описание]              |

## [Заголовок: Правила для агентов]
- [Правило: разбивай составные shell-команды на отдельные шаги]
```

**Создание CLAUDE.md**

`AGENTS.md` — формат, который уже понимают Codex, Cursor, Copilot и Gemini CLI. Claude Code ищет `CLAUDE.md`. Чтобы не поддерживать две независимые копии одного контекста, `CLAUDE.md` создаётся как символическая ссылка на `AGENTS.md`.

После записи `AGENTS.md` выполнить:

1. Проверить состояние `CLAUDE.md`:
   - **Не существует** → создать симлинк: `ln -sf AGENTS.md CLAUDE.md` (из корня проекта, относительный таргет).
   - **Уже симлинк на `AGENTS.md`** → ничего не делать (идемпотентно).
   - **Существует как обычный файл или симлинк на что-то другое** → не перезаписывать молча. Спросить через `AskUserQuestion` на языке `language.ui`, заменить ли независимый `CLAUDE.md` симлинком на `AGENTS.md`, или оставить как есть.
2. Если пользователь подтвердил замену — выполнить `ln -sf AGENTS.md CLAUDE.md`. Если отказался — оставить существующий `CLAUDE.md` без изменений и упомянуть это в итоговом сообщении.

## Проверка tasar

Выполнить после генерации `AGENTS.md`, до итогового сообщения.

**Условие пропуска:** если в проекте уже существует `tasar/` или `.tasar/` — пропустить этот шаг целиком, tasar уже инициализирован.

**Проверка доступности:**
1. Утилита: `command -v tasar` (bash) — доступна ли команда `tasar` в PATH.
2. Навыки tasar: доступен ли навык `tasar-propose` в списке навыков, перечисленных агенту в текущей сессии (system-reminder со списком skills). Наличие `tasar-propose` считается индикатором, что `tasar-apply` и `tasar-archive` тоже установлены — они ставятся одним комплектом.

Если хотя бы одно из двух условий не выполнено — пропустить шаг молча, без вопроса и без упоминания в итоговом сообщении.

Если оба условия выполнены — спросить через `AskUserQuestion`:

```
AskUserQuestion: Обнаружены утилита tasar и навыки tasar-propose/apply/archive, но в этом проекте tasar ещё не инициализирован.
Инициализировать tasar в этом проекте?

Варианты:
1. Да — выполнить tasar init (Рекомендуется)
2. Нет — пропустить
```

**Если «Да»:**
- Выполнить `tasar init` в корне проекта.
- Проверить что создана директория `tasar/`.
- Отметить в итоговом сообщении, что tasar инициализирован и что `/kodla-plan` теперь будет автоматически выполнять `/tasar-propose`.

**Если «Нет»:**
- Не выполнять `tasar init`.
- Не упоминать в итоговом сообщении (пользователь уже видел и отклонил предложение в диалоге).

## Проверка Laravel

Выполнить после проверки tasar, до итогового сообщения.

**Условие пропуска:** пропустить этот шаг целиком, если выполняется хотя бы одно:
- `composer.json` отсутствует
- в `composer.json` нет `laravel/framework` в `require` или `require-dev`
- уже существует `phpstan.neon` или `phpstan.neon.dist` (статический анализ уже настроен)

**Проверка доступности навыка:** доступен ли `kodla-larastan` в списке навыков, перечисленных агенту в текущей сессии (system-reminder со списком skills). Если недоступен — пропустить молча.

Если Laravel обнаружен, PHPStan не настроен, и навык доступен — спросить через `AskUserQuestion`:

```
AskUserQuestion: Обнаружен Laravel-проект (laravel/framework в composer.json).
Настроить статический анализ (PHPStan/Larastan) через /kodla-larastan?

Варианты:
1. Да — запустить /kodla-larastan (Рекомендуется)
2. Нет — пропустить
```

**Если «Да»:**
- Вызвать `/kodla-larastan`.
- Отметить в итоговом сообщении, что статический анализ настроен через `kodla-larastan`.

**Если «Нет»:**
- Не вызывать `kodla-larastan`.
- Не упоминать в итоговом сообщении (пользователь уже видел и отклонил предложение в диалоге).

## Правила

1. **Не устанавливать сторонние скиллы** — не запускать `npx skills`, `pip install` и другие менеджеры пакетов для AI-скиллов
2. **Не настраивать MCP** — не изменять `.mcp.json` или другие MCP-конфиги
3. **Не запускать проверку безопасности** — не запускать security-scan.py или аналогичные инструменты
4. **`.kodla/` — директория конфигурации** — никогда не писать в legacy-директории других систем AI-контекста
5. **Использовать `kodla config-update`** — никогда не записывать `.kodla/config.yaml` напрямую без хелпера
6. **Языковые настройки фиксированы** — после разрешения не менять язык в середине работы
