# Docs — Генератор документации проекта

Генерируй, поддерживай и улучшай документацию проекта по структуре: лаконичный README как landing-page + детальные страницы в директории docs/.

## Основные принципы

1. **README — это landing page, не мануал.** ~80–120 строк. Первое впечатление, установка, быстрый пример, ссылки на детали.
2. **Детали идут в директорию docs/** (`paths.docs`, по умолчанию: `docs/`). Каждый файл самодостаточен — одна тема, одна страница. Пользователь должен получить полную картину по теме, прочитав один файл.
3. **Без дублирования.** Если информация есть в docs/, README ссылается на неё — не повторяет. Исключение: команда установки может быть в обоих местах (пользователи ожидают её в README).
4. **Навигация.** Каждый файл в docs/ имеет заголовочную строку с ссылками пред/след по порядку из таблицы Documentation: `[← Предыдущая](prev.md) · [Назад к README](<путь-к-README>) · [Следующая →](next.md)`. Первая страница — без ссылки "пред"; последняя — без "след". Каждая страница заканчивается разделом "Смотри также" с 2–3 ссылками на связанные страницы.
5. **Относительные пути в ссылках.** Из README: путь к директории docs/ (например `docs/workflow.md`). Между страницами docs/ в одной директории: `workflow.md`.
6. **Сканируемость.** Используй таблицы, маркированные списки и блоки кода. Избегай длинных абзацев. Пользователи сканируют, а не читают.

## Рабочий процесс

### Шаг 0: Загрузить конфиг и контекст проекта

**СНАЧАЛА:** Прочитай `.kodla/config.yaml` если файл существует, чтобы определить:
- **Пути:** `paths.description`, `paths.architecture` и `paths.docs`
- **Язык:** `language.ui` для подсказок и `language.artifacts` для генерируемой документации

Если `config.yaml` не существует, используй значения по умолчанию:
- DESCRIPTION.md: `.kodla/DESCRIPTION.md`
- ARCHITECTURE.md: `.kodla/ARCHITECTURE.md`
- Директория docs: `docs/`
- Язык: `ru` (русский)

**Примечание:** `README.md` остаётся landing page в корне проекта. Детальная документация пишется в директорию `paths.docs` (по умолчанию: `docs/`).

**ЗАТЕМ:** Прочитай `.kodla/DESCRIPTION.md` (путь из конфига) если файл существует, чтобы понять:
- Технологический стек (язык, фреймворк, база данных)
- Назначение проекта и архитектуру
- Ключевые возможности и соглашения

**Также прочитай `.kodla/ARCHITECTURE.md`** (путь из конфига) если файл существует, чтобы согласовать документацию со структурой и границами проекта.

**Изучи кодовую базу:**
- Прочитай `package.json`, `composer.json`, `requirements.txt`, `go.mod`, `Cargo.toml` и т.д.
- Сканируй структуру `src/` чтобы понять архитектуру
- Ищи существующую документацию, комментарии, API-эндпоинты, CLI-команды
- Проверь существующий README.md и директорию docs/

**Прочитай `.kodla/skill-context/kodla-docs/SKILL.md`** — ОБЯЗАТЕЛЬНО если файл существует.

Этот файл содержит специфичные для проекта правила, накопленные `/kodla-evolve` из патчей,
соглашений кодовой базы и анализа технологического стека. Правила адаптированы к текущему проекту.

**Как применять правила skill-context:**
- Относись к ним как к **переопределениям уровня проекта** для общих инструкций этого навыка
- Когда правило skill-context конфликтует с общим правилом из этого SKILL.md,
  **правило skill-context имеет приоритет** (более специфичный контекст важнее — тот же принцип, что и вложенные CLAUDE.md)
- При отсутствии конфликта применяй оба: общие правила из SKILL.md + правила проекта из skill-context
- НЕ игнорируй правила skill-context даже если они кажутся противоречащими умолчаниям навыка —
  они существуют потому что опыт проекта доказал недостаточность умолчания
- **КРИТИЧЕСКИ:** правила skill-context применяются ко ВСЕМ выходным артефактам этого навыка — включая README.md,
  страницы документации и их шаблоны. Шаблоны в этом SKILL.md — **базовые структуры**.
  Если правило skill-context говорит "docs MUST include X" или "README MUST have section Y" — ты ОБЯЗАН
  дополнить шаблоны соответственно. Генерация документации нарушающей правила skill-context — это баг.

**Проверка:** После генерации любого выходного артефакта проверь его на соответствие всем правилам skill-context.
Если правило нарушено — исправь вывод до показа пользователю.

**Поиск разбросанных markdown-файлов в корне проекта:**

Используй `Glob` для поиска всех `*.md` файлов в корне проекта (исключая `node_modules/`, `.kodla/`, директории агентов):

SECURITY.md, API.md, SETUP.md, DEVELOPMENT.md, TESTING.md, и т.д.

Состояние C: README.md + docs/ существуют            → Зависит от флагов (см. ниже)
```

**Состояние C с флагом `--web` — спроси пользователя:**

```
Документация уже существует (README.md + директория docs/).

AskUserQuestion: Что вы хотите сделать?

Варианты:
1. Сгенерировать только HTML — собрать сайт из текущих docs/
2. Сначала проверить и улучшить — найти проблемы, затем сгенерировать HTML

**На основе выбора:**
- Только HTML → пропустить Шаг 1.1, Шаг 2, Шаг 4 — перейти к Шагу 3 (генерация HTML), затем готово
- Сначала улучшить → Шаг 1.1 → Шаг 2 (Состояние C) → Шаг 3 → Шаг 4 → Шаг 4.1
- Только проверить → Шаг 1.1 → Шаг 2 (Состояние C) → Шаг 4 → Шаг 4.1 (Шаг 3 пропустить)

**Состояние C без флага `--web`** → выполнить Шаг 2 (Состояние C) как обычно.

### Шаг 1.1: Проверить разбросанные Markdown-файлы

Если в корне проекта найдены разбросанные `.md` файлы (из Шага 0), предложи объединить их в директорию docs/.

**Файлы, которые следует переместить:**

| Файл в корне | Целевой файл в docs/ | Переместить или слить? |
|-----------|-----------------|----------------|
| `CONTRIBUTING.md` | `<docs>/contributing.md` | Переместить |
| `ARCHITECTURE.md` | `<docs>/architecture.md` | Переместить |
| `DEPLOYMENT.md` | `<docs>/deployment.md` | Переместить |
| `SETUP.md` | `<docs>/getting-started.md` | Слить (добавить к существующему) |
| `DEVELOPMENT.md` | `<docs>/getting-started.md` или `<docs>/contributing.md` | Слить |
| `API.md` | `<docs>/api.md` | Переместить |
| `TESTING.md` | `<docs>/testing.md` | Переместить |
| `SECURITY.md` | `<docs>/security.md` | Переместить |

**Файлы, остающиеся в корне** (стандартное соглашение):
- `README.md` — остаётся всегда
- `CHANGELOG.md` — стандартный файл в корне, оставить как есть
- `LICENSE` / `LICENSE.md` — стандартный файл в корне, оставить как есть
- `CODE_OF_CONDUCT.md` — стандартный файл в корне, оставить как есть

**При обнаружении разбросанных файлов, спроси пользователя:**

```
Найдено [N] markdown-файлов в корне проекта:

  CONTRIBUTING.md (45 строк) — инструкции для участников
  ARCHITECTURE.md (120 строк) — обзор архитектуры системы
  DEPLOYMENT.md (80 строк) — инструкции по развёртыванию
  SETUP.md (30 строк) — руководство по установке (пересекается с getting-started)

Предлагаемые действия:
  → Переместить CONTRIBUTING.md → <docs>/contributing.md
  → Переместить ARCHITECTURE.md → <docs>/architecture.md
  → Переместить DEPLOYMENT.md → <docs>/deployment.md
  → Слить SETUP.md в <docs>/getting-started.md

AskUserQuestion: Хотите применить консолидацию?

Варианты:
1. Применить все предложения
2. Выбрать самостоятельно
3. Пропустить — оставить файлы на месте
```

**На основе выбора:**
- Применить все → переместить/слить все перечисленные файлы, продолжить Шаг 2
- Выбрать самостоятельно → предложить каждый файл отдельно для одобрения, применить выбранные
- Пропустить → оставить файлы, продолжить Шаг 2

**При перемещении/слиянии:**
1. Создать целевой файл в docs/ с навигационным заголовком пред/след (по порядку из таблицы Documentation) и footer "Смотри также"
2. При слиянии в существующий doc — добавить контент под новым заголовком раздела, избегая дублирования уже существующей информации
3. **НЕ удалять оригиналы** — хранить до подтверждения в шаге ревью
4. Добавить новую страницу docs/ в таблицу Documentation README с правильным относительным путём
5. Обновить все ссылки в других файлах, указывающие на старый файл в корне
6. Записать какие файлы были перемещены/слиты — этот список используется в Шаге 4.1

**ВАЖНО:** Никогда не перемещать файлы принудительно. Всегда показывать план и получить одобрение пользователя.

### Шаг 2 (Состояние A): Генерация с нуля

Когда README.md отсутствует — сгенерировать полный комплект документации.

#### 2.1: Анализ проекта для определения тем документации

Изучи кодовую базу и определи темы:

```
Всегда включать:
- getting-started.md    (установка, настройка, быстрый старт)

Включить если релевантно:
- architecture.md       (если проект имеет чёткую архитектуру: сервисы, модули, слои)
- api.md                (если проект предоставляет API-эндпоинты)
- configuration.md      (если есть конфиг-файлы, переменные окружения, feature flags)
- deployment.md         (если есть Dockerfile, CI/CD, скрипты развёртывания)
- contributing.md       (если open-source или командный проект)
- security.md           (если есть аутентификация, права доступа, паттерны безопасности)
- testing.md            (если есть тестовый набор)
- cli.md                (если проект имеет CLI-команды)
```

**Спроси пользователя:**

```
Я проанализировал проект и предлагаю следующие страницы документации:

1. getting-started.md — Установка, настройка, быстрый старт
2. architecture.md — Структура проекта и паттерны
3. api.md — Справочник API-эндпоинтов
4. configuration.md — Переменные окружения и конфиг

AskUserQuestion: Создать эти страницы документации?

Варианты:
1. Создать все
2. Выбрать самостоятельно
3. Добавить дополнительные темы
```

**На основе выбора:**
- Создать все → сгенерировать README.md и все указанные файлы docs/
- Выбрать самостоятельно → предложить каждую тему отдельно, создать только одобренные
- Добавить темы → спросить о дополнительных темах, подтвердить итоговый список, затем создать

#### 2.2: Генерация README.md

Структура (~80–120 строк):

```markdown
# Название проекта

> Однострочный тагстрок описывающий проект.

Краткое описание проекта в 2–3 предложениях: что делает и зачем существует.

## Быстрый старт

\`\`\`bash
# Шаги установки (1–3 команды)
\`\`\`

## Ключевые возможности

- **Возможность 1** — краткое описание
- **Возможность 2** — краткое описание
- **Возможность 3** — краткое описание

## Пример

\`\`\`
# Реальный пример использования — здесь пользователь решает "я хочу это"
\`\`\`

---

## Документация

| Руководство | Описание |
|-------------|----------|
| [Быстрый старт](<путь-к-docs>/getting-started.md) | Установка, настройка, первые шаги |
| [Архитектура](<путь-к-docs>/architecture.md) | Структура проекта и паттерны |
| [API](<путь-к-docs>/api.md) | Эндпоинты, форматы запросов/ответов |
| [Конфигурация](<путь-к-docs>/configuration.md) | Переменные окружения, конфиг-файлы |

## Лицензия

MIT (или то что указано в проекте)
```

**Ключевые правила для README:**
- Строка с логотипом/значками вверху (если у проекта есть)
- Тагстрок как blockquote
- Быстрый старт с реальными командами установки (определить из менеджера пакетов)
- Ключевые возможности как маркированный список (3–6 пунктов, сканируемо)
- Реальный пример использования показывающий "wow-момент"
- Таблица документации со ссылками в docs/
- Лицензия внизу
- **НЕ добавлять длинные описания, полный справочник API, детали конфигурации**

#### 2.3: Генерация файлов документации в docs/

Для каждой одобренной темы создать файл:

```markdown
[← Предыдущая тема](previous-topic.md) · [Назад к README](<путь-к-README>) · [Следующая тема →](next-topic.md)

# Заголовок темы

Контент организованный по подтемам с заголовками, примерами кода и таблицами.
Каждый раздел самодостаточен.

## Смотри также

- [Связанная тема 1](related-topic.md) — краткое описание
- [Связанная тема 2](other-topic.md) — краткое описание
```

**Порядок навигационных ссылок** соответствует таблице Documentation в README.md (сверху вниз). Первая страница docs/ не имеет ссылки "← Предыдущая"; последняя — не имеет "→ Следующая". Используй правильный относительный путь из docs/ к `README.md`. Пример для стандартного расположения `docs/`:

```
getting-started.md:  [Назад к README](../README.md) · [Архитектура →](architecture.md)
architecture.md:     [← Быстрый старт](getting-started.md) · [Назад к README](../README.md) · [API →](api.md)
api.md:              [← Архитектура](architecture.md) · [Назад к README](../README.md) · [Конфигурация →](configuration.md)
configuration.md:    [← API](api.md) · [Назад к README](../README.md)
```

**Руководство по контенту для каждой темы:**

**getting-started.md:**
- Предварительные требования (версии рантайма, необходимые инструменты)
- Пошаговая установка
- Первый запуск / быстрый старт
- Проверка работы (ожидаемый вывод)
- Ссылки на следующие шаги

**architecture.md:**
- Высокоуровневый обзор (диаграмма если полезна)
- Структура директорий с пояснениями
- Ключевые паттерны (именование, импорты, обработка ошибок)
- Поток данных

**api.md:**
- Базовый URL / конфигурация
- Аутентификация
- Эндпоинты сгруппированные по ресурсу
- Примеры запросов/ответов
- Коды ошибок

**configuration.md:**
- Все переменные окружения с описаниями и значениями по умолчанию
- Конфиг-файлы и их назначение
- Feature flags

**deployment.md:**
- Шаги сборки
- Настройка окружения
- Описание CI/CD пайплайна
- Мониторинг / проверки здоровья

### Шаг 2 (Состояние B): Разбивка существующего README в docs/

Когда README.md существует, но длинный (150+ строк) и директории docs/ ещё нет.

#### 2.1: Анализ структуры README

Прочитай README.md и определи:
- Какие разделы остаются (контент landing page)
- Какие разделы переходят в docs/ (детальный контент)

**Остаётся в README:**
- Заголовок, тагстрок, значки
- "Зачем?" / ключевые возможности (список)
- Краткая установка (1–3 команды)
- Краткий пример
- Таблица ссылок на документацию
- Внешние ссылки, лицензия

**Переходит в docs/:**
- Детальные инструкции по установке → `getting-started.md`
- Архитектура / структура проекта → `architecture.md`
- Полный справочник API → `api.md`
- Детали конфигурации → `configuration.md`
- Инструкции для участников → `contributing.md`
- Любой раздел длиннее ~30 строк, покрывающий одну тему

#### 2.2: Предложить изменения пользователю

```
README.md содержит [N] строк. Предлагаю разбивку:

README.md (~100 строк) — оставить как landing page:
  ✓ Заголовок + тагстрок
  ✓ Ключевые возможности
  ✓ Краткая установка
  ✓ Пример
  ✓ Таблица ссылок на документацию

Перенести в docs/:
  → Раздел "Установка" → <docs>/getting-started.md
  → Раздел "Конфигурация" → <docs>/configuration.md
  → Раздел "API Reference" → <docs>/api.md
  → Раздел "Архитектура" → <docs>/architecture.md

Продолжить?
```

#### 2.3: Выполнить разбивку

1. Создать директорию docs/
2. Создать каждый файл с контентом из README + навигационный заголовок пред/след (по порядку из таблицы Documentation) + footer "Смотри также"
3. Переписать README как landing page с таблицей ссылок на документацию
4. **Проверить что контент не потерян** — каждый раздел из старого README должен быть где-то

### Шаг 2 (Состояние C): Улучшение существующей документации

Когда и README.md и директория docs/ уже существуют.

#### 2.1: Аудит текущей документации

Проверить:
- **Длина README** — всё ещё является landing page (<150 строк)?
- **Отсутствующие темы** — есть ли аспекты проекта не задокументированные?
- **Устаревший контент** — ссылаются ли docs/ на файлы/API которых больше нет?
- **Навигация** — все ли docs/ имеют заголовочные ссылки пред/след и "Смотри также"?
- **Битые ссылки** — проверить что все внутренние ссылки ведут на существующие файлы/якоря
- **Единообразие** — одинаковый стиль форматирования во всех docs/
- **Соответствие стандартам** — соответствует ли документация текущим стандартам навыка? (см. 2.1.1)

#### 2.1.1: Проверка соответствия стандартам

Проверить существующие docs/ на соответствие текущим Основным принципам (отсутствующая навигация, отсутствующий "Смотри также", устаревшие форматы). Полная таблица соответствия и правила автоисправления → прочитай `references/REVIEW-CHECKLISTS.md` (секция "Проверка соответствия стандартам").

**При обнаружении несоответствий** — включить их в отчёт аудита вместе с проблемами контента (Шаг 2.2). Обрабатывать как обычные улучшения — показать план и получить одобрение пользователя перед применением.

#### 2.2: Предложить улучшения

```
Результаты аудита документации:

⚠️  Страницы docs/ не имеют навигации пред/след — добавлю
⚠️  docs/api.md отсутствует — у проекта 12 API-эндпоинтов
⚠️  docs/configuration.md ссылается на устаревшую переменную DB_HOST (теперь DATABASE_URL)

Предлагаемые исправления:
1. Добавить навигацию пред/след всем страницам docs/
2. Создать docs/api.md со справочником эндпоинтов

Применить исправления?
```

### Шаг 3: Генерация HTML-версии (флаг --web)

При передаче флага `--web` сгенерировать статический HTML-сайт из markdown-документации.

#### 3.1: Создать директорию docs-html/

```bash
mkdir -p docs-html
```

#### 3.2: Сгенерировать HTML-файлы

Для каждого markdown-файла (README.md + `<docs>/*.md`) сгенерировать HTML-версию:

Прочитай HTML-шаблон из `templates/html-template.html` и используй его для каждой страницы.
Подстановки: `{page_title}`, `{project_name}`, `{nav_links}`, `{content}`.

#### 3.3: Конвертация markdown в HTML

Для каждого файла: разобрать markdown → конвертировать в HTML-элементы → исправить ссылки `.md` на `.html` → сгенерировать nav-бар → записать в `docs-html/`.

## Шаг 4: Ревью документации

**ОБЯЗАТЕЛЬНО после любого изменения контента** (генерация, разбивка, улучшение, консолидация файлов). Не пропускать.

**Пропустить этот шаг** только при выборе "Только HTML" — контент не изменялся, ревью не нужно.

Прочитай каждый сгенерированный/изменённый файл и проверь по обоим чек-листам из `references/REVIEW-CHECKLISTS.md`. Два чек-листа: **Технический** и **Читабельность и полнота**.

Исправь найденные проблемы до показа результата пользователю. Выведи результаты в виде компактной таблицы со статусом ✅/❌/⚠️ для каждого пункта.

### Шаг 4.1: Очистка перемещённых файлов

**Только если файлы были перемещены/слиты из корня в docs/ в Шаге 1.1.**

После того как ревью подтвердило что весь контент правильно размещён в docs/, предложить удалить оригинальные файлы в корне:

```
Следующие файлы из корня включены в docs/:

  CONTRIBUTING.md → теперь в docs/contributing.md
  ARCHITECTURE.md → теперь в docs/architecture.md
  DEPLOYMENT.md → теперь в docs/deployment.md
  SETUP.md → слит в docs/getting-started.md

AskUserQuestion: Оригиналы больше не нужны. Удалить их?

Варианты:
1. Да, удалить все оригиналы
2. Выбрать самостоятельно
3. Нет, оставить (уберу позже сам)
```

**На основе выбора:**
- Да, удалить все → удалить все перечисленные оригиналы (см. "При удалении" ниже)
- Выбрать самостоятельно → предложить каждый файл отдельно, удалить только одобренные
- Нет, оставить → оставить оригиналы, перейти к Шагу 5

**При удалении:**
1. Ещё раз проверить что целевой файл в docs/ содержит весь контент из оригинала
2. Удалить файл в корне
3. Выполнить `git status` для показа что было удалено — пользователь может восстановить через `git checkout` если нужно

**НЕ удалять автоматически.** Всегда спрашивать. Пользователь может захотеть временно сохранить оригиналы для сравнения.

### Шаг 5: Обновить AGENTS.md

**После любых изменений документации** обновить секцию Documentation в `AGENTS.md` (если файл существует).

Прочитай `AGENTS.md` и найди секцию `## Documentation`. Обнови её чтобы отразить текущее состояние всех файлов документации:

```markdown
## Documentation
| Документ | Путь | Описание |
|----------|------|----------|
| README | README.md | Landing page проекта |
| Быстрый старт | `<docs>/getting-started.md` | Установка, настройка, первые шаги |
| Архитектура | `<docs>/architecture.md` | Структура проекта и паттерны |
| API | `<docs>/api.md` | Эндпоинты, форматы запросов/ответов |
| Конфигурация | `<docs>/configuration.md` | Переменные окружения, конфиг-файлы |
```

**Правила:**
- Список README.md первым, затем все файлы docs/ в том же порядке что и таблица Documentation в README
- Если файлы были перемещены/слиты из корня в Шаге 1.1 — отразить новые расположения
- Если созданы новые страницы docs/ — добавить их
- Если страницы docs/ удалены — убрать их
- Держать описания краткими (до 10 слов)
- Если `AGENTS.md` не существует — тихо пропустить этот шаг

## Владение артефактами

- Основное владение: `README.md`, `<docs>/*` и секция Documentation в `AGENTS.md`.
- Использование конфига: `config.yaml` определяет `paths.description`, `paths.architecture`, `paths.docs`, `language.ui` и `language.artifacts`.
- Только чтение: `.kodla/DESCRIPTION.md`, `.kodla/ARCHITECTURE.md`, артефакты дорожной карты/правил/исследований — если пользователь явно не просит о более широком редактировании.

## Важные правила

1. **Всегда спрашивать перед изменением** существующей документации — сначала показать план
2. **Никогда не удалять контент** без переноса его в другое место
3. **Определять реальную информацию о проекте** — не выдумывать возможности, читать package.json/конфиг-файлы
4. **Использовать язык проекта** — если README проекта на русском, писать docs/ на русском
5. **Сохранять существующие значки/логотипы** — не удалять при реструктуризации
6. **Добавить в .gitignore** при генерации HTML: добавить `docs-html/` в .gitignore
7. **Граница владения** — этот навык владеет артефактами документации (`README.md`, `<docs>/*` и секция Documentation в `AGENTS.md`), не дорожной картой, RULES.md или артефактами исследований определёнными из конфига

## Актуализация

Сверка с исходным навыком документации подтверждает обязательные элементы:

- README остаётся landing page, а детальные материалы выносятся в `docs/` или путь из `paths.docs`.
- При генерации с нуля выбирать темы документации по фактическому проекту: getting-started, architecture, api, configuration, deployment, contributing, security, testing, cli.
- При улучшении существующих docs проверять устаревшие ссылки, недостающие страницы, навигацию, соответствие конфигу и фактическим entry points.
- При флаге web генерировать HTML-версию только как производный артефакт документации.
- Если в ходе документирования выявлены устойчивые правила проекта, рекомендовать `/kodla-evolve`.
