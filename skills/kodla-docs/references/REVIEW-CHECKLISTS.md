# Чек-листы ревью документации

## Технический чек-лист

Проверь структуру, ссылки и полноту:

- [ ] README.md содержит менее 150 строк
- [ ] README имеет: заголовок, тагстрок, быстрый старт, пример, таблицу документации, лицензию
- [ ] Каждый файл docs/ имеет навигационный заголовок пред/след по порядку из таблицы Documentation
- [ ] Первая страница docs/ не имеет ссылки "← Предыдущая"; последняя — не имеет "→ Следующая"
- [ ] Каждый файл docs/ имеет раздел "Смотри также" в конце с 2–3 связанными ссылками
- [ ] Контент не был потерян при разбивке/реорганизации
- [ ] Все внутренние ссылки работают (нет битых ссылок и мёртвых якорей)
- [ ] Примеры кода используют реальные команды/синтаксис проекта
- [ ] Инструкции по установке реальные и работают (проверено по файлам менеджера пакетов)
- [ ] Нет дублирования контента между README и docs/
- [ ] Нет разбросанных `.md` файлов в корне которые должны быть в docs/

## Чек-лист читабельности — "глазами нового пользователя"

Прочитай каждую страницу как разработчик который **никогда не видел этот проект**. Для каждой страницы проверь:

### Первые 10 секунд (выше сгиба)
- [ ] Могу ли я понять что делает этот проект в течение 10 секунд чтения README?
- [ ] Тагстрок чёткий и конкретный — не расплывчатый маркетинг ("революционное решение")?
- [ ] Есть ли реальная команда установки которую можно скопировать прямо сейчас?

### "Показывай, не рассказывай"
- [ ] Есть ли в README конкретный пример использования (не просто "установи и запусти")?
- [ ] Показывают ли блоки кода реальные команды с реальным выводом, а не абстрактные заглушки?
- [ ] Примеры пригодны для копирования — нет `<placeholder>` который нужно заменять?

### Сканируемость
- [ ] Могу ли я найти любую конкретную тему менее чем за 5 секунд сканируя заголовки?
- [ ] Абзацы короткие (максимум 3–4 строки)? Длинные абзацы пропускают
- [ ] Используются ли списки вместо перечислений через запятую в тексте?
- [ ] Используются ли таблицы для структурированных данных вместо вложенных списков?

### Жаргон и допущения
- [ ] Объясняются ли аббревиатуры при первом употреблении (или есть ссылка на объяснение)?
- [ ] Нет предположений о внутренних знаниях? ("как описано в RFC" — каком RFC?)
- [ ] Поймёт ли каждую страницу junior-разработчик без помощи коллег?

### Навигация и поток
- [ ] После чтения README понятно куда идти дальше?
- [ ] После завершения любой страницы docs/ ведут ли ссылки пред/след и "Смотри также" логически вперёд?
- [ ] Упорядочена ли таблица Documentation в README по пути нового пользователя? (старт → процесс → детали)

### Мотивация
- [ ] Отвечает ли README на вопрос "зачем мне это нужно?" до вопроса "как это работает?"
- [ ] Есть ли "wow-момент" — возможность или пример который заставляет захотеть попробовать?
- [ ] Структура docs/ выглядит привлекательно, а не пугающе? (максимум 6–8 страниц)

## Проверка соответствия стандартам

Docs/ могут быть сгенерированы предыдущей версией этого навыка. Сравни существующую документацию с текущими Основными принципами и шаблонами. Типичные несоответствия для обнаружения:

| Отсутствующий стандарт | Как обнаружить | Автоисправление |
|------------------------|----------------|-----------------|
| Нет навигации пред/след | Заголовок содержит только `[← Назад к README]` без ссылок `·` на соседние страницы | Добавить ссылки пред/след по порядку из таблицы Documentation |
| Нет раздела "Смотри также" | Файл заканчивается без `## Смотри также` | Добавить раздел с 2–3 ссылками на связанные страницы |
| Устаревший формат "Назад к README" | Путь или текст ссылки не соответствуют текущему паттерну | Обновить до текущего формата |
| Отсутствует таблица Documentation в README | В README нет таблицы со ссылками на docs/ | Добавить таблицу |
| README слишком длинный | README более 150 строк при наличии docs/ | Предложить перенести лишний контент в docs/ |

**При обнаружении несоответствий** — включить их в отчёт аудита вместе с проблемами контента (Шаг 2.2). Обрабатывать как обычные улучшения — показать план и получить одобрение пользователя перед применением.

**НЕ спрашивать "была ли это сгенерировано старой версией?"** — просто тихо обнаружить что отсутствует и исправить. Пользователю не нужно знать о версиях навыка; он просто видит что его документация становится лучше.
