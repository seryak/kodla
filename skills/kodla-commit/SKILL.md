# Генератор коммитов (Conventional Commits)

Генерирует сообщения коммитов по спецификации [Conventional Commits](https://www.conventionalcommits.org/).

## Рабочий процесс

**Шаг 1. Читай конфиг**

Прочитай `.kodla/config.yaml` если существует, чтобы определить:
- **Язык коммитов:** `git.commit_language` — язык для тела и темы сообщений коммитов
- **Git настройки:** `git.skip_push_after_commit` для поведения после коммита

Если config.yaml не существует — используй значения по умолчанию:
- Язык коммитов: `en` (английский)
- `skip_push_after_commit: true`

**Если `git.commit_language` не задан в конфиге** (ключ отсутствует или файл не существует):

Предложи создать настройку через AskUserQuestion:

```
Опция git.commit_language не задана в .kodla/config.yaml.
На каком языке писать сообщения коммитов?

Варианты:
1. Английский (en) — рекомендуется для open-source
2. Русский (ru)
3. Другой язык — укажу сам
```

- Если пользователь выбирает 1 или 2 — записать `git.commit_language: <en|ru>` в `.kodla/config.yaml` (создать файл если не существует, добавить ключ если файл есть)
- Если пользователь выбирает "другой" — запросить код языка (например `de`, `fr`, `uk`), затем записать
- После записи продолжить рабочий процесс с выбранным языком

**Шаг 2. Анализируй изменения**

- Выполни `git status` чтобы увидеть staged-файлы
- Выполни `git diff --cached` чтобы увидеть staged-изменения
- Если ничего не staged — покажи предупреждение и предложи добавить файлы

**Шаг 3. Определи тип коммита**

- `feat` — новая функциональность
- `fix` — исправление бага
- `docs` — только документация
- `style` — стиль кода (форматирование, точки с запятой)
- `refactor` — рефакторинг без новых фич и исправлений
- `perf` — улучшение производительности
- `test` — добавление или изменение тестов
- `build` — система сборки или зависимости
- `ci` — конфигурация CI
- `chore` — задачи обслуживания

**Шаг 4. Определи scope**

- По путям файлов (например, `src/auth/` → `auth`)
- Из аргумента если передан
- Необязательно — опусти если изменения затрагивают несколько областей

**Шаг 5. Сформируй сообщение**

- Тема не длиннее 72 символов
- Повелительное наклонение ("добавить" не "добавлен")
- Строчная буква после типа
- Без точки в конце темы

## Формат

```
<тип>(<scope>): <тема>

<тело>

<footer>
```

## Примеры

**Простая фича:**
```
feat(auth): add password reset functionality
```

**Исправление бага с телом:**
```
fix(api): handle null response from payment gateway

The payment API can return null when the gateway times out.
Added null check and retry logic.

Fixes #123
```

**Breaking change:**
```
feat(api)!: change response format for user endpoint

BREAKING CHANGE: user endpoint now returns nested profile object
```

## Поведение

1. Проверь staged-изменения
2. Проанализируй diff
3. Если staged-изменения содержат несвязанную работу (например, фича + баг, или изменения в независимых модулях) — предложи разбить на отдельные коммиты:
   - Покажи какие файлы/hunks к какому коммиту относятся
   - Уточни план разбивки с пользователем через AskUserQuestion
   - При согласии: `git reset HEAD`, затем stage и commit каждой группы отдельно
4. Предложи сообщение коммита
5. Подтверди с пользователем через AskUserQuestion:

   ```
   Предлагаемое сообщение коммита:

   <тип>(<scope>): <тема>

   <тело>

   <footer>

   Варианты:
   1. Закоммитить как есть
   2. Закоммитить только заголовок
   3. Изменить сообщение
   4. Отмена
   ```

   (`<тело>` и `<footer>` показывать в превью только если они присутствуют в сгенерированном сообщении.)

6. Обработай ответ пользователя:
   - **Закоммитить как есть** → выполни `git commit` с полным сообщением (заголовок + тело + footer)
   - **Закоммитить только заголовок** → выполни `git commit -m "<тип>(<scope>): <тема>"` — одна строка, без тела и footer
   - **Изменить сообщение** → запроси скорректированное сообщение, вернись к шагу 5
   - **Отмена** → остановись, не коммить

7. После коммита — поведение определяется конфигом:
   - Если `git.skip_push_after_commit: true` → завершить работу
   - Иначе — предложи push через AskUserQuestion:
     - Если у ветки нет upstream: `git push -u origin <ветка>`
     - Иначе: `git push`

Если передан аргумент (например, `/kodla-commit auth`):
- Использовать как scope
- Или как контекст для сообщения

## Важно

- Никогда не коммить секреты или учётные данные
- Внимательно проверяй большие diff перед коммитом
- НЕ добавляй `Co-Authored-By` или другие trailer-строки об авторстве AI
