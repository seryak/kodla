Написать тесты для PHP-проекта в стиле, согласованном с проектом, и так, чтобы тесты ловили реальные регрессии — а не просто покрывали строки.

Я создам или дополню:
- тесты в `tests/...` (структура зеркалит production-код)
- факти/билдеры в `tests/Fakes/` или `tests/Factories/` — если их не хватает
- (опционально) обновлю существующие тесты при `## MODIFIED Requirements` в delta-спеке

Когда тесты пройдут — если используется tasar, можно запускать `/tasar:archive`.

---

**Входные данные**: запрос должен содержать одно из:
- цель — класс / неймспейс / предметная область / название tasar-спека
- ИЛИ контекст недавно завершённой задачи (после `/tasar:apply`, после `/kodla-implement-plan`)

**Шаги**

1. **Загрузка конфига и контекста**

   **Конфиг проекта:**

   Прочитай `.kodla/config.yaml` если существует. Извлеки:
   - `paths.description` — описание проекта (по умолчанию: `.kodla/DESCRIPTION.md`)
   - `paths.architecture` — архитектура проекта (по умолчанию: `.kodla/ARCHITECTURE.md`)
   - `paths.research` — сохранённые исследования (по умолчанию: `.kodla/RESEARCH.md`)
   - `paths.rules` / `rules.base` — правила проекта (по умолчанию: `.kodla/rules/`)
   - `language.ui` — язык взаимодействия (по умолчанию: `ru`)
   - `language.artifacts` — язык тестов и комментариев (по умолчанию: `ru`)

   **Skill-context (правила `/kodla-evolve`):**

   Прочитай `.kodla/skill-context/kodla-php-test/SKILL.md` если существует.

   Этот файл содержит проектно-специфичные правила, накопленные `/kodla-evolve` на основе опыта работы с этим проектом. Правила из skill-context имеют **приоритет** над общими правилами этого навыка — как вложенные CLAUDE.md переопределяют родительские. Перед созданием тестов проверь финальный результат на соответствие всем правилам skill-context.

   **Контекст проекта:**

   Прочитай файлы если существуют:
   - `.kodla/DESCRIPTION.md` — стек, архитектура, соглашения и нефункциональные требования
   - `.kodla/ARCHITECTURE.md` — структура проекта, границы модулей, правила зависимостей
   - `.kodla/rules/base.md` и именованные правила из конфига — локальные соглашения по именованию и стилю
   - `.kodla/RESEARCH.md` — сохранённое исследование; раздел `Активное резюме` может указывать на область для покрытия тестами

   Используй контекст проекта для корректного выбора namespace, конвенций именования и структуры директорий тестов.

   **Разведка тестового окружения:**

   Прочитай:
   - `composer.json` — определи фреймворк (`phpunit/phpunit` или `pestphp/pest`) и стек (`laravel/framework`, `symfony/framework-bundle`, vanilla)
   - `phpunit.xml`, `phpunit.xml.dist`, `tests/Pest.php` — настройки тестов
   - `tests/TestCase.php` — какие трейты и хелперы (RefreshDatabase, WithFaker, кастомные)
   - 2–3 ближайших существующих теста того же типа (Unit/Feature, того же типа субъекта — Service, Controller, Action) — **обязательно**, для копирования naming, стиля assertion'ов, mocking-подхода
   - `tests/README.md` если есть — там часто документированы конвенции

   Подгрузи нужные референсы:
   - PHPUnit → `references/phpunit.md`
   - Pest → `references/pest.md`
   - Laravel в стеке → `references/laravel.md`
   - tasar в проекте → `references/tasar.md`

   Если ни PHPUnit, ни Pest не установлены — сообщи пользователю и остановись.

2. **Определи режим**

   **Режим A — по цели.** Пользователь указал что покрыть:
   - Конкретный класс — все публичные методы × значимые ветки
   - Предметная область / неймспейс — собери список затронутых классов, представь план до генерации
   - Tasar-спек (`tasar/specs/<name>.md`) — каждый `### Requirement` становится test class'ом, каждый `#### Scenario` — отдельным тестом

   **Режим B — после реализации.** Покрыть только что сделанное:

   Определи источник scope в следующем порядке приоритетов:

   **1. Tasar (приоритет)** — ищи активное изменение:
   ```bash
   ls tasar/changes/ 2>/dev/null | grep -v archive
   ```
   Если нашлось — прочитай `tasks.md` (закрытые `[x]` = что реализовано) и все файлы в `specs/` (`## ADDED Requirements` приоритетнее `## MODIFIED`).

   **2. Kodla-план (fallback)** — если tasar нет:
   ```bash
   ls .kodla/plans/*.md 2>/dev/null
   ```
   Прочитай план. Задачи с `[x]` = реализованный код → scope тестов.
   Задачи с `[ ]` = ещё не реализовано → тесты пока не пишем.
   Используй описание и контекст плана для понимания предметной области.

   **3. Git diff (last resort)** — если ни tasar, ни kodla-план не найдены:
   ```bash
   git diff --name-only HEAD~1 HEAD
   git diff --name-only --cached
   ```
   Фильтруй `*.php` вне `tests/` и `vendor/`. Для каждого файла читай `git diff <file>` — фокусируйся на изменившемся **поведении**, не на каждой строке.

   **Перед генерацией всегда сообщи пользователю определённый scope.** Например: *"По активному изменению `add-task-priority` (закрыто 3 из 4 задач) добавлю тесты на: создание с приоритетом, валидацию неверного значения, дефолт `medium`. Продолжать?"*

3. **Спланируй тесты**

   Используй **TodoWrite** для отслеживания. Для каждого планируемого теста определи:

   - **Путь** — повторяет структуру production-кода. Для Laravel: `tests/Unit/Services/PaymentServiceTest.php` для `app/Services/PaymentService.php`.
   - **Тип** — unit (чистая логика, без IO) или feature/integration (БД, HTTP, очередь). Будь честным: если код пишет в БД, юнит-тест со всеми моками — спектакль. Делай feature.
   - **Тест-кейсы** — по одному на каждое наблюдаемое поведение. Для tasar — по одному на каждый `#### Scenario`.
   - **Edge cases** — null, пустые коллекции, граничные значения, ошибочные ветки. Каждый `if`/`match`/`throw` в проде = отдельная ветка с тестом.

   Перед первой генерацией в новом для тебя проекте прочитай `references/anti-patterns.md` — каталог типовых ошибок LLM при генерации тестов.

4. **Напиши тесты**

   Стиль — **повторяет** существующие тесты проекта (определён в шаге 1). Не вводи свой стиль.

   Конкретные паттерны — в референсах: `references/phpunit.md`, `references/pest.md`, `references/laravel.md`, `references/mocking.md`, `references/tasar.md`.

   Для tasar-сценариев тело теста повторяет `WHEN/THEN`:

   ```
   #### Scenario: Успешное создание
   - **WHEN** клиент отправляет POST с валидными данными
   - **THEN** задача создаётся и возвращается с HTTP 201
   ```

   →

   ```php
   it('создаёт задачу и возвращает HTTP 201 когда POST с валидными данными', function () {
       $response = $this->postJson('/api/tasks', ['name' => 'Buy milk']);

       $response->assertStatus(201);
       expect(Task::query()->where('name', 'Buy milk')->exists())->toBeTrue();
   });
   ```

   Имя теста **цитирует** Scenario, а не пересказывает — для трейсабилити: при падении в CI читатель сразу находит соответствующий пункт спека.

5. **Запусти, почини, проверь**

   ```bash
   # Pest
   vendor/bin/pest tests/Unit/Services/PaymentServiceTest.php
   vendor/bin/pest --filter "создаёт задачу"

   # PHPUnit
   vendor/bin/phpunit tests/Unit/Services/PaymentServiceTest.php
   vendor/bin/phpunit --filter "test_creates_task"
   ```

   При падении теста разбери причину:
   - **Ошибка в тесте** (чаще всего — неверный namespace, фабрика, setup) → почини тест.
   - **Баг в проде** → стоп, сообщи пользователю. **Не** переписывай тест под баг, чтобы он прошёл.
   - **Флаки** (timing, ordering, randomness) → почини дизайн (заморозь время через `Carbon::setTestNow`, посей faker, контролируй порядок). Никогда `sleep()`-and-pray.

   После прохождения новых тестов запусти весь suite — проверь, что не сломал общие фабрики, фикстуры или общее состояние.

6. **Сверка с tasar-спеком** (если используется)

   Каждый `#### Scenario` из затронутых Requirement-блоков должен иметь свой тест. Если какой-то Scenario пропущен — либо допиши тест, либо явно сообщи пользователю почему пропустил.

   Для `## REMOVED Requirements` в delta-спеке — найди тесты, покрывающие удалённое поведение, и предложи их удалить (с подтверждением). Не оставляй тесты на удалённую функциональность.

7. **Покажи итог**

   Выведи:
   - Список созданных/изменённых тестовых файлов (пути)
   - Какие сценарии покрыты (если используется tasar — со ссылкой на Requirement)
   - Результат запуска (`X passed, Y failed`)
   - Если есть нюансы (пропущенный сценарий, найденный баг в проде, флаки-предупреждение) — отдельно

**Чек-лист перед завершением**

- [ ] Тесты запускаются зелёным локально
- [ ] **Mutation-проверка**: мысленно убери одну значимую строку из прод-кода — упадёт ли тест? Если нет — тест тавтологический, переписать
- [ ] Edge cases покрыты, не только happy path
- [ ] Naming совпадает со стилем проекта (snake_case / `it()` / camelCase — что выбрано в существующих тестах)
- [ ] Namespace и расположение зеркалят production-код
- [ ] Нет забытых `dd()`, `dump()`, `var_dump()`, `print_r()`
- [ ] Не замокан тестируемый класс (mock того что тестируется = тест проходит при любых багах)
- [ ] Нет `->only()` (Pest) или фокусированных тестов — они silently отключают остальной suite
- [ ] Правила skill-context соблюдены
- [ ] Если tasar — каждый затронутый Scenario имеет тест, либо явное обоснование пропуска

**Важные правила**

1. **Skill-context в приоритете** — правила из `.kodla/skill-context/kodla-php-test/SKILL.md` всегда перекрывают инструкции этого навыка
2. **Контекст проекта обязателен** — перед генерацией тестов прочитать DESCRIPTION.md, rules/base.md; нарушение конвенций = ошибка
3. **Порядок источников scope** — tasar → kodla-план → git diff (не пропускать уровни без проверки)
4. **Сначала план, потом код** — для >3 тестовых файлов всегда показывать пользователю scope перед генерацией
5. **Тип теста честный** — если код пишет в БД, это feature-тест, не unit даже ради красивых цифр покрытия
6. **Не мокать тестируемый класс** — mock того что тестируем = тест всегда зелёный вне зависимости от багов
7. **Баги в проде — стоп** — найденный баг сообщаем явно, тест под багованное поведение не пишем
8. **Цитируй Scenario, не пересказывай** — имя теста = заголовок Scenario из спека дословно
9. **Без focused-тестов в коммите** — `->only()` (Pest) silently отключают весь suite
10. **Русский язык** — все вопросы к пользователю и итоговые сообщения на русском (если `language.ui: ru`)

**Ограничения**

- Не модифицирую production-код для тестируемости (extract dependency, разбиение метода) без явного согласия пользователя — предложу вариант, дождусь подтверждения.
- Не пишу тесты на код, который ещё не написан. TDD-режим (тесты до реализации) — отдельный сценарий, в этом скилле не покрыт.
- Не пишу тесты на код фреймворка (Eloquent CRUD, Symfony Form internals, контейнер) — тестируется только своя логика поверх.
- Не удаляю существующие тесты автоматически даже при `## REMOVED Requirements` — спрашиваю подтверждение.
- Не использую `->only()` или подобные focused-режимы в коммитимом коде.
- Не игнорирую edge cases ради скорости — лучше написать 5 хороших тестов, чем 30 happy-path.
- Если в проекте нет ни PHPUnit, ни Pest — не устанавливаю автоматически. Сообщаю пользователю и предлагаю варианты (по умолчанию — Pest как современный выбор).
