# Маппинг tasar → тесты

Когда в проекте есть директория `tasar/`, считай её источником истины для **того, какое поведение нужно покрыть**. Scope тестов берётся из спек-файлов; тела тестов — из блоков Scenario.

## Структура tasar (краткое напоминание)

```
tasar/
├── specs/                       # Накопительная истина — текущее состояние всех требований
│   └── <name>.md
└── changes/
    ├── <change-name>/           # Активное изменение
    │   ├── proposal.md          # Что и зачем
    │   ├── design.md            # Как (технический подход)
    │   ├── tasks.md             # Чеклист реализации
    │   └── specs/
    │       └── <name>.md        # Дельта-спек: ADDED / MODIFIED / REMOVED
    └── archive/
        └── YYYY-MM-DD-<name>/   # Завершённые изменения
```

## Какой файл читать под какую задачу

| Задача | Источник |
|---|---|
| Покрыть стабильную область кодовой базы | `tasar/specs/<area>.md` |
| Покрыть поведение, добавленное активным изменением | `tasar/changes/<active>/specs/<name>.md` (delta) + `tasar/changes/<active>/tasks.md` |
| Режим B (после реализации): тесты на только что сделанное | `tasks.md` активного изменения + дельта-спек |
| Покрыть всё (рефакторинг, затронувший много областей) | дельта активного изменения + соответствующие главные спеки в `tasar/specs/` |

## Маппинг формата спека на тесты

### Главный спек (`tasar/specs/<name>.md`)

```markdown
# Spec: task-api

## Requirements

### Requirement: Создание задачи через API
Система SHALL предоставлять эндпоинт `POST /api/tasks` для создания задач.

#### Scenario: Успешное создание
- **WHEN** клиент отправляет POST с валидными данными
- **THEN** задача создаётся и возвращается с HTTP 201

#### Scenario: Ошибка валидации
- **WHEN** клиент отправляет POST с пустым `name`
- **THEN** ответ HTTP 422 с ошибкой по полю
```

Маппинг:

- **`### Requirement:` → один test class / файл.** Имя класса выводится из заголовка требования.
- **`#### Scenario:` → один тест-метод внутри этого класса.** Имя метода = заголовок сценария (в naming-стиле проекта).
- **Блок WHEN → Arrange + Act.** WHEN описывает входные данные / триггер.
- **Блок THEN → Assert.** THEN описывает наблюдаемый результат.

Пример вывода (Pest, Laravel):

```php
// tests/Feature/Api/CreateTaskViaApiTest.php

describe('POST /api/tasks создаёт задачу', function () {
    it('создаёт задачу и возвращает HTTP 201 когда payload валидный', function () {
        $response = $this->postJson('/api/tasks', ['name' => 'Buy milk']);

        $response->assertStatus(201);
        $response->assertJsonPath('name', 'Buy milk');
    });

    it('возвращает HTTP 422 с ошибкой по полю когда name пустой', function () {
        $response = $this->postJson('/api/tasks', ['name' => '']);

        $response->assertStatus(422);
        $response->assertJsonValidationErrors(['name']);
    });
});
```

### Дельта-спек (`tasar/changes/<active>/specs/<name>.md`)

```markdown
# Delta: add-task-priority

## ADDED Requirements

### Requirement: Приоритет задачи
Система SHALL поддерживать поле `priority` (low / medium / high) для задач.

#### Scenario: Дефолтный приоритет
- **WHEN** задача создаётся без указания `priority`
- **THEN** приоритет по умолчанию `medium`

## MODIFIED Requirements

### Requirement: Создание задачи через API
Система SHALL принимать опциональный параметр `priority` при создании задачи.

## REMOVED Requirements

### Requirement: Устаревший флаг приоритета
```

Приоритет тестов:

1. **`## ADDED Requirements`** — каждый Scenario получает новый тест. Это самое важное — совершенно новое поведение с нулевым покрытием.
2. **`## MODIFIED Requirements`** — найди существующий test class, покрывающий это требование (по соответствующему главному спеку → grep по существующим тестам). Допиши тесты под новое поведение; обнови существующие, если их setup или assertions теперь некорректны.
3. **`## REMOVED Requirements`** — найди тесты, покрывающие удалённое поведение, и **удали** их. Не оставляй мёртвые тесты на поведение, которого больше нет. Если сомневаешься — спроси перед удалением.

## Tasks.md — что было реализовано

```markdown
# Tasks: add-task-priority

- [x] Добавить колонку `priority` в миграцию таблицы `tasks`
- [x] Добавить `priority` в fillable + cast модели `Task`
- [x] Обновить `CreateTaskAction` для приёма приоритета
- [ ] Обновить документацию API
```

В режиме B (после реализации) пункты `[x]` говорят, какой код изменился → какие тесты нужны. Пункты `[ ]` ещё не реализованы — на них тесты не пишем.

## Встройка в воркфлоу

Где этот скилл стоит в пайплайне tasar:

```
tasar new <name>
    ↓
/tasar:propose      proposal + design + tasks + delta-spec
    ↓
/tasar:apply        реализация
    ↓
[этот скилл]        тесты на ADDED/MODIFIED Requirements
    ↓
/tasar:archive      проверка и архивирование
```

То есть разумный дефолтный триггер для режима B: *"после `/tasar:apply` и до `/tasar:archive`"*.

## Типичные ловушки при работе со спеками tasar

- **Не пересказывай Scenario в имени теста — цитируй.** Весь смысл spec-driven подхода — в трейсабилити: при падении теста читатель должен моментально найти Scenario в спеке.
- **Не пропускай "тривиальные" сценарии.** Если он в спеке — это часть контракта. Сценарий, выглядящий тривиальным, часто оказывается тем самым, что ловит реальную регрессию.
- **Если у Requirement нет блоков Scenario** — спроси у пользователя. Либо спек неполный (push back), либо отсутствует Scenario для случая, на который тебя просят написать тест.
- **MODIFIED Requirements не всегда требуют новых тестов** — иногда нужны *обновлённые* существующие. Сначала проверь существующее покрытие, прежде чем добавлять параллельные тесты.
