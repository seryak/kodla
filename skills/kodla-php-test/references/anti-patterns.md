# Антипаттерны в тестах

Каталог наиболее частых ошибок в LLM-сгенерированных PHP-тестах. Прочитай перед написанием первого теста в новом для тебя проекте; перечитывай при ревью собственного вывода.

## 1. Mocking того, что тестируется

```php
// Плохо
$service = $this->createMock(PaymentService::class);
$service->method('charge')->willReturn(true);
$this->assertTrue($service->charge(100));   // тестирует мок, а не код
```

Если метод тестируется — он должен быть **реальной** реализацией. Мочить только его зависимости, не сам метод.

## 2. Тавтологические assertion'ы

```php
// Плохо — ничего не утверждает о поведении
$this->assertTrue(true);
$this->assertNotNull($result);              // когда null был невозможен в принципе
expect($user)->toBeInstanceOf(User::class); // когда конструктор и так возвращает User по type-hint

// Хорошо — утверждает поведение
expect($user->isAdmin())->toBeFalse();
expect($result->total)->toBe(150);
```

Тест должен иметь возможность *упасть*, если прод-код неверен. Мысленная проверка: убери одну значимую строку из проды — поймает ли тест?

## 3. Coverage-чейзинг

Написание теста, который только касается строки ради повышения покрытия. Запах: `expect(true)->toBeTrue()` в конце теста, который прогнал сложный метод без проверки результата.

Строка, покрытая тестом, который не проверяет её эффект, **не покрыта** на практике. Не пиши такие тесты; если руководство требует цифр coverage — пиши тесты на реальное поведение, они покроют строки как побочный эффект.

## 4. Over-mocking

```php
// Плохо — мочит каждую зависимость, тестирует оркестрацию моков
$repo = $this->createMock(UserRepo::class);
$mailer = $this->createMock(Mailer::class);
$logger = $this->createMock(Logger::class);
$cache = $this->createMock(Cache::class);
// ... 30 строк shouldReceive() ...
```

Когда моков больше, чем реальных объектов 4:1, тест тестирует не систему, а оркестрацию моков. Варианты:

- Используй реальные реализации, где это дёшево (in-memory cache, array logger, fake mailer)
- Подними тест из unit в feature/integration
- Зарефактори прод-код — у него слишком много зависимостей

См. `mocking.md`.

## 5. Скрытое состояние БД / общее состояние

```php
// Плохо — запускается первым, "проходит" из-за остаточных данных от другого теста
public function test_user_exists(): void {
    expect(User::count())->toBeGreaterThan(0);
}
```

В Laravel: используй `RefreshDatabase` или `DatabaseTransactions`. В vanilla: чисти/сей в `setUp` (или `beforeEach`). Тесты должны проходить в любом порядке, в изоляции.

## 6. Зависимость от времени и флакающее поведение

```php
// Плохо — упадёт в полночь
expect(Carbon::now()->format('Y-m-d'))->toBe(date('Y-m-d'));
```

В Laravel: `Carbon::setTestNow('2025-01-01 12:00:00')` или `$this->travelTo(...)`. Vanilla: внедри интерфейс `Clock` через DI. Никогда не предполагай, что реальное wall-clock время совпадает с ожиданиями.

## 7. Зависимые от порядка тесты

Тесты, требующие конкретного порядка запуска или зависящие от побочных эффектов предыдущих тестов в том же файле. Первый признак: тест проходит при запуске в одиночку, но падает в составе suite (или наоборот).

Каждый тест должен быть независимым. Если ловишь себя на мысли "ну, этот тест запускается после того, значит юзер уже создан" — стоп. Либо каждый тест создаёт что ему нужно, либо `beforeEach` это делает.

## 8. Assertion'ы на внутренности

```php
// Плохо — связан с реализацией
expect($service->buildQuery())->toContain('WHERE status = "active"');

// Хорошо — утверждает наблюдаемый результат
expect($service->getActiveUsers())->toHaveCount(3);
```

Тестируй то, что видят вызывающие (возвращаемые значения, состояние БД, отправленные события, HTTP-ответы). Не тестируй приватные методы, промежуточные query-строки или другие внутренности — они меняются при рефакторингах, при идентичном поведении.

## 9. Раздутый setUp / beforeEach

Если `beforeEach` на 50 строк — класс теста, скорее всего, нужно разбивать. Читатель, открывший один тест-метод, должен понять его без скроллинга вверх. Допустимо выносить *маленький* общий setup; недопустимо прятать туда основную часть Arrange.

## 10. Snapshot-тесты не к месту

Snapshot-тесты для HTML / JSON / массивов полезны как regression-detection на стабильных структурах. Они бесполезны для верификации дизайна (есть ли на странице нужная информация?) и кошмар по поддержке для активно эволюционирующих структур (каждое изменение требует обновления snapshot — что LLM любезно делает не задумываясь).

Использовать для: рендера почтовых шаблонов, генерации конфиг-файлов, фиксированных отчётов. Избегать для: feature-ответов, форма которых легитимно меняется.

## 11. Generic-имена тестов

```php
// Плохо
public function test_creation(): void
public function test_it_works(): void
it('works correctly', ...)

// Хорошо — имена описывают тестируемое поведение
public function test_creates_task_with_default_medium_priority(): void
it('rejects creation when name is empty', ...)
```

Failure messages в логах CI — единственный контекст, который будет у твоего будущего "я". `test_creation FAILED` не говорит ни о чём.

## 12. Тестирование фреймворка

```php
// Плохо — тестирует, что Laravel работает, а не твой код
$user = User::create(['name' => 'X']);
expect(User::find($user->id))->not->toBeNull();
```

Команды Laravel/Symfony/Doctrine тестируют свои фреймворки. Ты тестируешь *свою доменную логику поверх фреймворка*. Если тест прогоняет только code paths фреймворка — удали.

## 13. Faker / seeding без детерминизма

```php
// Плохо — недетерминированно — флакает, когда фейковый email случайно совпал с существующим
$user = User::factory()->create();
expect(User::where('email', $user->email)->count())->toBe(1);
```

Либо посей Faker (`$this->faker->seed(...)`), либо утверждай на связях / ID, которые ты контролируешь, а не на случайно сгенерированном содержимом.

## 14. Скрытые assertion'ы в моках

```php
// Плохо — assertion спрятан внутри Mockery, легко пропустить при ревью
$mailer->shouldReceive('send')->once()->with(Mockery::on(fn($m) => $m->subject === 'Welcome'));
$service->register($user);
// в теле теста явного assertion нет
```

Предпочитай `Bus::fake()` / `Mail::fake()` / `Event::fake()` (Laravel) или in-memory fakes — и делай assertion'ы явными в конце теста:

```php
Mail::assertSent(WelcomeEmail::class, fn($m) => $m->user->is($user));
```

Читается лучше, и `->once()` от Mockery не упадёт молча, если тест выйдет раньше времени.

## 15. Пропуск unhappy path

Класс с пятью методами и только happy-path тестами **покрыт на 40%**, что бы ни говорил coverage tool. Каждый `if` / `match` / `throw` в проде — это ветка, которая нуждается в тесте (или явном, обоснованном решении не тестировать её).
