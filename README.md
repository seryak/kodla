# kodla

CLI-инструмент для настройки AI-контекста в проектах. Kodla помогает AI-агентам понять ваш проект: генерирует конфигурации, планы реализации и build-файлы — чтобы вы тратили меньше времени на объяснения и больше на работу.

## Установка

```bash
# Через Composer (глобально)
composer global require kodla/kodla

# Или скачать бинарник
curl -L https://github.com/kodla/kodla/releases/latest/download/kodla -o /usr/local/bin/kodla
chmod +x /usr/local/bin/kodla
```

Скиллы kodla работают через Claude Code. После установки скиллов они доступны как `/kodla:init`, `/kodla:plan` и т.д.

## Скиллы

### kodla-init

**Настраивает AI-контекст проекта — один раз, чтобы AI понял проект навсегда.**

Сканирует проект, определяет стек технологий и генерирует файлы `.kodla/`:
- `config.yaml` — конфигурация языка и настроек
- `DESCRIPTION.md` — описание проекта для AI-агентов
- `rules/base.md` — правила работы с кодом
- `AGENTS.md` — инструкции для агентов

#### Когда использовать

- Начинаете работать с AI над существующим проектом, и агент делает неподходящие предложения
- Создаёте новый проект и хотите AI-поддержку с первого дня
- После онбординга нового разработчика — пусть AI тоже "ознакомится" с проектом

#### Примеры

**Существующий проект без AI-контекста**

Открываете Claude в корне Laravel-монолита для интернет-магазина. Агент предлагает использовать сессии вместо JWT, не знает про ваш EventBus и добавляет vanilla JS вместо Livewire. Запускаете `/kodla:init` — скилл сканирует `composer.json`, находит Laravel 11 + Livewire + Pest + MySQL, генерирует описание и правила. Теперь любой агент с первого сообщения понимает стек и архитектуру.

**Новый Go-проект**

Создаёте новый сервис для обработки вебхуков Stripe. До начала работы:
```bash
kodla init "Go-сервис для обработки вебхуков Stripe. Получает события от Stripe, валидирует подпись, публикует в Kafka."
```
Скилл создаёт конфиг с описанием, указывает Go-правила и создаёт `AGENTS.md` с командами для запуска.

#### Не делает

Не создаёт код приложения, не настраивает CI/CD, не управляет зависимостями.

### kodla-plan

**Создаёт детальный план реализации до начала работы — исследует кодовую базу и разбивает задачу на конкретные шаги.**

Запускает параллельное исследование проекта через Explore-агентов, задаёт уточняющие вопросы и сохраняет план в `.kodla/plans/<slug>.md`.

#### Когда использовать

- Задача нетривиальная и затрагивает несколько файлов или слоёв
- Хотите убедиться, что AI понял задачу правильно до начала работы
- Нужно согласовать подход с командой прежде чем писать код

#### Примеры

**Новая фича в существующем API**

Нужно добавить систему push-уведомлений для мобильного приложения. Пишете `/kodla:plan добавить push-уведомления через Firebase`. Скилл находит `UserService`, `NotificationChannel` и существующие Event-классы, выясняет нужны ли тесты и ограничения по времени. Создаёт план из 9 задач в 3 фазах: модель → сервис → API → тесты.

**Рефакторинг большого контроллера**

`OrderController` разросся до 800 строк: логика оплаты, создание накладных, отправка email. Запускаете `/kodla:plan вынести логику оплаты из OrderController в PaymentService`. Скилл находит все 12 мест где вызывается платёжная логика, строит последовательный план рефакторинга без поломки существующих 47 тестов.

#### Не делает

Не пишет код, не редактирует файлы проекта. Если в проекте есть папка `tasar/` — автоматически перенаправляет к `/tasar-propose` для создания полного изменения.

### kodla-makefile

**Генерирует или улучшает файл автоматизации сборки — Makefile, Taskfile.yml, Justfile или Magefile.go.**

Анализирует проект (стек, Docker, CI, тесты, линтеры), выбирает подходящий инструмент и создаёт готовый build-файл с документированными целями. Умеет улучшать существующие файлы, не удаляя написанное вручную.

#### Когда использовать

- Нет build-файла, но нужны удобные команды `make dev`, `make test`, `make deploy`
- Новый разработчик приходит в проект и спрашивает "как запустить локально?"
- Существующий Makefile из 5 строк не покрывает и половины нужного

#### Примеры

**Go-микросервис без Makefile**

Новый сервис для обработки изображений: Go + Docker + PostgreSQL + golangci-lint. Запускаете `/kodla:makefile`. Скилл обнаруживает `docker-compose.yml`, `Dockerfile` и `.golangci.yml`, генерирует Makefile:

```makefile
make dev        # поднять сервисы и запустить в watch-режиме
make test       # go test с race detector и coverage
make lint       # golangci-lint с вашей конфигурацией
make migrate    # применить миграции через goose
make build      # собрать бинарник для production
make clean      # удалить артефакты сборки
```

**PHP-проект с неполным Makefile**

Laravel-проект с Makefile из 3 целей: `install`, `test`, `cs-fix`. Запускаете `/kodla:makefile`. Скилл не трогает существующие цели, добавляет недостающие:

```makefile
make fresh      # пересоздать БД + запустить сидеры
make migrate    # применить новые миграции
make coverage   # отчёт покрытия тестами в HTML
make analyse    # phpstan level 8
make queue      # запустить воркер с автоперезапуском
```

Также обновляет `AGENTS.md` с полным справочником команд.

#### Не делает

Не создаёт Dockerfile, не настраивает CI/CD пайплайны, не управляет секретами.

### kodla-improve

**Вторая итерация планирования — находит пробелы в готовом плане и улучшает формулировки задач.**

Читает существующий план, глубоко исследует кодовую базу через 3 параллельных агента, анализирует 5 категорий проблем: пропущенные задачи, размытые формулировки, неправильный порядок, дублирование, выход за scope. Показывает предложения перед применением.

#### Когда использовать

- План есть, но задачи слишком абстрактные ("настроить кеширование", "добавить валидацию")
- В процессе планирования нашли edge case который план не учитывает
- Порядок задач кажется неоптимальным — что-то делается раньше чем нужно

#### Примеры

**Уточнение размытых задач**

После `/kodla:plan` получили план с задачей "добавить кеширование для API". Запускаете `/kodla:improve`. Скилл разбивает одну задачу на 5 конкретных:
1. Выбрать стратегию кеширования (Redis vs. in-memory) исходя из текущей инфраструктуры
2. Добавить `RedisService` с TTL-конфигурацией
3. Кешировать `GET /products` с инвалидацией по тегам категорий
4. Кешировать ответы внешнего API курсов валют (TTL 1 час)
5. Написать тест: проверить что при изменении продукта кеш инвалидируется

**Поиск пропущенных задач**

План для системы загрузки аватаров пользователей включает: загрузку файла, валидацию размера, сохранение в S3, обновление URL в профиле. Скилл находит пропущенное: нет задачи для удаления старого файла из S3 при смене аватара, нет обработки ошибок сети при загрузке, нет cleanup временных файлов. Добавляет эти задачи с правильным порядком.

#### Не делает

Не реализует задачи, не пишет код. Работает только с существующими планами в `.kodla/plans/` или `tasar/changes/`.

### kodla-research

**Режим исследования — партнёр по мышлению для изучения идей и прояснения требований перед реализацией.**

Не создаёт код и не меняет файлы проекта. Читает кодовую базу, строит ASCII-диаграммы, задаёт уточняющие вопросы и сохраняет результаты в `.kodla/RESEARCH.md`. Подходит для открытых вопросов без очевидного ответа.

#### Когда использовать

- Не знаете как подойти к задаче и хотите "подумать вслух" перед планированием
- Нужно сравнить несколько архитектурных решений с учётом текущего контекста
- Хотите понять как устроена незнакомая часть проекта перед тем как её трогать

#### Примеры

**Архитектурный выбор**

Проект растёт: 50К пользователей, API начинает тормозить. Нужно решить как хранить файлы пользователей. Пишете `/kodla:research как лучше организовать хранение файлов: S3, локально или через CDN`. Скилл изучает текущую инфраструктуру (нашёл `docker-compose.yml` с MinIO), анализирует объём данных по логам, строит диаграмму сравнения:

```
S3 (AWS)        → масштабируемо, дорого при больших объёмах, vendor lock-in
MinIO (self)    → уже есть в проекте, бесплатно, сложнее в production
Cloudflare R2   → S3-совместимо, дешевле, хороший CDN
```

Фиксирует вывод: R2 лучший вариант с учётом текущего бюджета. Сохраняет в RESEARCH.md.

**Понять незнакомый код**

Нужно добавить новый тип уведомлений, но не понятно как работает текущая система. Пишете `/kodla:research как устроена система уведомлений в проекте`. Скилл читает middleware, модели, Event-классы, конфиги — и объясняет полный поток:

```
Request → NotificationController
        → NotificationService::dispatch()
        → EventBus::emit(NotificationCreated)
        → [async] NotificationWorker
        → Channel::send() [email | push | sms]
```

С указанием конкретных файлов и строк.

#### Не делает

Не создаёт код приложения, не меняет файлы проекта (единственное исключение — пишет в `.kodla/RESEARCH.md`). Не принимает решения за вас — исследует и помогает думать.

## Рабочий процесс

Скиллы работают как последовательный конвейер: понять → спланировать → уточнить → реализовать.

```
Новый проект:
  kodla-init → kodla-plan → реализация

Сложная фича (есть сомнения в подходе):
  kodla-research → kodla-plan → kodla-improve → реализация

Быстрая фича (подход ясен):
  kodla-plan → реализация

Улучшение готового плана:
  kodla-improve → реализация

Добавить автоматизацию в любой момент:
  kodla-makefile (независимо от других скиллов)
```

### Типичная сессия

```
# 1. Один раз для проекта
/kodla:init

# 2. Перед каждой нетривиальной задачей
/kodla:plan добавить систему рейтингов для товаров

# 3. Если план кажется неполным
/kodla:improve

# 4. Реализация через /tasar:apply или напрямую
```

> **Совет:** `kodla-init` нужно запустить один раз. После этого все агенты автоматически получают контекст проекта через `.kodla/` — не нужно объяснять стек в каждом новом чате.
