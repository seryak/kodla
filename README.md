# kodla

CLI-инструмент для настройки AI-контекста в проектах. Kodla помогает AI-агентам понять ваш проект: генерирует конфигурации, планы реализации и build-файлы — чтобы вы тратили меньше времени на объяснения и больше на работу.

## Установка

```bash
# Через Composer (глобально)
composer global require kodla/kodla

# Или скачать бинарник
curl -L https://github.com/kodla/kodla/releases/latest/download/kodla -o /usr/local/bin/kodla
chmod +x /usr/local/bin/kodla
```

Скиллы kodla работают через Claude Code. После установки скиллов они доступны как `/kodla:init`, `/kodla:plan` и т.д.

## Скиллы

### kodla-init

**Настраивает AI-контекст проекта — один раз, чтобы AI понял проект навсегда.**

Сканирует проект, определяет стек технологий и генерирует файлы `.kodla/`:
- `config.yaml` — конфигурация языка и настроек
- `DESCRIPTION.md` — описание проекта для AI-агентов
- `rules/base.md` — правила работы с кодом
- `AGENTS.md` — инструкции для агентов

#### Когда использовать

- Начинаете работать с AI над существующим проектом, и агент делает неподходящие предложения
- Создаёте новый проект и хотите AI-поддержку с первого дня
- После онбординга нового разработчика — пусть AI тоже "ознакомится" с проектом

#### Примеры

**Существующий проект без AI-контекста**

Открываете Claude в корне Laravel-монолита для интернет-магазина. Агент предлагает использовать сессии вместо JWT, не знает про ваш EventBus и добавляет vanilla JS вместо Livewire. Запускаете `/kodla:init` — скилл сканирует `composer.json`, находит Laravel 11 + Livewire + Pest + MySQL, генерирует описание и правила. Теперь любой агент с первого сообщения понимает стек и архитектуру.

**Новый Go-проект**

Создаёте новый сервис для обработки вебхуков Stripe. До начала работы:
```bash
kodla init "Go-сервис для обработки вебхуков Stripe. Получает события от Stripe, валидирует подпись, публикует в Kafka."
```
Скилл создаёт конфиг с описанием, указывает Go-правила и создаёт `AGENTS.md` с командами для запуска.

#### Не делает

Не создаёт код приложения, не настраивает CI/CD, не управляет зависимостями.

### kodla-plan

**Создаёт детальный план реализации до начала работы — исследует кодовую базу и разбивает задачу на конкретные шаги.**

Запускает параллельное исследование проекта через Explore-агентов, задаёт уточняющие вопросы и сохраняет план в `.kodla/plans/<slug>.md`.

#### Когда использовать

- Задача нетривиальная и затрагивает несколько файлов или слоёв
- Хотите убедиться, что AI понял задачу правильно до начала работы
- Нужно согласовать подход с командой прежде чем писать код

#### Примеры

**Новая фича в существующем API**

Нужно добавить систему push-уведомлений для мобильного приложения. Пишете `/kodla:plan добавить push-уведомления через Firebase`. Скилл находит `UserService`, `NotificationChannel` и существующие Event-классы, выясняет нужны ли тесты и ограничения по времени. Создаёт план из 9 задач в 3 фазах: модель → сервис → API → тесты.

**Рефакторинг большого контроллера**

`OrderController` разросся до 800 строк: логика оплаты, создание накладных, отправка email. Запускаете `/kodla:plan вынести логику оплаты из OrderController в PaymentService`. Скилл находит все 12 мест где вызывается платёжная логика, строит последовательный план рефакторинга без поломки существующих 47 тестов.

#### Не делает

Не пишет код, не редактирует файлы проекта. Если в проекте есть папка `tasar/` — автоматически перенаправляет к `/tasar-propose` для создания полного изменения.

### kodla-makefile

**Генерирует или улучшает файл автоматизации сборки — Makefile, Taskfile.yml, Justfile или Magefile.go.**

Анализирует проект (стек, Docker, CI, тесты, линтеры), выбирает подходящий инструмент и создаёт готовый build-файл с документированными целями. Умеет улучшать существующие файлы, не удаляя написанное вручную.

#### Когда использовать

- Нет build-файла, но нужны удобные команды `make dev`, `make test`, `make deploy`
- Новый разработчик приходит в проект и спрашивает "как запустить локально?"
- Существующий Makefile из 5 строк не покрывает и половины нужного

#### Примеры

**Go-микросервис без Makefile**

Новый сервис для обработки изображений: Go + Docker + PostgreSQL + golangci-lint. Запускаете `/kodla:makefile`. Скилл обнаруживает `docker-compose.yml`, `Dockerfile` и `.golangci.yml`, генерирует Makefile:

```makefile
make dev        # поднять сервисы и запустить в watch-режиме
make test       # go test с race detector и coverage
make lint       # golangci-lint с вашей конфигурацией
make migrate    # применить миграции через goose
make build      # собрать бинарник для production
make clean      # удалить артефакты сборки
```

**PHP-проект с неполным Makefile**

Laravel-проект с Makefile из 3 целей: `install`, `test`, `cs-fix`. Запускаете `/kodla:makefile`. Скилл не трогает существующие цели, добавляет недостающие:

```makefile
make fresh      # пересоздать БД + запустить сидеры
make migrate    # применить новые миграции
make coverage   # отчёт покрытия тестами в HTML
make analyse    # phpstan level 8
make queue      # запустить воркер с автоперезапуском
```

Также обновляет `AGENTS.md` с полным справочником команд.

#### Не делает

Не создаёт Dockerfile, не настраивает CI/CD пайплайны, не управляет секретами.

### kodla-improve

**Вторая итерация планирования — находит пробелы в готовом плане и улучшает формулировки задач.**

Читает существующий план, глубоко исследует кодовую базу через 3 параллельных агента, анализирует 5 категорий проблем: пропущенные задачи, размытые формулировки, неправильный порядок, дублирование, выход за scope. Показывает предложения перед применением.

#### Когда использовать

- План есть, но задачи слишком абстрактные ("настроить кеширование", "добавить валидацию")
- В процессе планирования нашли edge case который план не учитывает
- Порядок задач кажется неоптимальным — что-то делается раньше чем нужно

#### Примеры

**Уточнение размытых задач**

После `/kodla:plan` получили план с задачей "добавить кеширование для API". Запускаете `/kodla:improve`. Скилл разбивает одну задачу на 5 конкретных:
1. Выбрать стратегию кеширования (Redis vs. in-memory) исходя из текущей инфраструктуры
2. Добавить `RedisService` с TTL-конфигурацией
3. Кешировать `GET /products` с инвалидацией по тегам категорий
4. Кешировать ответы внешнего API курсов валют (TTL 1 час)
5. Написать тест: проверить что при изменении продукта кеш инвалидируется

**Поиск пропущенных задач**

План для системы загрузки аватаров пользователей включает: загрузку файла, валидацию размера, сохранение в S3, обновление URL в профиле. Скилл находит пропущенное: нет задачи для удаления старого файла из S3 при смене аватара, нет обработки ошибок сети при загрузке, нет cleanup временных файлов. Добавляет эти задачи с правильным порядком.

#### Не делает

Не реализует задачи, не пишет код. Работает только с существующими планами в `.kodla/plans/` или `tasar/changes/`.

### kodla-research

**Режим исследования — партнёр по мышлению для изучения идей и прояснения требований перед реализацией.**

Не создаёт код и не меняет файлы проекта. Читает кодовую базу, строит ASCII-диаграммы, задаёт уточняющие вопросы и сохраняет результаты в `.kodla/RESEARCH.md`. Подходит для открытых вопросов без очевидного ответа.

#### Когда использовать

- Не знаете как подойти к задаче и хотите "подумать вслух" перед планированием
- Нужно сравнить несколько архитектурных решений с учётом текущего контекста
- Хотите понять как устроена незнакомая часть проекта перед тем как её трогать

#### Примеры

**Архитектурный выбор**

Проект растёт: 50К пользователей, API начинает тормозить. Нужно решить как хранить файлы пользователей. Пишете `/kodla:research как лучше организовать хранение файлов: S3, локально или через CDN`. Скилл изучает текущую инфраструктуру (нашёл `docker-compose.yml` с MinIO), анализирует объём данных по логам, строит диаграмму сравнения:

```
S3 (AWS)        → масштабируемо, дорого при больших объёмах, vendor lock-in
MinIO (self)    → уже есть в проекте, бесплатно, сложнее в production
Cloudflare R2   → S3-совместимо, дешевле, хороший CDN
```

Фиксирует вывод: R2 лучший вариант с учётом текущего бюджета. Сохраняет в RESEARCH.md.

**Понять незнакомый код**

Нужно добавить новый тип уведомлений, но не понятно как работает текущая система. Пишете `/kodla:research как устроена система уведомлений в проекте`. Скилл читает middleware, модели, Event-классы, конфиги — и объясняет полный поток:

```
Request → NotificationController
        → NotificationService::dispatch()
        → EventBus::emit(NotificationCreated)
        → [async] NotificationWorker
        → Channel::send() [email | push | sms]
```

С указанием конкретных файлов и строк.

#### Не делает

Не создаёт код приложения, не меняет файлы проекта (единственное исключение — пишет в `.kodla/RESEARCH.md`). Не принимает решения за вас — исследует и помогает думать.

### kodla-implement-plan

**Выполняет задачи из плана последовательно — отслеживает прогресс и продолжает между сессиями.**

Берёт план из `.kodla/plans/` или `tasar/changes/` и выполняет задачи одну за другой. Сразу обновляет чеклист в файле плана после каждой задачи. При следующем запуске автоматически продолжает с первой незавершённой задачи.

#### Когда использовать

- После `/kodla:plan` или `/tasar-propose` — план готов, пора реализовывать
- При продолжении прерванной сессии — не нужно вспоминать на чём остановились
- Когда хотите видеть прогресс по задачам и контролировать каждый шаг

#### Примеры

**Реализация системы уведомлений**

После `/kodla:plan` получили план из 9 задач для системы push-уведомлений. Запускаете `/kodla:implement-plan`. Скилл выполняет задачи по одной: создаёт модель, сервис, API-эндпоинты — обновляет чеклист сразу после каждой. Через 3 часа прерываетесь на задаче 6.

**Возобновление после перерыва**

На следующий день снова запускаете `/kodla:implement-plan`. Скилл читает план, видит что задачи 1–5 выполнены, и автоматически продолжает с 6-й. Не нужно объяснять контекст — продолжает с того места где остановились.

#### Не делает

Не создаёт планы, не пишет тесты если их нет в плане, не добавляет задачи вне утверждённого плана.

### kodla-check-tasks

**Проверяет реализацию плана — все задачи выполнены, код работает, нет незавершённых маркеров.**

Аудирует выполнение задач по плану, запускает build и тесты, ищет TODO/FIXME/console.log и var_dump в коде. Формирует детальный отчёт с таблицей статусов. Ничего не меняет — только читает и анализирует.

#### Когда использовать

- После `/kodla:implement-plan` — убедиться что всё действительно сделано
- Перед деплоем или созданием pull request
- При сомнениях "всё ли сделано" — быстрый аудит без ручной проверки

#### Примеры

**Аудит после реализации**

Реализовали план из 9 задач. Запускаете `/kodla:check-tasks`. Скилл находит: задачи 1–4 DONE, задача 5 PARTIAL (метод создан, но не зарегистрирован в DI), задачи 6–9 не начаты. В коде есть 3 оставшихся TODO и один console.log. Возвращаете план на доработку.

**Проверка перед PR**

Перед созданием PR запускаете `/kodla:check-tasks --strict`. Скилл прогоняет тесты (48/48 ✓), проверяет линтер, убеждается что нет отладочного вывода. Итог: "Готово к мержу".

#### Не делает

Не исправляет код, не отмечает задачи выполненными, не предлагает коммит — только сообщает статус.

### kodla-commit

**Создаёт коммит по Conventional Commits — анализирует staged-изменения и предлагает семантическое сообщение.**

Определяет тип (`feat`, `fix`, `refactor`, `ci`…) и scope по путям файлов, генерирует сообщение в соответствии со спецификацией. При наличии несвязанных изменений предлагает разбить на отдельные коммиты. После коммита предлагает push.

#### Когда использовать

- После реализации фичи или исправления — быстро сформировать правильное сообщение коммита
- Хотите убедиться что коммит следует конвенции проекта
- Staged-изменения смешивают несколько логических единиц — нужно разбить

#### Примеры

**Обычный коммит**

Staged: изменения в `src/auth/` и `tests/auth/`. Запускаете `/kodla-commit`. Скилл предлагает:
```
feat(auth): add JWT refresh token rotation
```
Подтверждаете — коммит создан, предлагает `git push`.

**Несвязанные изменения**

Staged: правки в `UserService` (баг) и новый `ExportController` (фича). Скилл замечает два логических блока, предлагает разбить на два коммита: `fix(users)` и `feat(export)`. Вы подтверждаете — коммиты создаются последовательно.

#### Не делает

Не добавляет файлы в staged (только читает `git diff --cached`), не пушит без подтверждения, не добавляет AI co-author строки.

### kodla-fix

**Исправляет конкретный баг или проблему — немедленно или через план.**

Анализирует описание бага или стектрейс, находит корневую причину, предлагает два режима: исправить сразу или создать `.kodla/FIX_PLAN.md` для сложных случаев. Добавляет логирование с префиксом `[FIX]` и предлагает тест на регрессию.

#### Когда использовать

- Что-то сломалось и есть воспроизводимая ошибка
- Получили стектрейс из production — нужно быстро локализовать и пофиксить
- Нужно исправить баг без риска сломать смежную логику

#### Примеры

**Null pointer в production**

Сервер возвращает 500 на `/api/profile` для анонимных пользователей. Пишете `/kodla:fix null pointer в UserService::getProfile() при анонимных сессиях`. Скилл находит отсутствующую проверку `$user !== null`, исправляет, добавляет логирование `[FIX]` и предлагает тест-сценарий.

**Стектрейс из логов**

Вставляете стектрейс в сообщение с `/kodla:fix`. Скилл локализует ошибку до конкретного файла и строки, объясняет причину, предлагает патч. Для сложных случаев с несколькими зависимостями создаёт `FIX_PLAN.md` и останавливается — вы одобряете план перед началом исправления.

#### Не делает

Не рефакторит смежный код, не добавляет новые фичи во время исправления.

### kodla-docs

**Генерирует и поддерживает документацию проекта — README как лендинг и детальные страницы в `docs/`.**

Создаёт README на 80–120 строк (витрина проекта, а не мануал) и детальные страницы по темам в директории `docs/`. Умеет работать с нуля, реорганизовывать разросшийся README, или обновлять устаревшую документацию.

#### Когда использовать

- В проекте нет документации вообще — README отсутствует или пустой
- README разросся до 300+ строк и стал мануалом вместо лендинга
- После крупной фичи нужно актуализировать доки

#### Примеры

**Проект без документации**

Laravel-монолит для интернет-магазина: ни README, ни docs/. Запускаете `/kodla:docs`. Скилл сканирует `composer.json`, `routes/`, `app/`, генерирует README (установка, стек, команды) и 4 страницы: `docs/install.md`, `docs/architecture.md`, `docs/api.md`, `docs/testing.md`.

**Реорганизация разросшегося README**

README на 400 строк: установка, все API-эндпоинты, примеры запросов, схема БД. Запускаете `/kodla:docs`. Скилл оставляет в README только ключевую информацию (80 строк), выносит детали в `docs/api.md` и `docs/database.md` с навигацией.

#### Не делает

Не изменяет код приложения, не коммитит изменения, не удаляет markdown-файлы без явного подтверждения.

### kodla-reference

**Создаёт справочники знаний из URL, документации и локальных файлов — чтобы AI знал вашу технологию точно, а не приблизительно.**

Загружает источники через WebFetch, обрабатывает и сохраняет структурированные справочники в `.kodla/references/`. Справочники переиспользуются во всех последующих сессиях через `/kodla-plan`, `/kodla-implement-plan` и `/kodla-research` — один раз зафиксировали, больше не объясняете.

#### Когда использовать

- AI не знает или знает неточно вашу внутреннюю библиотеку, кастомное API или специфичный фреймворк
- Хотите выверенные ответы на основе конкретной документации, а не обучающих данных
- Нужен постоянный артефакт знаний который переживёт сессию

#### Примеры

**Внутренняя библиотека**

Проект использует кастомный event bus — документация только на внутреннем вики. Запускаете `/kodla-reference https://wiki.internal/event-bus --name event-bus`. Скилл загружает страницу, извлекает API, сохраняет `.kodla/references/event-bus.md`. Теперь `/kodla-plan` видит справочник и не предлагает стандартные решения вместо вашего event bus.

**Обновление устаревшего справочника**

Библиотека обновилась, справочник устарел. Запускаете `/kodla-reference --update --name event-bus`. Скилл повторно загружает те же источники, обновляет только изменившиеся разделы.

#### Не делает

Не выполняет git-операции, не угадывает содержимое недоступных URL — сообщает об ошибке доступа.

### kodla-rules

**Добавляет правила и конвенции проекта — сохраняет в `RULES.md` чтобы AI помнил их в каждой сессии.**

Записывает конкретные правила в `RULES.md`. Поддерживает три уровня: глобальные аксиомы, базовые конвенции, правила для конкретных областей (API, frontend, БД). Каждый вызов добавляет новые правила, не удаляя старые.

#### Когда использовать

- AI предлагает паттерн который явно не подходит для вашего проекта
- Хотите зафиксировать архитектурное решение чтобы не объяснять его снова
- Нужны правила для конкретной области: только для API, только для работы с БД

#### Примеры

**Зафиксировать архитектурный паттерн**

AI несколько раз предложил прямые Eloquent-запросы в контроллерах. Пишете `/kodla:rules всегда использовать Repository pattern для работы с БД, прямые запросы в контроллерах запрещены`. Правило добавляется в `RULES.md` и применяется ко всем следующим сессиям.

**Правила для конкретной области**

Команда договорилась о стандартах для REST API. Запускаете `/kodla:rules area:api`. Скилл задаёт вопросы о конвенциях и создаёт `rules/api.md`: именование эндпоинтов, формат ошибок, пагинация. Файл регистрируется в `config.yaml` — агент подгружает его только при работе с API.

#### Не делает

Не применяет правила к существующему коду, не создаёт иерархий (правила хранятся плоским списком).

---

### kodla-evolve

**Улучшает скиллы kodla на основе паттернов вашего проекта — AI учится на накопленных патчах.**

Анализирует прошлые исправления багов, паттерны кодовой базы и конвенции. Находит повторяющиеся ошибки AI и пробелы в покрытии скиллов. Генерирует проектно-специфичные правила в skill-context файлах — без изменения базовых скиллов.

#### Когда использовать

- AI несколько раз предложил одно и то же неподходящее решение
- Накопилось 5–10 патчей с исправлениями одного типа
- Хотите чтобы AI знал особенности вашего стека и не повторял типичные ошибки

#### Примеры

**Обучение на накопленных патчах**

За месяц накопилось 8 патчей: AI постоянно забывает про мягкое удаление (`SoftDeletes`), предлагает `delete()` вместо `softDelete()`. Запускаете `/kodla:evolve plan`. Скилл анализирует патчи, добавляет правило в `kodla-plan-context`: "всегда проверять трейт SoftDeletes перед операциями удаления".

**Улучшение всех скиллов сразу**

Запускаете `/kodla:evolve all`. Скилл проходит по всем установленным скиллам, анализирует паттерны и предлагает набор улучшений: 3 правила для plan-context, 2 для implement-plan-context, 1 для fix-context. Вы подтверждаете или отклоняете каждое.

#### Не делает

Не редактирует базовые файлы скиллов (только skill-context), не создаёт новые скиллы, не применяет изменения без вашего подтверждения.

---

### kodla-unittest

**Пишет или дополняет unit-тесты для конкретного метода, функции или файла-класса — в стиле, согласованном с проектом.**

Мультиязычный навык: best practices хранятся по языкам в `references/<язык>/rules.md` (сейчас заполнен PHP — PHPUnit/Pest, Laravel-специфика, mocking, антипаттерны; структура позволяет добавлять Go, JS/TS, Python и другие по мере надобности). Определяет тест-фреймворк проекта, повторяет naming и mocking-подход из существующих тестов, запускает тесты и чинит падения. Требует **явную** цель — метод, функцию или путь к файлу; scope не угадывается и не определяется автоматически из tasar/плана/git diff.

#### Когда использовать

- Нужно покрыть тестами конкретный метод класса, функцию или файл
- После `/tasar:apply`, `/kodla:implement-plan` или `/kodla:check-tasks` — добавить тесты на только что реализованное (передав список изменённых файлов явно)

#### Примеры

**Конкретный метод**

```
/kodla-unittest PaymentService::charge
```

Покрывает метод: happy path + edge cases (значимые ветки `if`/`match`/`throw`).

**Файл-класс**

```
/kodla-unittest src/Services/PaymentService.php
```

Покрывает все публичные методы файла.

**После реализации**

```
/kodla-unittest src/Services/AuthService.php src/Controllers/AuthController.php
```

Явно переданный список изменённых файлов (например, из отчёта `/kodla:implement-plan`) — навык не ищет их сам.

#### Не делает

Не модифицирует production-код без явного согласия, не пишет тесты на код фреймворка, не удаляет существующие тесты автоматически, не определяет scope самостоятельно.

---

### kodla-woodpecker-ci

**Генерирует конфигурации Woodpecker CI pipeline в `.woodpecker/` — с учётом типа backend и без типичных ошибок.**

Анализирует tech-стек (PHP, Node.js, Go) через `.kodla/config.yaml` или файловые маркеры. Предлагает три варианта backend: docker, local или multi (build в Docker + deploy на хосте). Применяет best practices из документации и предотвращает 6 типичных ошибок конфигурации.

#### Когда использовать

- Нужно настроить CI для проекта с Woodpecker CI
- Хотите multi-backend пайплайн: сборка в Docker, деплой напрямую на сервере
- После настройки сервера — добавить `.woodpecker/` конфиги не вспоминая детали синтаксиса

#### Примеры

**PHP-проект с деплоем на тот же сервер**

Laravel-проект, Woodpecker стоит на том же сервере. Запускаете `/kodla-woodpecker-ci`. Скилл определяет PHP по `composer.json`, предлагает multi-backend. Создаёт два файла:

```yaml
# .woodpecker/build.yml — на docker-агенте
steps:
  - name: install
    image: composer:2   # Docker контейнер
  - name: package
    image: alpine:3.20  # создаёт tar-архив в /tmp/woodpecker-build/

# .woodpecker/deploy.yml — на local-агенте
depends_on: [build]
steps:
  - name: deploy
    image: bash         # shell на хосте, не Docker image
    commands:
      - /var/www/myapp/deploy.sh
```

Автоматически добавляет `lfs: false` (предотвращает `git: 'lfs' is not a git command`) и tar-fix через `/tmp` (предотвращает `file changed as we read it`).

**Node.js проект, только тесты**

```
/kodla-woodpecker-ci node
```

Создаёт `.woodpecker/pipeline.yml` с `node:22-alpine`, `npm ci` + `npm test`.

#### Не делает

Не устанавливает и не настраивает сервер Woodpecker CI, не генерирует systemd-юниты или docker-compose для самого Woodpecker.

---

### kodla-larastan

**Устанавливает и настраивает статический анализ PHPStan/Larastan для Laravel-проекта.**

Определяет Laravel по `laravel/framework` в `composer.json`. Устанавливает `larastan/larastan`, `shipmonk/dead-code-detector`, `tomasvotruba/bladestan` (только отсутствующие пакеты), генерирует `phpstan.neon` с правильным набором `includes` и стартовым `level: 5`. Поднимает лимит памяти по умолчанию через `composer.json` → `scripts.analyse`, чтобы не набирать `--memory-limit=1G` вручную. Для проектов с накопленным кодом предлагает сгенерировать `phpstan-baseline.neon`.

#### Когда использовать

- Новый Laravel-проект — нужен статический анализ с нуля
- Существующий Laravel-проект без PHPStan — хотите начать ловить только новые ошибки, не утонув в старых
- `phpstan.neon` уже есть, но не хватает `bladestan`/`dead-code-detector` — нужно точечно дополнить

#### Примеры

**Новый Laravel-проект**

Запускаете `/kodla-larastan`. Скилл находит `laravel/framework`, ставит три пакета, создаёт `phpstan.neon`:

```neon
includes:
    - vendor/larastan/larastan/extension.neon
    - vendor/nesbot/carbon/extension.neon
    - vendor/tomasvotruba/bladestan/config/extension.neon
    - vendor/shipmonk/dead-code-detector/rules.neon

parameters:
    level: 5 #Level лучше постепенно поднимать до 8–max.
    paths:
        - app/
        - routes/
```

Добавляет в `composer.json` скрипт `"analyse": "phpstan analyse --memory-limit=1G"` — дальше просто `composer analyse`.

**Существующий проект с накопленным кодом**

На вопрос «существующий или новый проект» отвечаете «существующий». Скилл выполняет `vendor/bin/phpstan analyse --generate-baseline --memory-limit=1G`, добавляет `phpstan-baseline.neon` последней строкой в `includes`. Старые ошибки заморожены, новые ловятся сразу.

#### Не делает

Не поддерживает не-Laravel PHP-проекты (обычный PHPStan без Larastan), не устанавливает `phpstan/phpstan` явно (приходит транзитивно через `larastan/larastan`), не перезаписывает существующий `phpstan.neon` без подтверждения.

## Tasar

Tasar — система управления изменениями, встроенная в kodla. Каждое нетривиальное изменение проходит полный цикл: предложение → дизайн → задачи → реализация → архив. Артефакты хранятся в `tasar/changes/<name>/` и синхронизируются со спеками проекта.

> Если в вашем проекте есть папка `tasar/`, скилл `/kodla:plan` автоматически перенаправляет к `/tasar-propose`.

### tasar-propose

**Создаёт изменение — proposal, design, задачи и дельта-спек за один шаг.**

Принимает описание что нужно сделать, создаёт папку `tasar/changes/<name>/` и последовательно заполняет четыре артефакта: proposal.md, design.md, tasks.md, specs/. Задаёт уточняющие вопросы только когда контекст неясен.

#### Когда использовать

- Задача нетривиальная и нужны документация + согласованный список задач
- Хотите обсудить подход до начала написания кода
- `/kodla:plan` автоматически перенаправляет сюда если в проекте есть `tasar/`

#### Примеры

**Новая фича с полной документацией**

Нужно интегрировать Stripe для приёма оплаты. Запускаете `/tasar-propose add-payments Интегрировать Stripe для подписок`. Скилл создаёт proposal (что и зачем), design (выбор библиотеки, схема интеграции), 12 задач в правильном порядке, дельта-спек с новыми требованиями к платёжному модулю.

**Автоматический редирект из kodla:plan**

В проекте есть `tasar/`. Пишете `/kodla:plan добавить экспорт в CSV`. Скилл замечает tasar-структуру и автоматически перенаправляет к `/tasar-propose` — создаётся полноценное изменение вместо простого плана.

#### Не делает

Не пишет код приложения, не реализует задачи — только документация и планирование.

---

### tasar-apply

**Реализует задачи из изменения tasar — последовательно, с обновлением артефактов по ходу.**

Читает все артефакты изменения, показывает прогресс и выполняет задачи одну за другой. Если подход меняется в процессе — сразу обновляет `design.md` и `tasks.md`, не откладывая на конец сессии.

#### Когда использовать

- После `/tasar-propose` — артефакты созданы, пора реализовывать
- При возобновлении прерванной реализации — продолжает с первой незавершённой задачи
- Для просмотра прогресса без запуска реализации (`/tasar:apply status`)

#### Примеры

**Реализация платёжной интеграции**

После `/tasar-propose add-payments` запускаете `/tasar:apply add-payments`. Скилл читает 12 задач, выполняет 1–5 (модели, миграции, сервис), останавливается для подтверждения перед миграцией БД. После подтверждения продолжает с 6-й задачи.

**Возобновление прерванной работы**

На следующий день снова запускаете `/tasar:apply`. Скилл находит активное изменение `add-payments`, видит что выполнено 7 из 12 задач и продолжает с 8-й — без необходимости объяснять контекст заново.

#### Не делает

Не создаёт новые изменения, не архивирует выполненные.

---

### tasar-archive

**Архивирует завершённое изменение — перемещает в `archive/` с датой и синхронизирует спеки.**

Проверяет что все задачи выполнены, согласовывает артефакты с реальной реализацией, синхронизирует дельта-спек в `tasar/specs/`, перемещает изменение в `tasar/changes/archive/YYYY-MM-DD-name/`.

#### Когда использовать

- Все задачи выполнены и проверены через `/kodla:check-tasks`
- Перед началом следующего изменения — держать `changes/` чистым

#### Примеры

**Архивирование после реализации**

Все 12 задач `add-payments` выполнены. Запускаете `/tasar:archive add-payments`. Скилл синхронизирует `specs/payments.md` с главными спеками проекта, перемещает папку в `archive/2026-05-01-add-payments`. История изменения сохраняется, `changes/` остаётся чистым.

**Архивирование с незавершёнными задачами**

Запускаете `/tasar:archive` и скилл находит 2 незавершённые задачи — предупреждает, но не блокирует. Вы можете архивировать с пометкой или вернуться к реализации.

#### Не делает

Не блокирует архивирование при предупреждениях, не архивирует без явного подтверждения пользователя.

## Рабочий процесс

Скиллы работают как последовательный конвейер: понять → спланировать → уточнить → реализовать → проверить.

```
Новый проект:
  kodla-init → kodla-plan → kodla-implement-plan → kodla-check-tasks → kodla-commit

Сложная фича (есть сомнения в подходе):
  kodla-research → kodla-plan → kodla-improve → kodla-implement-plan → kodla-check-tasks → kodla-commit

Быстрая фича (подход ясен):
  kodla-plan → kodla-implement-plan → kodla-commit

Улучшение готового плана:
  kodla-improve → kodla-implement-plan

Исправить баг:
  kodla-fix → kodla-commit

Документировать проект:
  kodla-docs

Добавить автоматизацию в любой момент:
  kodla-makefile (независимо от других скиллов)

Настроить CI/CD пайплайн:
  kodla-woodpecker-ci (независимо от других скиллов)

Настроить статический анализ Laravel:
  kodla-larastan (независимо от других скиллов)

Зафиксировать знания по технологии:
  kodla-reference (независимо от других скиллов)

С tasar (сложные изменения с документацией):
  tasar-propose → tasar-apply → tasar-archive

Улучшить AI после накопления патчей:
  kodla-evolve
```

### Типичная сессия

```
# 1. Один раз для проекта
/kodla:init

# 2. Перед каждой нетривиальной задачей
/kodla:plan добавить систему рейтингов для товаров

# 3. Если план кажется неполным
/kodla:improve

# 4. Реализация
/kodla:implement-plan

# 5. Проверка перед PR
/kodla:check-tasks
```

> **Совет:** `kodla-init` нужно запустить один раз. После этого все агенты автоматически получают контекст проекта через `.kodla/` — не нужно объяснять стек в каждом новом чате.
